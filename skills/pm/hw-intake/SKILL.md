# hw-intake — 项目入口与路由判定

## 1. Purpose

本 Skill 是智能硬件 PM Agent 系统的**唯一入口**。所有新项目必须经过本 Skill 才能进入后续研究、规划或 PRD 阶段。

核心任务：
- 将零散的项目来源资料转换为结构化的项目启动卡
- 基于证据（而非猜测）完成 L1/L2/L3 路由判定
- 生成对应路由的文档任务包
- 准备 Gate 1 审批简报，提交人工 PM 批准

在 Agent 工作流中的位置：**Phase 0（启动）→ Gate 1 → Phase 1（研究）**。本 Skill 是 Gate 1 的守门人。路由判定必须在启动时完成，不在研究之后才判断路线。

## 2. Context

### 触发条件
- 用户发起新项目讨论、提交项目简述、上传项目资料、或明确提出"新项目"/"启动一个项目"
- 用户引用已有产品并说明需要变更、升级、降本或定制

### 前置条件
- 无强制前置条件（本 Skill 是系统入口）
- 最低启动要求：用户提供至少一段项目简述（一句话即可启动）

### 输入
- 项目来源资料（任意形式）：口头简述、文档链接、PRD 草稿、客户需求书、售后工单、管理层决策、合同/SOW、招标文件
- 资料清单（source-manifest）：Agent 协助登记，用户只需上传文件或提供链接，不需要手工整理内容

### 输出消费者

| 消费者 | 消费内容 | 时机 |
|--------|----------|------|
| 人工 PM | Gate 1 简报 | 本 Skill 产出后立即送审 |
| Researcher Agent | 启动卡 + 路由判定 | Gate 1 批准后，进入研究阶段 |
| PM Agent（下游 Skill） | 任务包（文档清单 + 依赖关系） | Gate 1 批准后，按任务包执行 |
| Reviewer Agent | Gate 1 简报（含 AI 路由复核） | 本 Skill 产出后独立审查 |

### 不负责
- 不执行具体研究（市场、用户、竞品）— 那是 Researcher Agent 的工作
- 不编写 PRD 或产品定义 — 那是 PM Agent 下游 Skill 的工作
- 不自行批准路由 — Gate 1 是人工决策点，Agent 只提交分析供审批
- 不编译正式任务包（含执行指令）— 任务编译仅在人工 Gate 1 批准之后

## 3. Operating Principles

### 原则 1：路由现在判定，不等研究之后
路由判定（L1/L2/L3）必须在项目启动时完成，作为 Gate 1 的核心决策。不能在研究完成后再判断路线——"先研究看看"是不可接受的偷懒。

**反面行为**：先启动市场研究，"等研究完再看走哪条路"。这会把 L1 项目拖入不必要的深度研究，或让 L3 项目在研究不足的情况下做出关键决策。

**违反后果**：L1 项目可能被执行了完整研究链（浪费时间和资源）；L3 项目可能因研究阶段安排不足而遗漏关键风险维度。路由是规划决策，不是研究结论。

---

### 原则 2：证据先行，无证据不打低风险
路由判定中的每个风险维度（市场、用户、技术、供应链、认证、投入、交付）必须有证据支撑其评级。没有证据时，默认至少按"中风险"处理，不能凭经验或直觉打"低"。

**反面行为**："这个市场我们很熟，打低风险没问题"——在没有引用任何研究数据、历史证据或客户反馈的情况下降低风险评级。

**违反后果**：被低估的风险维度对应的研究被裁剪，后期发现问题时已完成不可逆的设计或供应链决策。

---

### 原则 3：一次只问一个问题，按依赖顺序推进
互动访谈每轮只提一个问题。问题的顺序由依赖关系决定（准入 → 产品对象 → 基线/复用 → 差异 → 风险 → 摘要），不可以随机主题切换，也不可以把两个独立决策拼在一个问题里。

**反面行为**：一次性列出 10 个问题让用户填写；跳过产品对象判断直接问差异范围；在准入未确认时询问详细风险评级；把"目标市场"和"技术方案"塞进同一个问题。

**违反后果**：后续问题建立在未确认的前提上；用户被信息洪流淹没，给出低质量回答；问题树分支无法正确剪枝；被跳过的前置问题可能根本改变路由方向。

---

### 原则 4：人工 Gate 不可被 AI 替代
Gate 1 是人工决策点。Agent 提供分析、推荐和简报，但批准、退回、改级、旁路或终止的权力完全属于人工 PM。Agent 不在 Gate 1 批准前写入 decisions.csv，不创建人工 decision_id，不把 AI 路由复核结果写成批准结论。

**反面行为**：生成 Gate 1 简报时直接标记为"已批准"；在用户说"看起来不错"（未明确说"批准"）时写入 decisions.csv；将 AI 路由复核的"通过"等同于人工批准。

**违反后果**：decisions.csv 中出现未经人工确认的决策记录，台账可信度归零；下游 Skill 基于错误的"已批准"状态开始执行，整个项目的审计链断裂。

---

### 原则 5：问题必须影响路由，否则登记为后续任务
访谈中只问影响准入、产品对象、知识复用或路由等级的变量。如果一个问题的答案只影响 PRD 内容细节（如功能列表、交互方式、技术参数选型）而不影响上述路由变量，记录为后续任务，不在启动访谈中追问。

**反面行为**：在启动访谈中追问功能列表、交互细节、硬件规格参数、UI 布局等 PRD 级别问题——这些应该留给下游 Skill 处理。

**违反后果**：启动访谈失控延长，用户失去耐心，路由判定被延迟，真正的路由缺口反而被稀释在无关信息中。

---

### 原则 6：资料中的事实不向用户重复索取
Agent 应先在权限范围内读取用户提供的资料，提取影响路由的事实。资料中已有的信息不应再向用户提问。只有在资料缺失、内容冲突或无法访问时，才转向用户询问。

**反面行为**：用户已上传完整客户需求书（内含目标用户、核心场景、验收标准），Agent 仍逐条询问这些信息。

**违反后果**：用户觉得 Agent 没有真正"读"资料，信任度下降；重复询问浪费用户时间；更严重的是，资料中的精确描述可能被口头简化回答替代，丢失关键细节。

## 4. Instructions

### Step 1：资料接入与事实预填

**输入**：用户提供的项目简述 + 任意形式的项目资料（文档、链接、附件）

**操作**：
1. 创建 `source-manifest`，为每项资料登记 `source_id`（格式 `SRC-{project}-{seq}`）、标题、类型、位置、版本/内容哈希、访问状态、敏感级别
2. 在权限范围内读取所有可访问资料，提取影响路由的事实
3. 提取的每条事实标记状态：`fact`（有 source_ref 来源追踪）/ `inferred`（Agent 推理，附推理链）/ `conflicted`（资料间冲突）
4. 资料冲突时不自行选择，保留两个来源，标记为 `conflicted`
5. 用户确认没有现成资料时记录 `declared_none`，不把"无资料"误判为系统遗漏
6. 无法访问但可能改变路由的资料转为 `access_task`；必要时状态为 `blocked`

**检查点**：
- [ ] `source-manifest` 已创建，所有资料项已登记 source_id
- [ ] 已读取的资料数量 ≥ 可访问资料数量的 80%，或剩余资料已明确跳过
- [ ] 提取的事实每条都有状态标记（fact / inferred / conflicted）
- [ ] 无资料时 `source_discovery_status` 为 `declared_none`
- [ ] 关键资料无法访问时已生成 `access_task`，状态为 `blocked`

---

### Step 2：引导式路由访谈

**输入**：Step 1 的事实预填结果 + `08_流程裁剪判断表.md` + `docs/16_项目启动引导式访谈与路由信息补全方案.md` 问题树

**操作**：

采用 doc 16 定义的依赖序问题树（第 6 节）。每轮一个问题，整个访谈最多 6 个问题（含因"不知道"产生的补充追问）。问题选择器逻辑：每次选择问题树中**前置条件已解决**的第一个未回答问题。

问题树的六个区域按依赖顺序排列：

| 序号 | 问题域 | 目标变量 | 路由影响 | 前置条件 |
|------|--------|----------|----------|----------|
| Q1 | A：工作流准入 | 是否进入智能硬件产品开发工作流 | 决定进入（in_scope）/ 旁路（out_of_scope）/ 阻塞（blocked） | 资料接入已完成 |
| Q2 | B：产品对象 | 既有产品变更 / 同品类新 SKU / 新品类 | 决定 L1 / L2 / L3 候选分支 | Q1 = in_scope |
| Q3 | C：基线与知识复用 | 是否有可复用的产品基线、品类研究、市场数据 | 决定 L1 vs L2 vs L3 的关键分叉 | Q2 已确认 |
| Q4 | D：差异范围 | 目标市场/用户/场景/竞品/功能/技术方案的差异程度和可补齐性 | 决定 L2 vs L3 | Q3 确认可复用（L2 分支），或 Q2 = 新品类直接进入 |
| Q5 | E：风险与任务修正 | 7 个风险维度的评级及对应的专项研究/验证需求 | 微调路由等级和任务包范围 | Q2-Q4 完成 |
| Q6 | F：摘要确认 | 用户确认所有已收集的事实摘要 | 锁定路由快照，进入产出阶段 | Q1-Q5 完成 |

每个问题卡片的格式（对齐 doc 16 第 7 节问题卡片格式）：

```
当前进度：{问题域名称}（{当前序号}/{预计总问题数}）

已知事实：{从资料和已确认回答中提取的关键事实，≤3 条，每条附来源}

问题：{一个明确的问题，只问一个路由变量}

建议答案：{推荐答案或"暂无推荐，请确认"}
依据：{推荐答案的证据依据；无证据时明确写"暂无证据支撑，以下为推测"}

可选回答：
A. {选项 A — 对路由的影响最大的选项放在前面}
B. {选项 B}
C. {选项 C 或 "不知道"}

对路由的影响：{选择不同答案会如何改变路线判定，每种情况一句话说明}
```

互动规则：
- 用户回答后立即更新事实快照，重新计算下一个问题（对齐 doc 16 第 3.6 节）
- 已被前一答案剪枝的问题分支不再询问
- 用户回答"不知道"时，按 doc 16 第 8.1 节追问三个补充项（谁最可能知道 / 可从哪个文档或系统获得 / 何时需要获得），记录为结构化输入缺口 `{owner, expected_source, due_at, blocking, next_action}`
- 资料与口头答案冲突时标记 `conflicted`，向有决策权的人确认；冲突影响准入、产品对象或知识复用时，状态为 `blocked`
- 用户纠正非路由信息时（如纠正功能描述但不改变路由），记录为后续任务，不重新打开已关闭的问题分支
- 若阻塞项涉及跨角色研究或决策，且预计无法在一次访谈中解决，可按 doc 16 第 8.4 节升级为轻量 Wayfinder 模式：创建路由地图（目的地固定为 Gate 1 路由建议就绪），标记 `gap_type`、`interaction`（HITL/AFK）、`depends_on`

**检查点**：
- [ ] 问题总数 ≤ 6（含"不知道"的补充追问）
- [ ] 每个问题卡片包含 5 个要素：已知事实、问题、建议答案及依据、可选回答、路由影响
- [ ] 推荐答案引用已知证据；无证据时明确写"暂无推荐"
- [ ] 路由快照中无阻塞缺口（除非 `blocked` 终态）
- [ ] 已确认的事实有来源追踪（source_ref 或 user_answer）
- [ ] "不知道"的回答已转为结构化输入缺口（owner + expected_source + due_at + blocking）

### Step 3：生成路由判定

**输入**：Step 2 的路由快照 + `08_流程裁剪判断表.md`

**操作**：
1. 根据已确认的路由快照，对照 `08_流程裁剪判断表.md` 第 2 节（项目类型与文档要求表）确定流程等级
2. 对照 `08_流程裁剪判断表.md` 第 2A 节（三档流程必需文档与输入补齐）确定必需文档清单和可接受替代证据
3. 对照 `08_流程裁剪判断表.md` 第 3 节（可跳过条件）逐项检查每个阶段是否满足裁剪条件，写入裁剪理由和替代证据
4. 检查 `08_流程裁剪判断表.md` 第 3A 节（直接进入 PRD 的条件），判断是否可以跳过产品定义直接进入 PRD
5. 生成路由判定结论：L1 / L2 / L3 / out_of_scope / blocked

路由就绪条件（对齐 doc 16 第 9 节停止条件）：

| 终态 | 就绪条件 |
|------|----------|
| L1 | in_scope + 既有产品不创建新 SKU + 存在有效产品基线或 PRD + 定位/目标市场/核心用户可复用 + 本次变更需要产品取舍 + 阻塞缺口为空 |
| L2 | in_scope + 同品类新 SKU + 存在可引用的品类研究 + 关键差异已识别 + 差异可通过有限专项研究补齐 + 阻塞缺口为空 |
| L3 | in_scope + (新品类 / 缺少可复用证据的新市场 / 既有品类研究无法支撑产品定义) + 已说明需要从头补齐的研究链 + 已说明"为什么现有知识不可复用"的路由证据 |
| out_of_scope | 不进入智能硬件产品开发工作流 + 已明确旁路流程和接收角色 + 已记录重新进入条件 |
| blocked | 已明确阻塞变量和冲突 + 每个阻塞项有责任人/预期来源/下一步/阻塞的路由分支 + 下游依赖已停止追问 |

**检查点**：
- [ ] 路由等级的判定依据引用 ≥1 条来源可追溯的事实或证据
- [ ] 7 个风险维度（市场/用户/技术/供应链/认证/投入/交付）中 ≥4 个有评级（高/中/低）
- [ ] 每个"低风险"评级有对应的证据来源（source_ref 或 evidence_ref）
- [ ] 每份被裁剪（跳过）的文档在流程裁剪结论中写明了裁剪理由或替代证据
- [ ] `08_流程裁剪判断表.md` 第 4 节最小保留项（7 项：目标用户/客户、使用场景、范围边界、关键证据、关键假设、风险、验收标准）全部有内容或标记为不适用

---

### Step 4：呈现 Intent Card 并暂停等待确认

**输入**：Step 3 的路由判定结论

**操作**：

采用 market-deep-research 的 Intent Card 模式——先呈现分析意图，暂停等待人工确认，确认后才进入产出阶段。本步骤的核心目的：让用户在 Agent 投入完整产出之前确认路由方向正确，避免返工。

Intent Card 格式：

```
## 路由 Intent Card — {项目名称}

### 当前理解
- 项目类型：{既有产品变更 / 同品类新 SKU / 全新品类 / 不进入产品开发工作流}
- 推荐流程等级：**L1 轻量 / L2 标准 / L3 完整**
- 核心理由：{≤3 句话，引用关键事实}

### 路由依据摘要
| 维度 | 评级 | 依据 |
|------|------|------|
| 市场不确定性 | {高/中/低} | {≤2 句话，附来源} |
| 用户不确定性 | {高/中/低} | {≤2 句话，附来源} |
| 技术不确定性 | {高/中/低} | {≤2 句话，附来源} |
| 供应链不确定性 | {高/中/低} | {≤2 句话，附来源} |
| 认证合规风险 | {高/中/低} | {≤2 句话，附来源} |
| 投入规模 | {高/中/低} | {≤2 句话，附来源} |
| 交付风险 | {高/中/低} | {≤2 句话，附来源} |

### 推荐任务范围
- 必需文档：{列表}（共 {N} 份）
- 建议跳过：{列表}（理由：{每条裁剪理由}）
- 需补齐输入：{列表或"无"}

### 阻塞项
{阻塞项列表，或"无阻塞项，可立即进入产出"}

---
**请确认以上路由判定，或提出调整。**
回复"确认"继续生成 Gate 1 送审包；回复具体调整意见重新判定。
```

**关键规则**：
- Intent Card 呈交后 Agent 必须暂停，不进入 Step 5
- 等待用户明确回复（"确认"/"批准此路由"/具体调整意见）
- 用户的口头认可（"看起来差不多"、"应该没问题吧"）不算确认——要求用户给出明确肯定
- 用户提出调整时，回到对应的问题域重新判定；只调整受影响的维度，整个路由不重来

**检查点**：
- [ ] Intent Card 已呈现给用户，所有字段已填写
- [ ] Agent 已暂停，等待用户响应（未自行进入产出阶段）
- [ ] 用户回复明确（"确认"/"批准" 或具体调整意见）
- [ ] 若用户调整，已回到对应问题域修正并重新呈现 Intent Card
- [ ] 用户确认后路由快照已锁定（不再修改路由等级）

### Step 5：生成项目产出

**输入**：Step 4 已确认的路由快照 + `00_项目启动卡.md` 模板

**操作**：
1. 按本 Skill 第 5.2 节"项目启动卡模板"逐项填写，生成 `output/{project}/00_项目启动卡.md`
2. 按本 Skill 第 5.3 节"Gate 1 简报模板"逐项填写，生成 `output/{project}/gate-1-briefing.md`

### Step 6：提交 Gate 1 并等待人工审批

**输入**：Step 5 的完整产出文件

**操作**：
1. 将启动卡、Gate 1 简报、AI 路由复核结果打包为 Gate 1 送审包
2. 向用户呈现审批提示（包含审批要点清单和可用的审批指令）
3. 等待人工 PM 的审批指令

人工 PM 的五种可能响应及 Agent 对应动作：

| 人工指令 | Agent 动作 |
|----------|-----------|
| **批准**（"批准"/"approve"/"确认"） | 进入 Step 7，写入 decisions.csv |
| **退回**（"退回"/"reject" + 原因） | 根据退回原因回到对应的问题域（Step 2 对应 Q 或 Step 3），修正后重新走 Step 4-6 |
| **改级**（"改为 L{N}"） | 以人工指定等级为准，更新路由快照，重新生成 Step 5 产出，再次提交审批 |
| **旁路**（"旁路到 X 流程"） | 写入 decisions.csv（status=bypassed），记录旁路原因和目标流程 |
| **终止**（"终止"/"不做了"） | 写入 decisions.csv（status=terminated），记录终止原因 |

审批提示格式：
```
## Gate 1 审批请求

送审文件：
- 项目启动卡：output/{project}/00_项目启动卡.md
- Gate 1 简报：output/{project}/gate-1-briefing.md
- 任务包：output/{project}/任务包.md
- AI 路由复核：{通过 / 有 N 条非阻塞 findings}

请审批以下内容：
1. 路由等级：L1 / L2 / L3
2. 文档范围：{N} 份必需 + {M} 份可选
3. 输入补齐责任人

可用回复：
- "批准" — 进入研究阶段
- "退回：{原因}" — 说明退回原因，Agent 将重新判定
- "改为 L{N}" — 手动指定路由等级
- "旁路到 {流程}" — 不进入本工作流
- "终止" — 终止此项目
```

**检查点**：
- [ ] Gate 1 送审包已完整呈现给用户
- [ ] Agent 未在人工明确批准前写入 decisions.csv 或标记项目为"已批准"
- [ ] 人工审批指令明确且属于五种合法指令之一

## 6. Quality Bar

Reviewer 按以下 checklist 逐项检查，全部通过才算本 Skill 完成：

- [ ] **路由判定有证据**：L1/L2/L3 判定引用了 ≥1 条来源可追溯的事实或证据（source_ref 或 user_answer）；每个"低风险"评级 ≥1 条有对应的 source_ref
- [ ] **问题卡片完整**：每个访谈问题包含已知事实、问题、建议答案及依据、可选回答、路由影响 5 个要素；问题总数 ≤ 6（含补充追问）
- [ ] **启动卡无占位符**：启动卡中无 TBD、TODO、"根据实际情况调整"等占位符；未确认项写"待确认"并标注 expected_source 和 due_at（如"待确认 — expected_source: 业务负责人, due_at: 2026-08-15"）
- [ ] **裁剪有理由**：每份被跳过的文档在流程裁剪结论表中写明了裁剪理由或替代证据；理由不能是"感觉不需要"、"老板说不用"、"这个项目简单"
- [ ] **摘要 ≤500 字**：Gate 1 简报的"路由推荐" + "选项分析" + "关键假设与风险"三个章节的总字数 ≤ 500 字
- [ ] **decisions.csv 写入时机正确**：decisions.csv 中的 route_approval 记录的 decided_at 时间晚于人工 PM 的 Gate 1 批准指令时间；不存在"Agent 预言批准"（即 Agent 在人工确认前写入 approved 状态）
- [ ] **最小保留项全覆盖**：启动卡第 2 节 7 个风险维度中 ≥4 个有评级（高/中/低，而非空白）；启动卡第 4 节 8 个 PRD 前置输入全部有状态标记（已知/假设/缺失，而非空白）

## 8. Best Practices

### 好的输出 vs 差的输出

**好的路由判定理由：**
> 推荐 L2 标准流程。依据：(1) 用户确认本项目为同品类新 SKU 而非既有产品变更（Q2 回答）；(2) 存在 `CWLS-2025` 无线链式开窗机品类市场研究报告（SRC-001），目标市场和核心用户特征可复用；(3) 差异集中在新增型号的电机规格和结构方案，可通过专项竞品分析（hw-competitive-analysis）和简版用户研究（hw-user-research）补齐（Q4 回答）。技术不确定性为中（新传感器选型），建议保留完整 PRD 和验证计划。

**差的路由判定理由：**
> 这个项目不算大，走 L2 就行。市场调研感觉没必要做太深。

---

**好的裁剪理由：**
> 市场与机会研究报告：简版。替代证据：CWLS-2025 品类研究报告（2025Q3，覆盖北美市场，6 个月内有效，source_id=SRC-001），仅需补充本型号的价格带和渠道差异化分析即可满足产品定义需求。

**差的裁剪理由：**
> 市场与机会研究报告：跳过。因为觉得不需要，这个市场我们熟。

---

**好的"不知道"处理：**
> 用户对"目标市场的认证要求"回答"不知道"。已追问：(1) 认证负责人最可能知道；(2) 可从 FCC/CE 认证数据库和历史认证文档获得；(3) 需要在 Gate 2 之前确认。已记录为输入缺口 GAP-{project}-003：owner=认证负责人，expected_source=认证数据库和历史文档，due_at=2026-08-15，blocking=true（阻塞完整合规研究范围确定）。认证要求确认前，认证合规风险维度暂按"高"处理（保守假设）。

**差的"不知道"处理：**
> 用户说不知道认证要求，那就假设没有特殊认证要求，继续按 L2 推进。如果后面发现有问题再说。

---

**好的 Intent Card 交互：**
> Agent 呈现 Intent Card → 用户："看起来不错，但我担心供应链不确定性你打了'低'，其实我们这次用了一个新供应商" → Agent 回到 Q5 风险域重新评估 → 供应链不确定性调整为"中" → 路由从 L1 调整为 L2 → 重新呈现 Intent Card → 用户："这次对了，确认" → Agent 进入产出。

**差的 Intent Card 交互：**
> Agent 呈现 Intent Card → 用户："嗯看着差不多" → Agent 理解为"确认"，直接进入产出 → 用户后来发现路由不对，要求推翻重来。

---

**好的 Gate 1 提交：**
> Agent 呈现完整的 Gate 1 简报，包含 5 个审批要点和 5 种可用回复指令。用户回复"批准" → Agent 在 decisions.csv 追加 DEC-{project}-001 → 通知用户"项目已就绪，Researcher Agent 可以开始市场研究"。

**差的 Gate 1 提交：**
> Agent 在 Gate 1 简报最后写"以上内容已自动批准，项目已进入研究阶段" → 用户发现 decisions.csv 中有一条自己没批准的记录 → 台账可信度丧失。

### 常见陷阱

| 陷阱 | 表现 | 正确做法 |
|------|------|----------|
| 过早承诺等级 | 用户说了半句话（"我们做个类似 XX 的产品"），Agent 就断定"这是 L2" | 走完整条准入→产品对象→基线→差异→风险的问题链后再判定；用 Q1-Q5 的答案约束路由 |
| 忽略"不知道"的信号 | 用户说"不知道"时，Agent 自行猜测填充（"一般来说这种情况是..."） | 追问 who/know/where/when（谁最可能知道 / 可从哪里获得 / 何时需要），生成带 owner + expected_source + due_at 的结构化缺口；暂按保守假设推进 |
| 用裁剪逃避研究 | 每个文档都标记"可跳过"，把 L3 项目硬凑成 L1 | 对照 `08_流程裁剪判断表.md` 第 3 节逐项验证可跳过条件；不满足条件的必须保留；记录裁剪决策的替代证据和风险 |
| 资料未读就提问 | 用户已上传客户需求书，但 Agent 没读就开始问"目标用户是谁" | Step 1 资料接入必须先完成：读取所有可访问资料，预填事实；只用访谈补齐资料中没有或冲突的部分 |
| Intent Card 形式化 | Intent Card 写完立即接"接下来我生成启动卡..."，不等用户确认 | Intent Card 必须暂停：写完后不产生任何输出，明确等待用户回复"确认"或调整意见 |
| "差不多"当确认 | 用户说"看起来差不多"、"应该没问题吧"时，Agent 当作批准处理 | 口头认可不算确认——要求用户给出明确肯定（"确认"、"批准"、"同意此路由"）；可以在 Intent Card 末尾加引导："如果认可以上路由，请回复'确认'，我将生成 Gate 1 送审包" |
