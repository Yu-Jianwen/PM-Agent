# hw-product-definition — 产品定义

## 1. Purpose

本 Skill 解决"为谁做、解决什么问题、产品是什么、边界在哪里"的问题。它将已批准的产品规划报告（hw-product-strategy）和 MRD/BRD（hw-mrd-brd）转化为一份结构化的产品定义文档，明确产品定位、目标用户的 JTBD（功能/情感/社会三层）、MVP 范围与显式边界、使用场景矩阵、硬件特有约束（BOM 成本目标、关键器件、认证要求、供应链约束）。

在 PM Agent 工作流中，本 Skill 位于 MRD/BRD（hw-mrd-brd）之后、PRD（hw-prd）之前。它承接"市场机会是什么、商业上为什么值得做"，产出"产品具体是什么、不做什么"。PRD 不应重新讨论产品定位和范围取舍，除非产品定义发生重大变化。

核心任务：
- 将市场机会和商业判断转化为具体的产品定位陈述
- 为每个目标用户角色定义功能、情感、社会三层 JTBD
- 划清 MVP 范围与显式边界（"不做"清单与"做"清单同等重要）
- 构建使用场景矩阵（主要/次要/明确排除）
- 锁定硬件约束（BOM 成本目标、关键器件、认证标准、供应链前置条件）
- 产出产品定义文档，作为 PRD 的直接上游输入

- 产品规划报告已通过 Gate 4 审批 AND MRD/BRD 已通过 Gate 5 审批

- 对于 L2/L3 路由：使用 `04_产品定义文档.md` 模板，独立产品定义

### 路由差异（L1 vs L2/L3）

| 维度 | L1 | L2/L3 |
|------|-----|-------|
| 使用模板 | `12_L1_轻量产品定义_PRD合并文档`（最小产品定义章节） | `04_产品定义文档`（完整文档） |
| 产品定义独立性 | 嵌入 PRD 合并文档，非独立文档 | 独立文档，完整章节 |
| JTBD 深度 | 仅覆盖变更/新增用户角色的核心 JTBD | 所有用户角色的功能+情感+社会 JTBD |
| 边界定义深度 | "本次不做"清单 | 完整的产品边界表（含排除理由和未来规划） |
| 场景矩阵 | 仅覆盖变更场景 | 主要/次要/排除三层场景矩阵 |
| 硬件约束 | 仅受影响的约束 | 完整 BOM 目标 + 关键器件 + 认证 + 供应链 |

### 不负责

- 不重新评估市场是否值得做 — 那是 MRD/BRD 的决策，本 Skill 只做"具体是什么产品"
- 不重新进行竞品分析 — 引用竞品研究分析报告的结论，不做增量研究
- 不定义功能需求的实现细节 — 那是 PRD 的工作
- 不定义技术方案或芯片型号 — 那是 PRD 硬件模块的工作
- 不自行批准产品定义 — Gate 6 是人工决策点

## 3. Operating Principles

### 原则 1：边界与范围同等重要

产品定义中的"不做"清单（产品边界）和"做"清单（MVP 范围）具有同等权重。每一条"不做"必须写明排除理由（成本不可行 / 技术风险 / 本版时间不够 / 留给后续版本 / 非目标用户需求）。边界不清会导致 PRD 阶段的需求范围持续膨胀。

**反面行为**：只列出 MVP 范围和功能清单，对"不做"清单写"暂无"或"待定"。或在边界表中写"后续根据资源情况再定"，不给排除理由。

**违反后果**：PRD 编写时 Reviewer 无法判断某条需求是否越界。开发阶段接到"顺便加个功能"的需求时，PM 没有产品定义中的"不做"依据来拒绝。硬件项目一旦进入模具和认证，范围变更成本极高。

---

### 原则 2：定位陈述必须可证伪

产品定位陈述（"对于【目标用户】，【产品名称】是【品类】，能够【核心价值】。不同于【替代方案】，我们的优势是【差异化】"）中的每个断言都必须能被验证。如果定位说"最省电的 X"，必须有可测量的功耗目标值支撑。如果定位说"最适合 Y 场景"，必须有 JTBD 和场景矩阵支撑这个"最适合"的具体含义。

**反面行为**：定位陈述使用不可证伪的营销语（"极致体验""行业标杆""重新定义 X""最智能的 Y"），但没有任何量化指标或可比参照——"最省电"没有功耗目标，"最智能"没有定义什么是智能。

**违反后果**：PRD 无法判断功能优先级（所有功能都可以被解释为"支撑极致体验"）。营销团队无法从定位中提取可传播的差异化卖点。Gate 6 审批时人工 PM 无法判断定位是否可信。

---

### 原则 3：JTBD 必须覆盖功能、情感、社会三层

每个目标用户角色的 JTBD 必须覆盖三个维度：功能任务（用户要完成什么操作）、情感任务（用户想感受什么）、社会任务（用户希望别人怎么看他）。只写功能任务会导致产品只解决工具性问题，忽略采纳和留存的情感/社会驱动因素。硬件产品的购买决策尤其受情感（"用起来安心""放在家里好看"）和社会（"朋友觉得我有品味""符合我的身份"）维度影响。

**反面行为**：JTBD 只写功能维度（"当用户离家时，想远程查看家中情况，以便确保安全"），不写情感维度（"想感到安心，知道自己随时可以确认家中无事"）和社会维度（"想让家人觉得自己是负责任的、有安全意识的家庭成员"）。

**违反后果**：产品定义缺失情感和社会锚点 → PRD 功能设计偏工具化 → 旗舰产品失去溢价理由 → 营销缺乏情感话术素材。功能可以被竞品复制，情感和社会价值才能建立差异化壁垒。

---

### 原则 4：硬件约束是硬约束，不能后置

BOM 成本目标、关键器件可用性、认证要求、供应链前置条件在产品定义阶段就必须作为硬约束写入，不能推到 PRD 阶段再"根据方案确定"。如果这些约束在产品定义中不明确，PRD 可能定义出技术上可行但经济上不可行或供应链上无法量产的需求。

**反面行为**：在产品定义中只写"成本目标待 PRD 阶段确定"、"认证要求待合规团队确认后补"、"关键器件选型由硬件团队在 PRD 阶段确定"。或写一个模糊的 BOM 目标（"成本尽量低"）而不给具体数字和构成。

**违反后果**：PRD 定义了需要 $25 BOM 的功能组合，但产品定义的商业模型基于 $18 BOM 目标 → PRD 需要大幅返工。PRD 选定的关键器件交期 52 周 → 项目周期被迫延期。认证未在产品定义阶段识别 → PRD 完成后才发现需要增加 shielding/re-design → 模具重开。

---

### 原则 5：场景矩阵必须有"排除"列

使用场景矩阵必须包含三个类别：主要场景（产品核心设计目标）、次要场景（产品可以覆盖但不是优化重点）、明确排除的场景（产品不做、不优化、不建议用户使用）。排除场景是边界的场景化表达——如果一个场景被明确排除，PRD 中对应该场景的功能需求就可以直接判定为越界。

**反面行为**：场景矩阵只有"主要场景"和"次要场景"两列，没有"明确排除"列。或"明确排除"列写"暂无"——实际上每个产品都有不应覆盖的场景，不写等于没有边界。

**违反后果**：PRD 阶段收到"用户也可能在 X 场景下使用"的需求时，没有场景矩阵中的排除声明作为拒绝依据 → 范围膨胀。开发和测试也不知道哪些场景不需要优化 → 资源浪费在非目标场景的 corner case 上。

---

### 原则 6：每条范围决策有证据或假设支撑

MVP 范围中每一条"必须做"和"不做"的决策，必须关联至少一条证据（evidence_id）或声明的假设（assumption_id）。不能基于 PM 个人判断或"行业惯例"决定范围。这是从产品定义阶段建立可追溯性的起点——PRD 将从这些 evidence_id 出发建立 requirement → evidence 的完整追溯链。

**反面行为**："这个功能必须有，因为竞品都有"（但没有引用竞品分析报告中的具体证据）。"这个功能不做，因为觉得不重要"（但没有引用用户研究中的优先级数据）。将范围决策写成无来源的意见列表。

**违反后果**：traceability 链在产品定义阶段断裂 → PRD 无法追溯需求来源 → Gate 6 审批时人工 PM 无法判断范围取舍是否合理 → Reviewer 标记 severity=blocker。

## 4. Instructions

### Step 1：加载上游输入与事实预填

- **输入**：读取产品规划报告 + MRD/BRD + 竞品研究分析报告 + 用户研究与 VOC 分析报告 + （L2+）合规研究报告 + `registers/evidence.csv` + `registers/assumptions.csv` + `registers/risks.csv`
- **操作**：
  1. 从产品规划报告提取：目标市场、产品"三定"（定位/定价/定渠道）、技术方向、关键决策记录
  2. 从 MRD/BRD 提取：市场规模与机会、目标用户角色链、竞品定位参照、定价策略、商业约束、成本目标、财务假设
  3. 从竞品研究分析报告提取：竞品定位对比表、竞品功能差异矩阵、竞品定价区间、竞品 BOM 估算
  4. 从用户研究与 VOC 分析报告提取：用户角色画像、使用场景列表、用户痛点与未满足需求、VOC 中的功能期望
  5. 从合规研究报告（L2+）提取：目标市场认证标准清单、强制性 vs 建议性认证、认证周期和时间线
  6. 从 evidence.csv 提取与目标用户、场景、竞品差异化、成本约束相关的证据行
  7. 从 assumptions.csv 提取与产品方向相关的未验证假设
  8. 从 risks.csv 提取与产品范围、硬件约束相关的已识别风险
  9. 创建"上游输入就绪检查表"：逐项核查前置条件是否满足，缺失输入标注为输入缺口
- **检查点**：
  - [ ] 产品规划报告、MRD/BRD 已读取，关键提取物已记录（定位、定价、用户角色、成本目标）
  - [ ] 竞品定位对比数据已提取，至少覆盖 3 个竞品
  - [ ] 用户角色画像已提取，至少区分主用户 / 次用户 / 决策者 / 付费者
  - [ ] 合规认证清单（L2+）或合规评估（L1）已提取
  - [ ] 上游输入就绪检查表已填写：所有"阻塞=是"的缺失输入有处理方式
  - [ ] 有"缺失 + 阻塞=是 + 未处理"时，本 Skill 不应进入 Step 2，向人工 PM 报告输入缺口

---

### Step 2：定义产品定位陈述

- **输入**：Step 1 提取的目标用户、竞品定位参照、差异化证据
- **操作**：
  1. 使用标准定位公式构建产品定位陈述：
     ```
     对于【目标用户/客户群体】，
     【产品名称】是一款【参照品类/方案类别】，
     能够【核心差异化价值——用户获得什么结果，不是产品有什么功能】。
     不同于【主要竞品或替代方案】，
     我们的核心优势是【可验证的差异化——不是"更好"，而是"不同在什么地方，为什么用户在乎这个不同"】。
     ```
  2. 定位陈述中的每个元素必须有来源：
     - "目标用户" → 引自 MRD/BRD 目标用户章节 + 用户研究报告 user persona
     - "参照品类" → 引自竞品分析报告的品类定义
     - "核心价值" → 引自用户研究中的 JTBD 和痛点，聚焦用户获得的结果而非产品功能
     - "差异化" → 引自竞品分析报告的差异矩阵，必须是竞品确实没有或做得差的能力
  3. 从定位陈述推导 3-5 条核心价值主张（value propositions），每条对应一个目标用户的核心任务
  4. 形成"竞品对标结论"：一句话总结本产品在竞品地图中的位置（高端/中端/入门、功能领先/性价比/场景专用）
  5. 编写"成本/结构约束"摘要：BOM 目标、关键成本驱动器件、对工业设计和结构方案的成本约束
  6. 填写定位语选择理由：说明为什么这个定位（而不是其他可选定位）是最优的——从市场空白、用户需求和竞品弱点三个角度给出理由
- **检查点**：
  - [ ] 定位陈述包含全部 5 个要素（目标用户、产品名/品类、核心价值、替代方案、差异化）
  - [ ] 定位陈述中的每个断言有可验证的来源（source_ref 或 evidence_id）
  - [ ] 核心价值主张 3-5 条，每条 ≤50 字，不包含功能罗列
  - [ ] 竞品对标结论有竞品分析报告中的差异矩阵数据支撑
  - [ ] 定位语选择理由从市场空白/用户需求/竞品弱点三个角度给出
  - [ ] 成本/结构约束不是"待定"——至少有一句话描述（如"BOM 目标 ≤$XX，关键成本驱动为 XX 器件，不含包装和配件"）

---

### Step 3：定义 JTBD（每个用户角色）

- **输入**：Step 1 提取的用户角色画像 + 用户研究中的场景和痛点
- **操作**：
  1. 为每个用户角色（主用户、次用户、决策者、付费者——如果决策者与付费者角色不同则分别定义）编写 JTBD
  2. 每个用户角色的 JTBD 必须覆盖三个维度：

  **功能任务（Functional Jobs）**：用户要完成什么操作、达成什么结果。
  - 格式："当【情境】，我想【动作/操作】，以便【结果/目的】。"
  - 至少 2 条功能任务，优先覆盖用户研究中高频出现的场景

  **情感任务（Emotional Jobs）**：用户在完成功能任务的过程中想感受什么、不想感受什么。
  - 格式："在使用【产品/场景】时，我想感到【正面情感】，不想感到【负面情感】。"
  - 至少 1 条情感任务，优先覆盖 VOC 中反复出现的情绪词（"安心""省心""不焦虑""有掌控感"）

  **社会任务（Social Jobs）**：用户希望别人怎么看待使用这个产品的自己。
  - 格式："当别人看到/知道我在用【产品】时，我希望他们认为我是【社会形象】。"
  - 至少 1 条社会任务，对于消费类硬件必须有，工业类硬件如无明确社会驱动因素可标注"不适用"并说明理由

  3. 对每条 JTBD，填写"当前方案"和"当前方案的失败点"：
     - "当前方案"：用户目前用什么方法/产品完成这个任务
     - "失败点"：当前方案在哪里让用户不满——这是产品的机会窗口
  4. 对每条 JTBD 关联证据（evidence_id）或假设（assumption_id）
- **检查点**：
  - [ ] 每个用户角色的 JTBD 表中至少包含功能任务（≥2 条）+ 情感任务（≥1 条）
  - [ ] 消费类硬件的主用户角色至少包含 1 条社会任务；不适用时有明确理由
  - [ ] 每条 JTBD 有"当前方案"和"失败点"（非空，非"无明显失败点"——如果真的没有失败点，说明这个任务不是产品机会）
  - [ ] 每条 JTBD 关联了至少 1 条 evidence_id 或 assumption_id
  - [ ] JTBD 格式使用"当...我想...以便..."，不写成功能需求（"设备应该支持 X"）

### Step 4：定义 MVP 范围与显式边界

- **输入**：Step 2 的定位陈述 + Step 3 的 JTBD + 竞品功能差异矩阵 + MRD/BRD 商业约束 + 成本目标
- **操作**：

  **第一部分：MVP 范围定义（"做什么"）**

  1. 使用 MoSCoW 方法定义产品范围，覆盖以下维度：
     - 硬件（形态、规格、性能、接口、配件）
     - 固件（设备端逻辑、通信协议、OTA）
     - APP/小程序（用户界面、交互流程）
     - 云端/后台（设备管理、数据服务、运营后台）
     - 安装与售后（安装方式、售后策略、保修条款）

  2. 对每个维度，按四个优先级列出条目：
     - **Must have（必须做）**：不做的后果是产品不可交付或不可用。对应 KANO 基本型需求 + 部分期望型。
     - **Should have（应该做）**：不做产品可以用但竞争力明显减弱。对应 KANO 期望型需求。本版本资源允许则做。
     - **Could have（可以做）**：锦上添花，有资源就做，没资源可砍。对应 KANO 兴奋型需求。
     - **Won't have this time（本版不做）**：明确排除，留给后续版本或永远不做。

  3. 每条条目描述不超过 2 句话，写明"是什么"不是"怎么实现"
  4. 每条 Must/Should 条目关联 evidence_id 或 assumption_id

  **第二部分：显式边界定义（"不做什么"）**

  5. 编写"不做清单"——这是产品定义中与 MVP 范围同等重要的章节。每一条"不做"必须包含：
     - **排除项**：明确排除什么功能/规格/场景/用户
     - **排除理由**：为什么不做的具体原因，必须属于以下分类之一：
       - `cost`：超出 BOM 目标或开发预算
       - `risk`：技术风险、供应链风险、认证风险过高
       - `phase`：留给后续版本，本版本先聚焦核心场景
       - `user`：不是目标用户的核心需求
       - `strategy`：与产品定位冲突
     - **触发条件**：什么情况下会重新考虑（如"竞品 X 发布类似功能后""第 2 版用户反馈强烈需要""芯片价格降到 X 以下"）
     - **影响范围**：不做这个对哪些用户角色/场景有影响

  6. "不做清单"必须覆盖以下容易膨胀的领域：
     - 平台兼容（iOS 版本下限、Android 版本下限、不支持的旧设备）
     - 场景边界（不做户外/不做多人协作/不做离线全功能）
     - 集成边界（不接入第三方平台 X、不支持某协议）
     - 服务边界（不提供上门安装、不提供 24h 客服）
     - 配件边界（不标配 X 配件、不支持用户自行更换 X）

- **检查点**：
  - [ ] 5 个维度（硬件/固件/APP/云端/安装售后）的 Must/Should/Could/Won't 表已填写，每个维度至少 1 条 Must
  - [ ] "不做清单"条目数 ≥ 5 条，每条有排除理由分类（cost/risk/phase/user/strategy 之一）
  - [ ] "不做清单"覆盖了平台兼容、场景边界、集成边界、服务边界、配件边界至少 3 个领域
  - [ ] 每条 Must/Should 条目关联了 ≥1 条 evidence_id 或 assumption_id
  - [ ] "不做清单"中的排除理由不是"暂不考虑""后续再说"等模糊措辞——每一条有具体的分类和触发条件
  - [ ] 范围表中没有与产品定位陈述冲突的条目（如定位"高性价比"但 Must 范围包含了高成本旗舰功能）

### Step 5：定义使用场景矩阵（主要 / 次要 / 明确排除）

- **输入**：Step 3 的 JTBD + Step 4 的 MVP 范围与边界 + 用户研究中的场景列表
- **操作**：
  1. 构建使用场景矩阵，包含三列：主要场景、次要场景、明确排除的场景

  **主要场景（Primary Scenarios）**：
  - 产品的核心设计目标——这些场景下的体验必须"好"，是资源投入的第一优先级
  - 每个场景包含：场景名称、场景描述（≤3 句话）、涉及的用户角色、对应的 JTBD、频率（每天/每周/每月/偶尔）、关键体验要求
  - 至少 3 个主要场景

  **次要场景（Secondary Scenarios）**：
  - 产品可以覆盖，但不是核心设计目标——"能用就行"，不需要极致优化
  - 每个场景包含：场景名称、场景描述（≤2 句话）、为什么是次要（是否低频/是否少数用户/是否边缘场景）、如果体验不佳是否会造成用户流失
  - 至少 2 个次要场景

  **明确排除的场景（Explicitly Excluded Scenarios）**：
  - 产品不做、不优化、不建议用户在这些场景下使用
  - 每个场景包含：场景名称、场景描述（≤1 句话）、排除理由分类（同 Step 4 的 cost/risk/phase/user/strategy）、如果用户强行在这个场景下使用会发生什么
  - 至少 2 个排除场景——如果写不出来，说明对产品边界思考不足

  2. 场景矩阵必须与 Step 4 的"不做清单"对齐：排除清单中的场景不能出现在主要或次要场景中
  3. 每个场景关联对应的 JTBD ID 和 evidence_id
- **检查点**：
  - [ ] 主要场景 ≥3 个，次要场景 ≥2 个，明确排除场景 ≥2 个
  - [ ] 每个主要场景有关键体验要求（可感知的质量标准，如"配网操作必须在 30 秒内完成"）
  - [ ] 次要场景标注了"如果体验不佳是否会造成用户流失"
  - [ ] 排除场景标注了"如果用户强行使用会发生什么"（不是"不推荐使用"就结束——描述具体会发生什么问题）
  - [ ] 场景矩阵与"不做清单"无冲突
  - [ ] 每个场景关联了 JTBD ID 或 evidence_id

### Step 6：定义硬件约束（成本、器件、认证、供应链）

- **输入**：MRD/BRD 中的成本目标 + 合规研究报告（L2+）+ 竞品分析中的 BOM 估算 + evidence.csv 中硬件相关证据
- **操作**：

  **1. BOM 成本目标**
  - 定义 BOM 成本目标（ex-factory，不含包装/物流/关税）
  - 拆解 BOM 成本到关键器件组：主控、通信模块、传感器、电源、结构件、包装
  - 标注每个器件组的成本区间（目标值和上限值），以及成本驱动的关键因素（芯片选型、工艺复杂度、采购量）
  - 如果当前竞品 BOM 估算与目标有差距，标注差距量和可能的降本路径

  **2. 关键器件**
  - 列出对产品功能和成本有决定性影响的 3-5 个关键器件
  - 每个器件标注：功能角色、对产品体验的影响（不选这个会损失什么）、供应风险（单一供应商/长交期/地缘政治敏感）、是否有 Pin-to-Pin 备选
  - 关键器件的选择必须对齐定位陈述：旗舰定位不能选入门级器件，性价比定位不能选高端溢价器件

  **3. 认证要求**
  - 列出目标市场/目标渠道的完整认证清单
  - 按类别分组：强制性认证（产品上市的必要条件）、建议性认证（不强制但有利销售）、参考性标准（行业最佳实践）
  - 每个认证标注：标准号/法规号、适用范围、预计认证周期、是否需要送样（影响项目排期）、对硬件设计的约束（如 EMC 要求影响 PCB layout、安全要求影响结构设计）
  - L1 项目如无合规研究报告，从 evidence.csv 和 MRD/BRD 中提取已知认证要求；未知部分标注为假设

  **4. 供应链约束**
  - 标注长交期器件（lead time > 12 周）
  - 标注对模具/工装的前置周期要求
  - 标注对量产爬坡的约束（如新供应商导入需要 3 个月、产线认证需要 2 个月）
  - 标注地缘政治或贸易合规对供应链的影响（出口管制器件、关税影响、原产地限制）
- **检查点**：
  - [ ] BOM 成本目标有具体数字（不是"尽量低"），且拆解到至少 4 个关键器件组
  - [ ] 关键器件清单 ≥3 个，每个标注了供应风险和备选方案
  - [ ] 认证清单中每个强制性认证有标准号和预计周期（不是"待确认"）
  - [ ] L1 项目如无合规研究报告但有认证假设，每个假设在 assumptions.csv 中有对应记录
  - [ ] 供应链约束覆盖了长交期器件、模具周期、量产爬坡至少 2 个维度
  - [ ] 硬件约束与产品定位陈述无冲突（如定位"极致性价比"但 BOM 成本目标高于竞品）

  2. 各章节内容映射：

  | 目标市场 | MRD/BRD 目标市场章节 | 产品定位、目标价格区间 |
  | 目标用户 | Step 1 用户角色 + Step 3 JTBD 角色划分 | 主用户/次用户/决策者/付费者的描述、关键需求、优先级 |
  | 核心场景与 JTBD | Step 3 JTBD 表 + Step 5 主要场景 | 每条 JTBD 含：场景描述、JTBD 语句、当前方案、失败点、产品机会 |

  - [ ] 产品定义文档全部章节已填写，无 TBD/TODO/"待定"/"后续补充"等占位符

  - [ ] 定位语使用了完整的五要素公式
  - [ ] "不做清单"在 charter 和产品范围章节中都出现，内容一致
  - [ ] 成功指标覆盖用户价值、商业价值、质量、交付、售后 5 个维度，每个指标有目标值和验证方式
  - [ ] 输入来源与缺口说明表所有行已填写；"缺失+阻塞=是"的条目有明确处理方式
  - [ ] L1 项目：L1 使用条件检查表全部满足（如有不满足的，应走 L2 标准流程而非强行使用 L1 模板）

## 6. Quality Bar

Reviewer 按以下 checklist 逐项检查，全部通过才算本 Skill 完成：

- [ ] **定位陈述可证伪**：定位语中每个断言（核心价值、差异化）有对应的可验证来源或量化指标；不含"极致""最好""行业标杆"等无法验证的词
- [ ] **JTBD 三维度覆盖**：每个主用户角色有 ≥2 条功能 JTBD + ≥1 条情感 JTBD；消费类硬件的主用户有 ≥1 条社会 JTBD（或有不适用理由）；每条 JTBD 有"当前方案"和"失败点"
- [ ] **MVP 范围有来源**：所有 Must-have 和 Should-have 条目关联 ≥1 条 evidence_id 或 assumption_id；Won't-have 条目有关联的排除理由
- [ ] **不做清单充分**："不做清单"条目数 ≥5 条；每条有排除理由分类（cost/risk/phase/user/strategy）和触发条件；覆盖平台兼容/场景边界/集成边界/服务边界/配件边界至少 3 个领域
- [ ] **场景矩阵有排除列**：主要场景 ≥3 个，次要场景 ≥2 个，明确排除场景 ≥2 个；排除场景标注了"如果用户强行使用会发生什么"
- [ ] **硬件约束量化**：BOM 成本目标有具体数字并拆解到 ≥4 个器件组；关键器件 ≥3 个且标注供应风险和备选方案；强制性认证有标准号和预计周期
- [ ] **成功指标可测量**：每个成功指标有目标值（数字/百分比/时间范围）和验证方式；覆盖用户价值/商业价值/质量/交付/售后 ≥3 个维度
- [ ] **输入来源表完整**：Section 0 所有行已填写，所有"阻塞=是"的条目有处理方式；无"缺失 + 阻塞=是 + 未处理"的组合
- [ ] **无占位符**：文档中无 TBD/TODO/"待定"/"后续补充"/"暂不考虑"等占位符；不确定的内容标注为假设（assumption_id）并给出 confidence 和 validation_method
- [ ] **无定位与范围冲突**：产品定位陈述（如"极致性价比"）与 MVP 范围（如包含高成本旗舰功能）和硬件约束（如 BOM 目标高于竞品）之间没有矛盾
- [ ] **Charter 一页纸**：产品定义结论章节不超过一页（打印预览），包含产品名称/定位/目标用户/核心场景/核心价值/核心功能/不做清单/成功指标 8 个要素

## 8. Best Practices

### 好的输出 vs 差的输出

**好的产品定位陈述：**

> 对于首次购买智能家居设备、担心安装复杂的租房年轻用户，CapsuleCam 是一款 Wi-Fi 智能门铃，能够在不破坏墙面、不需要布线的条件下提供门外访客的视频监控和双向通话。不同于 Ring Video Doorbell（需要螺丝固定安装、且全部功能需付费订阅），CapsuleCam 的核心优势是通过 3M 无痕胶贴安装（3 分钟完成，退租时可无损移除）和本地 AI 人形检测（无需订阅即可区分快递员和路人）。

**差的产品定位陈述：**

> 这是一款智能门铃，主打极致体验和超高性价比，重新定义智能家居入门体验。

问题：无目标用户、无参照品类、无具体差异化、无可验证的断言——全是营销空话。PRD 无法从这个定位中提取任何功能优先级信号。

---

**好的 JTBD（功能+情感+社会三维）：**

> 主用户 — 功能任务：当我在公司开会无法接听门铃时，我想在手机上看到门外是谁并直接通话，以便不遗漏重要的快递和访客。
>
> 主用户 — 情感任务：当我听到门铃声但不确定外面是谁时（尤其是夜间），我想感到安全和有掌控感，而不是焦虑和犹豫要不要开门。
>
> 主用户 — 社会任务：当朋友来家里看到我的门铃时，我希望他们认为我是一个懂得利用科技提升生活质量、但不是乱花钱买没用 gadget 的人。

**差的 JTBD（只有功能，没有情感和社会）：**

> 用户想用手机看门外 → 所以需要视频门铃。

问题：没有情境、没有情感动机、没有社会驱动因素。产品定义失去了选择功能优先级的情感和社会锚点。

---

**好的"不做清单"：**

> - 不提供 7×24 小时云存储录像回放 → 排除理由：cost（云存储成本与 BOM 成本目标冲突，且目标用户（租房年轻用户）的价格敏感度不支持订阅模式）。触发条件：如竞品提供免费 24h 云存储成为行业标配后重新评估。影响范围：需要长期录像归档的用户（非主用户）。
> - 不支持 5GHz Wi-Fi → 排除理由：phase（本版优先保证 2.4GHz 的覆盖和稳定性，5GHz 留给后续版本）。触发条件：2.4GHz 干扰成为用户投诉 Top 3 问题后启动。影响范围：居住在高密度公寓且路由器不支持 2.4GHz 频段管理的用户（需在购买前明确告知）。
> - 不提供 HomeKit 集成 → 排除理由：user（目标用户以 Android 为主，iOS 用户占比 < 投标 MRD 假设的 20%）。触发条件：用户调研确认 iOS 用户占比 > 30% 且 HomeKit 是购买决策因素。影响范围：iOS 用户无法用 Home app 控制门铃（可通过 APP 独立使用）。

**差的"不做清单"：**

> - 暂不支持高级功能 → 后续考虑
> - 部分配件可能不含 → 待定

问题：没有具体内容、没有排除理由、没有触发条件、没有影响范围。PRD 阶段无法判断什么算"高级功能"、什么配件"可能不含"——等于没有边界。

---

**好的"场景排除"：**

> 场景：户外大门口，无遮挡，暴雨天气下使用
> 排除理由分类：user（目标用户租房场景下产品安装在室内门或公寓楼道内，不在完全露天环境中使用）
> 如果用户强行使用：IPX4 防护等级不足以应对暴雨直接冲刷，可能导致进水损坏。产品不保修因进水导致的故障。

**差的"场景排除"：**

> 场景：极端天气
> 排除：不推荐在极端天气使用

问题：没有定义什么是"极端天气"、没有说明为什么不推荐、没有说如果用了会发生什么。不构成有效边界。

---

### 常见陷阱

| 陷阱 | 表现 | 正确做法 |
|------|------|----------|
| 定位写成功能列表 | 定位陈述罗列功能（"支持蓝牙、Wi-Fi、Zigbee 三种协议"）而非用户价值 | 定位描述用户获得的结果，不是产品有什么功能。功能是实现手段，不是定位。 |
| JTBD 写成需求 | JTBD 写成"设备应该支持远程查看"或"需要视频监控功能" | JTBD 格式为"当...我想...以便..."。描述用户的任务和动机，不写技术方案或功能列表。 |
| 边界只写不做，不写理由 | "不做清单"每条只写"不做 XX 功能"，没有理由分类和触发条件 | 每条"不做"必须有排除理由分类 + 触发条件 + 影响范围——如果连为什么不做都说不清，说明没有认真思考过边界。 |
| 场景排除列空白 | 场景矩阵只有主要和次要场景，排除列写"暂无"——实际上每个产品都有不应覆盖的场景 | 每个产品至少能找到 2 个明确不应覆盖的场景（如室内产品不做户外、个人产品不做企业场景、消费产品不做工业场景）。找不到说明对产品边界思考不足。 |
| 硬件约束"待定" | BOM 目标写"待 PRD 阶段确定"、认证写"待合规团队确认"、器件写"由硬件团队选型" | 产品定义阶段的硬件约束不需要精确到具体型号，但必须有目标值（BOM≤$XX）、有边界（认证标准号）、有风险标注（供应风险高中低）。"待定"等于把不确定性传递到 PRD 阶段。 |
| 成功指标不可测量 | 成功指标写成"用户满意度高""市场反响好""产品质量可靠" | 每个指标必须有目标值（数字/百分比/时间）和验证方式。问自己：一年后我怎么判断这个指标是否达到了？如果无法回答，这个指标就不合格。 |
| Charter 变成 PRD 草稿 | 产品定义结论（Charter）写得过长，开始描述功能细节、交互逻辑、技术方案 | Charter 是一页纸的战略摘要：谁、什么场景、什么价值、做什么不做什么、怎么算成功。功能细节留给 PRD。 |
| 忽略跨模块一致性 | 定位说"极致性价比"但 BOM 目标高于所有竞品；JTBD 说"不想感到焦虑"但场景排除中没有夜间独处场景 | 定位、JTBD、范围、硬件约束、场景矩阵之间必须自洽。写完产品定义后做一次跨模块一致性检查——每一对相关章节之间不能有逻辑矛盾。 |
