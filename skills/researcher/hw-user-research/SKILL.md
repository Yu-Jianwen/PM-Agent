# 智能硬件用户研究与VOC分析

## 1. Purpose（目的）

本 Skill 解决智能硬件产品定义中"用户真正需要什么"的问题。它承接市场研究中识别的候选用户人群和场景假设，通过多角色链分析和 VOC（Voice of Customer）数据收集，将模糊的用户假设转化为可验证的用户洞察，输出到产品规划报告（hw-product-strategy）、MRD/BRD（hw-mrd-brd）、产品定义（hw-product-definition）和 PRD（hw-prd）。

在 3-Agent 工作流中，本 Skill 位于研究阶段的第二条并行线（与 hw-competitive-analysis 并行，均依赖 hw-market-study 完成），输出经 Reviewer（hw-review）审查后进入 Gate 3。

**核心命题**：智能硬件的用户不是一个人，而是一条角色链。安装工、日常使用者、购买决策者、付费者、维护者可能完全不同的人，各自有不同的 JTBD 和痛点。将"用户"压缩为单一人格是智能硬件产品失败的首要原因。

## 2. Context（上下文/适用场景）

### 触发条件
- Gate 1 已批准，路由判定（L1/L2/L3）已确认
- hw-market-study 已完成并通过 Gate 2 审查，已产出候选用户人群和 VOC 线索
- 项目需要用户洞察来驱动产品定义（所有 L1/L2/L3 路由都需要）

### 前置条件
- 项目启动卡已就绪（含项目代号 `{project}`）
- 市场研究报告 `output/{project}/market_study_report.md` 已存在，包含：
  - 候选用户人群描述（至少 1 个 segment）
  - 核心场景假设（至少 2 个）
  - 待验证问题（VOC 线索）
- `registers/evidence.csv` 和 `registers/assumptions.csv` 已初始化（含表头）

### 下游消费者
| 下游 Skill | 消费内容 |
|-----------|---------|
| hw-product-strategy | 用户角色链、核心 JTBD、Top 5 痛点、需求机会优先级 |
| hw-mrd-brd | 目标用户画像验证结论、用户旅程关键机会 |
| hw-product-definition | JTBD 输入、需求机会排序 |
| hw-prd | 用户场景、痛点优先级、验证问题 |
| hw-review | 完整报告 + evidence.csv 记录（用于 evidence 维度审查） |

### 不适用范围
- 不做竞品用户体验对标（那是 hw-competitive-analysis 的工作）
- 不做技术可行性评估（那是开发团队的工作）
- 不做 FTO 法律判断（那是法务的工作）
- 不做市场规模的最终测算（那是 hw-market-study 的工作）

## 3. Operating Principles（操作原则）

### Principle 1: 角色分离是强制的
智能硬件存在角色链分离：安装者、日常使用者、购买决策者、付费者、维护者、风险承担者可能完全不同的人。**绝对禁止**将这些角色合并为单一的"用户"概念。

- **反面行为**：报告只描述一个"目标用户"，将安装体验、使用体验、购买决策混为一谈。
- **违反后果**：产品定义遗漏关键角色的需求 → Reviewer 以 `scope` 类 blocker 退回。

### Principle 2: 每条用户声明必须有 direct quote
VOC 分析中的每一条用户痛点、需求、偏好声明，必须附带至少一条用户原话（direct quote），不能是 Agent 的转述或概括。源说了什么 ≠ 我们推断这意味着什么，两者必须分离。

- **反面行为**：报告写"用户觉得安装太复杂"，但没有引述任何用户的真实原话。
- **违反后果**：声明降级为 assumption，不能作为 evidence 写入 evidence.csv。

### Principle 3: 痛点优先级 = 频次 × 严重度 × 替代方案稀缺度
痛点优先级排序必须使用三维乘法模型，不能凭直觉排序。三个维度分别是：该痛点出现的频率、对用户体验的影响严重程度、用户当前可用的替代方案/变通方法的数量。

- **反面行为**：按"感觉最重要"排序痛点，缺乏频次数据或严重度依据。
- **违反后果**：优先级排序不可验证 → Reviewer 以 `evidence` 类 finding 标记。

### Principle 4: VOC 渠道缺失必须显式声明
不是所有 VOC 渠道都可达。电商评论、社媒讨论、售后工单、安装工反馈、客服录音等渠道中，实际可获取的必须声明样本量和偏差风险；不可获取的必须标注为"数据缺口"并说明对结论的影响。

- **反面行为**：只收集了电商评论就声称"用户研究完整"，不声明缺失的售后工单和安装工反馈渠道。
- **违反后果**：研究覆盖度不足 → Gate 3 审批时有条件通过，要求补充缺失渠道。

### Principle 5: JTBD 必须区分功能/情感/社会三层
每个角色的每个核心场景，必须分析三层 JTBD：功能性任务（要完成什么）、情感性任务（想感受什么）、社会性任务（想被他人怎么看）。只分析功能性任务会导致产品缺乏差异化洞察。

- **反面行为**：JTBD 只有"当……我想……以便……"的功能性描述，完全没有情感和社会维度。
- **违反后果**：产品定义缺乏情感和社会洞察 → PM 在 hw-product-definition 中无法建立差异化定位。

### Principle 6: 不确定性默认标记为 assumption
无法找到用户原话支撑的判断、基于少量样本的推测、从其他品类类推的结论——这些都不是 evidence，必须标记为 assumption 并写入 assumptions.csv，附带 confidence（高/中/低）和 validation_method。

- **反面行为**：基于 5 条京东评论推断"用户普遍认为……"，并以事实语气写入报告正文。
- **违反后果**：假证据污染 evidence.csv → 确定性校验 V-06 不通过 → Gate blocked。

## 4. Instructions（分步骤指引）

Think Step by Step。每步有明确的输入、操作和检查点。

---

### Step 1: 加载用户 Segments 和市场研究上下文

**输入**：
- `output/{project}/market_study_report.md` — 市场研究报告全文
- `registers/evidence.csv` — 查找市场研究中与用户相关的 evidence 记录
- 项目启动卡 — 获取项目代号 `{project}`、产品品类、目标市场

**操作**：
1. 读取市场研究报告，提取以下关键信息：
   - 候选用户人群（segments）：每个 segment 的人口学特征、场景假设、待验证问题
   - VOC 线索：市场研究中已发现的用户反馈方向（如"电商评论中多次提到安装困难"）
   - 目标市场的地理范围（全国/一线城市/海外等）——这决定 VOC 收集的语言和平台范围
2. 从 evidence.csv 中筛选 `related_doc` 为市场研究报告且与用户相关的记录
3. 将每个候选 segment 拆解为角色链：使用者、决策者、付费者、安装/维护者、风险承担者
4. 为每个角色标注初始假设（来自市场研究）和待验证问题清单

**检查点**：
- [ ] 至少识别出 1 个用户 segment（L1）或 ≥2 个（L2/L3）
- [ ] 每个 segment 至少拆解出 3 个角色（使用者、决策者、付费者），L2/L3 需包含安装/维护者
- [ ] 每个角色有 ≥1 条待验证假设
- [ ] 角色链中不存在被完全忽略的角色（如所有 segment 都没有拆出维护者 → 标记为 assumption 说明原因）

---

### Step 2: 收集 VOC 数据（按 Segment × 角色 × 渠道）

**输入**：
- Step 1 的角色链和待验证问题清单
- 每个角色的 VOC 渠道线索（从市场研究报告提取）

**操作**：
1. 为每个 segment × 角色组合确定 VOC 数据收集渠道：

   | 渠道 | 适用角色 | 搜索方式 | 证据等级上限 |
   |------|---------|---------|------------|
   | 电商评论（京东/天猫/亚马逊） | 付费者、使用者 | 按产品品类搜索 review 区，提取差评和中评中的原话 | B（品牌旗舰店）/ C（第三方店铺） |
   | 社交媒体（小红书/抖音/微博/Reddit） | 使用者、决策者 | 搜索"{品类}+体验""{品类}+后悔""{品类}+安装"等关键词 | C（需交叉验证） |
   | 问答平台（知乎/百度知道/Quora） | 决策者 | 搜索"{品类}+怎么选""{品类}+哪个牌子好""{品类}+值得买吗" | C（需交叉验证） |
   | 售后/维修论坛（什么值得买/贴吧/专业论坛） | 维护者、使用者 | 搜索"{品类}+坏了""{品类}+维修""{品类}+故障" | C |
   | 安装工反馈（58同城/鲁班到家/万师傅评价） | 安装者 | 搜索"{品类}+安装""{品类}+安装费""{品类}+安装难度" | C（需交叉验证） |
   | 行业媒体测评（Zealer/爱范儿/科技美学/digitimes） | 决策者 | 搜索"{品类}+评测""{品类}+体验报告" | B（知名媒体）/ C（自媒体） |
   | 客服/售后数据（如可获取） | 所有角色 | 搜索"{品类}+投诉""{品类}+退货" | B（如有真实工单数据） |
   | 线下渠道反馈（如可获取） | 付费者、决策者 | 搜索"{品类}+实体店体验""{品类}+卖场" | C |

2. 按渠道执行 VOC 收集：
   - 使用 `agent-reach` skill 搜索中文平台内容
   - 使用 `WebSearch` 作为降级方案（当 agent-reach 平台不支持时）
   - 对每个搜索结果页，使用 `WebFetch` 深度提取用户原话
3. 每条用户原话记录以下元数据：
   - 来源平台 + 链接
   - 发布时间
   - 说话人角色（如果能推断）
   - 原话全文（不是概括）
   - 初步解释（这条原话暗示什么需求/痛点）
4. 按 segment × 角色对原话进行分组

**检查点**：
- [ ] 每个 segment 至少收集到 3 个渠道的 VOC 数据
- [ ] 每个角色的原话总数 ≥ 10 条（L1）/ ≥ 20 条（L2）/ ≥ 30 条（L3）
- [ ] 不可获取的渠道已在报告中显式声明为"数据缺口"，并说明原因和对结论的影响
- [ ] 每条原话有完整的 source_grade（A/B/C/D）标记
- [ ] 每条原话记录已准备写入 evidence.csv（本步骤结束时流式写入）

---

### Step 3: JTBD 分析（按角色 × 场景）

**输入**：
- Step 2 收集的用户原话（按 segment × 角色分组）
- 市场研究报告中的场景假设

**操作**：
1. 对每个角色的每个核心场景，提炼三层 JTBD：

   | JTBD 层级 | 定义 | 提炼方法 | 格式 |
   |----------|------|---------|------|
   | **功能性** | 用户要完成什么具体任务 | 从用户原话中提取动作动词 + 目标对象 | 当[场景]，我想要[动作]，以便[功能性结果] |
   | **情感性** | 用户想感受什么 | 从用户原话中提取情绪词 + 想避免的情绪 | 当[场景]，我想要感受到[正面情绪]，避免[负面情绪] |
   | **社会性** | 用户想被他人怎么看待 | 从社交平台的炫耀/吐槽/求助内容中提取 | 当[场景]，我想要被他人认为[社会形象] |

2. 跨角色识别 JTBD 冲突：
   - 安装者要的是"安装快"（少花时间），付费者要的是"安装好"（不损坏墙面/布线美观）
   - 使用者要的是"功能多"，维护者要的是"故障少"
   - 标注这些冲突为 tradeoff——这是产品定义的关键输入

3. 将 JTBD 按场景分组，每个场景标注涉及的角色和证据编号

4. 对于每个 JTBD，识别"当前阻碍"——用户现在用什么替代方案来完成这个任务？替代方案的质量如何？

**检查点**：
- [ ] 每个角色至少提炼 3 个功能性 JTBD
- [ ] 每个 segment 至少提炼 2 个情感性 JTBD 和 1 个社会性 JTBD
- [ ] 至少识别 1 处跨角色 JTBD 冲突（如未发现，解释可能原因并标记为 assumption）
- [ ] 每个 JTBD 有 ≥1 条 evidence 支撑
- [ ] JTBD 陈述使用了"当……我想要……以便……"格式，不是松散的需求描述

---

### Step 4: 用户旅程映射

**输入**：
- Step 2 的用户原话（按场景和时间线）
- Step 3 的 JTBD
- 智能硬件标准旅程阶段

**操作**：
1. 使用智能硬件标准旅程阶段模板（12 个阶段），对每个 segment 逐阶段填写：

   | 阶段 | 定义 | 关键问题 |
   |------|------|---------|
   | **认知** | 用户如何发现产品品类/意识到需求 | 需求触发点是什么？信息渠道是什么？ |
   | **比较** | 用户如何比较不同产品/品牌 | 比较维度是什么？决策标准是什么？谁参与决策？ |
   | **购买** | 用户如何完成购买 | 购买渠道？决策周期多长？付费者与决策者是否同一人？ |
   | **到货** | 用户收到产品的体验 | 包装体验？开箱体验？配件完整性？ |
   | **安装** | 产品安装/部署过程 | 谁来安装？安装时长？是否需要专业人员？是否需要工具？ |
   | **配网** | 智能硬件连接网络/APP | 配网成功率？APP 下载引导？账号注册流程？ |
   | **首次使用** | 用户第一次使用核心功能 | 学习成本？是否有引导？首次体验是否达到预期？ |
   | **日常使用** | 用户的日常高频使用场景 | 使用频率？核心功能是否好用？自动化/联动是否工作？ |
   | **异常处理** | 设备故障/异常时的用户行为 | 故障率？用户如何诊断？自助解决 vs 求助客服？ |
   | **维护** | 设备日常维护和保养 | 维护频率？维护难度？耗材更换？ |
   | **售后** | 用户遇到问题后的售后体验 | 客服响应速度？退换货流程？维修周期？ |
   | **复购/推荐** | 用户是否会再次购买或推荐 | NPS？复购率？推荐理由？劝阻理由？ |

2. 对每个阶段填写：
   - 用户目标：用户在这个阶段想达成什么
   - 用户动作：用户具体做了什么
   - 接触点：用户与产品/品牌的交互界面（APP、包装、客服、说明书等）
   - 痛点：用户原话中反映的负面体验
   - 情绪：正向/中性/负向（附用户原话佐证）
   - 机会点：这个阶段有什么可改进的空间
   - 证据编号：支撑此阶段分析的 evidence ID

3. 标注"情绪最低点"——旅程中用户情绪最负面的阶段。这通常是产品的最大风险点。

4. 标注"啊哈时刻"——旅程中用户从"一般"变为"惊喜"的转折点。如果无法找到，说明产品可能缺乏差异化。

**检查点**：
- [ ] 12 个阶段全部覆盖（L1 可合并"配网"到"安装"、"异常处理"到"售后"，但需显式说明）
- [ ] 每个阶段至少有 1 条来自用户原话的 evidence
- [ ] 情绪最低点已识别并标注
- [ ] 如"啊哈时刻"不存在，已显式声明并标记为 risk

---

### Step 5: 痛点优先级矩阵

**输入**：
- Step 2 的用户原话
- Step 4 的用户旅程（每个阶段的痛点）
- Step 3 的跨角色冲突

**操作**：
1. 汇总所有阶段、所有角色的痛点，合并语义相同但表述不同的痛点（语义去重）
2. 对每个痛点进行三维评分：

   | 维度 | 评分标准 | 取值 |
   |------|---------|------|
   | **频次（F）** | 在 VOC 数据中被提及的频率 | 5=几乎所有用户都提到；4=多数用户提到；3=约半数用户提到；2=少数用户提到；1=极个别用户提到 |
   | **严重度（S）** | 对用户体验的影响程度 | 5=导致用户放弃使用/退货/差评；4=严重影响核心体验；3=明显不便但不阻断使用；2=轻微不便；1=几乎无影响 |
   | **替代方案稀缺度（A）** | 用户当前有多少可行的变通方法 | 5=完全无替代方案；4=有但代价很高；3=有部分变通方案；2=有较成熟的变通方案；1=已有完善的替代方案 |

3. 计算优先级分：**Priority Score = F × S × A**
   - P0（Blocker）：Score ≥ 80 — 必须解决，否则产品不可用
   - P1（Critical）：Score 50-79 — 核心体验，MVP 必须包含
   - P2（Important）：Score 25-49 — 有则显著提升体验
   - P3（Nice-to-have）：Score < 25 — 锦上添花

4. 对于 P0/P1 痛点，标注当前替代方案和对应的机会（可转化为产品需求）

5. 标注跨角色冲突的痛点——一个角色的需求可能是另一个角色的痛点来源

**检查点**：
- [ ] 至少识别 10 个独立痛点（L1）/ 15 个（L2）/ 20 个（L3）
- [ ] 每个痛点的 F/S/A 评分有 evidence 支撑（引用用户原话中的频次和严重度证据）
- [ ] P0 痛点不遗漏（Reviewer 将对 P0 遗漏做对抗性验证）
- [ ] 跨角色冲突痛点已显式标注

### Step 6: 生成研究报告并写入台账

**输入**：
- Step 1-5 的所有输出
- `templates/10_用户研究与VOC分析报告.md` — 输出模板结构

**操作**：
1. 将 Step 2 中收集的每条用户原话写入 evidence.csv（流式写入——发现即写入，不等报告完成）：

   | 字段 | 填写规则 |

   | `evidence_id` | `EV-{project}-{seq}`，自增序号从 001 开始，不与已有记录冲突 |
   | `title` | 简短概括（≤30字），如"京东用户反馈安装费过高" |
   | `source_type` | 用户评论/社媒内容/测评视频/售后记录/安装记录/访谈记录 |
   | `source_name` | 平台名 + 用户名/作者（如"京东评论区-用户王**"） |
   | `url_or_path` | 原始链接（如有） |
   | `date_collected` | YYYY-MM-DD |
   | `source_grade` | A/B/C/D（按证据分级体系） |
   | `direct_quote` | 用户原话全文（不是概括或改写） |
   | `importance` | central/supporting/tangential |
   | `related_doc` | `user_research_report` |
   | `related_section` | 报告中的章节号（如"5. VOC主题编码""7. 用户旅程"） |
   | `summary` | 一句话概括这条证据对研究的贡献（≤50字） |
   | `confidence` | 高/中/低 |
   | `notes` | 方法论备注、偏差风险、与其他证据的关联 |

2. 将无法找到原话支撑但基于推理的判断写入 assumptions.csv（流式写入）：

   | 字段 | 填写规则 |
   |------|---------|
   | `assumption_id` | `A-{project}-{seq}` |
   | `assumption` | 完整假设陈述 |
   | `category` | 用户 |
   | `related_doc` | `user_research_report` |
   | `impact` | 高/中/低（如果假设错误对产品决策的影响程度） |
   | `confidence` | 高/中/低（假设本身成立的可能性） |
   | `validation_method` | 访谈/问卷/试用/数据验证/样机测试 — 具体方案（不能为空） |
   | `owner` | Researcher |
   | `status` | open |
   | `notes` | 为什么无法找到 evidence、预计何时可验证 |

3. 按 Output Structure（第 5 节）的完整模板撰写报告

4. 报告完成后执行自检：
   - 摘要字数统计（≤500字）
   - evidence_id 引用一致性（报告中引用的 evidence_id 在 evidence.csv 中真实存在）
   - 输入来源表完整性（每个输入项的状态不是"未处理"）
   - 与市场研究报告的一致性（角色链是否与候选人群对齐）

**检查点**：
- [ ] evidence.csv 新增记录数 ≥ segment 数 × 角色数 × 3（每个角色至少 3 条核心 evidence）
- [ ] assumptions.csv 新增记录中，所有 `confidence=高` 的记录都有 `validation_method`
- [ ] 报告 10 个主章节全部填充（第 1-10 节 + 输入来源表）
- [ ] 摘要字数 ≤ 500 字（中文）
- [ ] 输入来源表中无"缺失"状态且未注明原因和处理方式的条目
- [ ] 报告中的所有 evidence_id 引用均在 evidence.csv 中存在
- [ ] 报告中的 evidence_id 和 assumption_id 使用 `{project}` 占位符替换为实际项目代号

## 6. Quality Bar（最低质量标准）

每次产出提交 Reviewer 或 Gate 前，Researcher 必须逐项自检：

- [ ] **摘要 ≤ 500 字**：中文摘要字数不超过 500 字，包含全部 4 项（路由影响发现、产品定义约束、开放问题、什么新证据会改变结论）
- [ ] **每条核心声明有 direct quote**：报告中标注 `central` 重要性的声明，每条都有至少一条来自用户的 direct quote（不是 Agent 改写或概括）
- [ ] **角色链完整**：每个 segment 的角色链至少覆盖使用者、决策者、付费者三个角色（L2/L3 还需安装者、维护者）。未覆盖的角色已在数据缺口中显式声明
- [ ] **JTBD 三层覆盖**：每个 segment 至少有功能性、情感性、社会性三层 JTBD。缺失层级已标记为 assumption 并写入 assumptions.csv
- [ ] **痛点优先级可复现**：每个痛点的 F/S/A 评分有可追溯的 evidence 依据。Reviewer 能根据 evidence 复现评分逻辑
- [ ] **VOC 渠道覆盖**：至少 3 个不同渠道的 VOC 数据（L1）/ 4 个（L2）/ 5 个（L3）。缺失渠道已声明为数据缺口
- [ ] **输入来源表完整**：表中每个输入项的状态为"已采集""部分缺失"或"缺失"，无"未处理"状态。所有"缺失"条目有原因说明
- [ ] **evidence.csv 写入完整**：报告中引用的所有 evidence_id 在 evidence.csv 中存在，且 direct_quote 字段非空、source_grade 非空
- [ ] **assumptions 标记完整**：所有 confidence=高的 assumption 都有 validation_method。无空 validation_method 的 high-confidence assumption
- [ ] **无占位符**：报告全文无 TBD、TODO、"待补充"、"根据实际情况调整"等占位符。所有章节已填充
- [ ] **跨角色冲突已识别**：报告中至少有一处跨角色需求冲突的分析。如确实未发现冲突，已解释原因并标记为 assumption
- [ ] **ID 引用一致性**：报告中的 evidence_id 和 assumption_id 格式正确（`EV-{project}-{seq}` / `A-{project}-{seq}`），且引用的 ID 在对应 CSV 文件中存在

## 7. Tool Integration（工具链）

### 7.1 主工具

| 工具 | 用途 | 使用场景 |
|------|------|---------|
| `agent-reach` | 中文平台 VOC 搜索 | 小红书、微博、B站、知乎等中文社交/内容平台的用户讨论搜索。**首选工具** |
| `WebFetch` | 单页面深度提取 | 电商评论区页面、具体论坛帖子、测评文章。获取完整用户原话 |
| `WebSearch` | 搜索引擎补充 | 当 agent-reach 不支持的平台，或需要跨平台综合搜索时使用 |

### 7.2 降级链

```
agent-reach（首选）
  ↓ 平台不支持或服务不可用
WebSearch + WebFetch 组合（降级）
  ↓ 搜索结果质量不足
标记为"搜索失败" → 写入数据缺口声明 → 提交假设（assumptions.csv）
```

### 7.3 质量门禁

| 门禁 | 阈值 | 不通过时的处理 |
|------|------|--------------|
| 单渠道 VOC 原话数量 | ≥ 5 条 distinct 原话才算一个有效渠道 | 少于 5 条的渠道降级为"线索"而非"证据来源"，在输入来源表中标注"部分缺失" |
| 用户原话可追溯性 | 每条原话可追溯到具体 URL 或平台+用户名 | 无法追溯的原话不写入 evidence.csv，降级为方向性信号 |
| evidence 写入门槛 | direct_quote 非空 + source_grade 非空 + date_collected 非空 | 三个字段任一为空 → 不写入 evidence.csv，保留在报告中标注为"待补充" |

## 8. Best Practices（最佳实践）

### 8.1 好的输出 vs 差的输出

#### 好的 VOC 主题分析

```markdown
| VOC 主题 | 典型原话 | 频次 | 产品启示 |
|---------|---------|------|---------|
| 安装费不透明 | "上门安装收了300，之前根本没说过要这么多"（京东-用户张**） | 京东 47 条 + 天猫 23 条 + 小红书 31 条 = 101 条 | 产品设计考虑免安装或一口价安装方案 |
```

特征：有具体原话、有平台分布、有计数依据、产品启示与 evidence 直接关联。

#### 差的 VOC 主题分析

```markdown
| VOC 主题 | 说明 |
|---------|------|
| 安装困难 | 很多用户反映安装不方便 |
```

特征：无原话、无计数、模糊概括、从"安装困难"无法推导任何产品决策。

#### 好的 JTBD

```markdown
功能性：当每天回家开门后，我想要一键启动全屋智能场景，以便不需要逐个打开 5 个 App 和设备。
情感性：当智能家居设备出故障时，我想要感受到"问题可控"，避免"焦虑和无助"。
社会性：当朋友来访时，我想要被他们认为"懂科技、会生活"，避免被认为"买了智商税"。
```

特征：具体场景 + 具体动作 + 具体情感/社会结果，能从 JTBD 直接推导功能需求。

#### 差的 JTBD

```markdown
用户想要智能家居好用。
```

特征：没有场景、没有动作、没有结果，无法推导任何产品需求。

### 8.2 常见陷阱

| 陷阱 | 为什么会发生 | 如何避免 |
|------|------------|---------|
| **电商评论代表全体用户** | 电商评论有自选择偏差（极端好/极端差才会评论），中间用户沉默 | 多渠道交叉验证。电商评论的频次不代表全体用户中的频次 |
| **把安装者的问题当成使用者的问题** | 将"用户"视为单一人格 | 每条原话标注说话人角色。角色不清的原话标记为"角色未知" |
| **VOC 主题只覆盖负面** | 差评更容易被搜索和关注 | 主动搜索正面体验和"啊哈时刻"。问"用户为什么留下来"而不仅是"用户为什么走" |
| **JTBD 写成功能列表** | 只分析功能性任务，忽略情感和社会维度 | 每条功能性 JTBD 配一条情感 JTBD。从用户原话中提取情绪词 |
| **痛点排序凭感觉** | 没有使用 F×S×A 乘法模型 | 强制对每个痛点打分。打分必须有 evidence 依据，记录在 evidence.csv 中 |
| **样本量不足就下结论** | 急于产出报告 | 样本量不足的结论降级为 hypothesis，写入 assumptions.csv 并标注 confidence=低 |
| **从电商评论推断市场份额** | 混淆销售排名和用户满意度 | 电商评论数据仅反映已购买用户的体验，不代表市场整体 |
| **忽视沉默的大多数** | 只关注发声用户 | 在"数据缺口"中声明哪些用户群体可能未被覆盖（如不写评论的老年用户） |
