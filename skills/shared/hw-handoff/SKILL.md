# hw-handoff — 下游交付交接（按团队拆包）

## 1. Purpose（目的）

本 Skill 解决"开发团队各自需要知道什么、不需要知道什么"的问题。它把 PRD 及其关联的完整产品知识体系拆解为面向具体执行团队的精简交付包——每个团队只需要阅读与自己交付物直接相关的内容，其余部分一律不发送。

在 Agent 工作流中，本 Skill 位于验证计划（hw-validation-plan）之后、开发启动之前。它是 PM 流程的**最后一个产出步骤**，承上启下地连接"产品定义完成"和"工程实现启动"。

本 Skill 不修改任何上游文档或台账。它是纯读取→过滤→分发的过程。

## 2. Context（上下文/适用场景）

### 触发条件

- Gate 7 已批准（PRD + 验证计划审批通过）
- PRD 已冻结：在此之后 PRD 不应再发生需求变更（如有变更，应走正式变更流程，变更后重新生成受影响的团队交付包）
- 开发团队即将启动，需要明确的交付物

### 前置条件

| 条件 | 检查方式 |
|------|---------|
| Gate 7 已批准 | decisions.csv 中存在 `gate=Gate 7, status=approved` 的决策记录 |
| PRD 文档已定稿 | `output/<project>/PRD_产品需求文档.md`（或 L1 合并文档）存在且版本已锁定 |
| requirements.csv 已定稿 | `registers/requirements.csv` 中存在本项目的全部需求记录，所有 P0/P1 需求的 status 为 approved |
| traceability.csv 已定稿 | `registers/traceability.csv` 中存在本项目的全部可追溯性记录 |
| 产品定义文档已批准 | `output/<project>/` 下产品定义文档存在且 Gate 6 已批准 |
| 验证计划已批准 | `output/<project>/` 下验证计划文档存在且 Gate 7 已批准 |

### 输入

| 输入项 | 路径 | 用途 |
|--------|------|------|
| PRD 文档 | `output/<project>/PRD_产品需求文档.md`（L2/L3）或 `output/<project>/12_L1_轻量产品定义_PRD合并文档.md`（L1） | 提取四模块（功能/软件/硬件/结构）的需求细节、规格、约束、验收标准 |
| requirements.csv | `registers/requirements.csv` | 获取完整需求清单，含 requirement_id、priority、owner、acceptance_criteria、related_evidence |
| traceability.csv | `registers/traceability.csv` | 获取需求→证据→验证项的追溯链，用于测试团队和质量团队 |
| 产品定义文档 | `output/<project>/` 下对应文件 | 提取产品定位、目标用户、核心场景、MVP 范围、成功指标，用于 APP 和测试团队 |
| 验证计划 | `output/<project>/` 下对应文件 | 提取验证项、测试方法、判定标准，用于测试团队和质量团队 |
| evidence.csv | `registers/evidence.csv` | 只读引用——在需要为某团队补充证据上下文时回查 |
| risks.csv | `registers/risks.csv` | 提取与本项目相关的风险项及其缓解措施，用于质量和供应链团队 |

### 输出消费者

| 消费者 | 消费内容 | 用途 |
|--------|----------|------|
| 硬件团队 | 硬件 handoff + BOM 约束 + 结构规格 + 认证清单 | 启动硬件设计、器件选型、原理图设计、PCB layout |
| 固件团队 | 固件 handoff + 状态机 + 通信协议 + OTA 策略 | 启动固件架构设计、通信栈开发、设备逻辑开发 |
| APP 团队 | APP handoff + UI/UX 需求 + API 规格 + 用户流程 | 启动移动端/桌面端开发、UI 设计、API 对接 |
| 测试团队 | 测试 handoff + 测试计划 + 验收标准汇总 + 验证项追溯 | 编写测试用例、搭建测试环境、执行验证 |
| 质量团队 | 质量 handoff + 认证清单 + 合规标准 + 质量门禁 | 启动认证申请、准备合规文档、制定质量控制计划 |
| 供应链团队 | 供应链 handoff + BOM 成本目标 + 供应商资质 + MOQ | 启动供应商寻源、报价、备料计划 |
| 售后团队 | 售后 handoff + 安装要求 + 维护流程 + 备件清单 | 编写安装手册、制定售后方案、准备培训材料 |

### 不负责

- 不修改 PRD 或任何上游文档（本 Skill 是只读消费）
- 不判断需求的可行性或合理性（那些问题应在 Gate 7 之前解决）
- 不替代开发团队的架构设计（交付包是需求输入，不是技术方案）
- 不创建新的需求或验证项（只从已有产物中提取和重组）
- 不决定团队间的开发优先级或排期（那是项目管理的工作）

## 3. Operating Principles（操作原则）

### Principle 1: 最小信息原则 — 每个团队只收到自己需要的

每个接收团队只应收到与其交付物直接相关的需求、规格和约束。发送完整 PRD 给所有人是**信息过载**，会导致团队成员在海量无关信息中迷失自己的交付重点。

- **反面行为**：把整份 80 页 PRD 发送给所有 7 个团队，"大家各取所需"。结果：硬件工程师要翻到第 60 页才找到 BOM 表，APP 开发者在功能需求章节中逐条辨别哪些与 APP 相关，测试团队在故事与流程中手动提取验收标准。
- **违反后果**：信息噪声淹没信号。团队可能遗漏关键需求（因为藏在无关章节中），或浪费时间理解不属于自己领域的内容。交付延迟和需求遗漏是直接后果。

### Principle 2: 完整覆盖原则 — 所有 P0 需求至少被一个团队覆盖

每条 P0 优先级的需求必须在至少一个团队的交付包中出现。不允许存在"幽灵需求"——PRD 中有、但没有任何团队知道自己需要为它负责的需求。

- **反面行为**：一条 P0 级别的"设备需支持 FCC Part 15 B 类辐射发射限值"需求，因为 owner 字段填写模糊（同时涉及硬件和固件），两个团队都没在自己的交付包中看到，导致认证阶段才发现天线设计不满足辐射限值。
- **违反后果**：P0 需求无人认领 → 开发阶段遗漏 → 认证/测试阶段才发现 → 返工成本可能是设计阶段的 10-100 倍。这是本 Skill 最严重的失败模式。

### Principle 3: 上下文足量原则 — 只给相关信息，但相关信息要给全

每个团队收到的需求不是孤立的条目清单，而是**有上下文的可用信息包**。一条硬件需求旁边应有相关的硬件规格、选型依据和验收标准，而不是让硬件工程师再回查 PRD 原文。

- **反面行为**：给硬件团队输出一个只有 15 条 requirement_id 的清单，没有任何规格、约束或验收标准。硬件工程师必须逐条回到 PRD 原文查找上下文，手尾工作量等同于自己通读完整 PRD。
- **违反后果**：手尾查找增加遗漏风险。团队可能基于不完整的理解做设计决策。"交付包"形同虚设——团队还是需要读完整 PRD。

### Principle 4: 一致性原则 — 交付包的内容必须与上游产物严格一致

交付包中的每一条信息都必须在 PRD、requirements.csv、traceability.csv 或验证计划中有对应的原始记录。不允许在拆包过程中"优化"措辞、补充信息或重新解释需求——那些变更应该回到 PRD 中并通过 Gate 7 批准。

- **反面行为**：拆包时觉得 PRD 中某条需求写得不够清楚，擅自补充了技术细节再发给硬件团队。硬件团队基于补充后的内容做设计，但固件团队看到的是 PRD 原始版本——两个团队对同一需求的理解不一致。
- **违反后果**：交付包和 PRD 之间的不一致是团队间理解偏差的根源。如果发现 PRD 中描述不清晰，正确做法是标记为"需澄清"并回退到 PRD 修订，而不是在拆包时自行补充。

### Principle 5: 无歧义归属原则 — 每条需求有明确的主责团队

对于涉及多团队的跨领域需求（如"BLE 配网"同时涉及固件和 APP），必须在交付包中明确主责团队和协作团队。不允许两个团队都以为对方负责。

- **反面行为**：一条"设备支持 OTA 固件升级"的需求，涉及固件（升级逻辑）、APP（用户提示和进度显示）、云端（固件包分发），但只在固件团队的交付包中出现，APP 和云端团队不知道 OTA 对他们的影响。
- **违反后果**：跨领域需求因归属不清而遗漏协作方的适配工作。OTA 固件逻辑就绪但 APP 未开发升级界面 → 功能不可用。

## 4. Instructions（分步骤指引）

### Step 1: 验证前置条件与加载全部产物

- **输入**：`registers/decisions.csv`、`output/<project>/` 目录
- **操作**：
  1. 检查 decisions.csv 中是否存在本项目 `gate=Gate 7, status=approved` 的记录。如果不存在，**立即终止本 Skill**，提示用户"PRD 尚未通过 Gate 7 审批，不能执行下游交付交接"。
  2. 确认 PRD 文档、产品定义文档、验证计划文档在 `output/<project>/` 下存在。列出文件清单供审计。
  3. 加载以下全部产物到上下文：
     - PRD 文档（完整内容）
     - 产品定义文档（完整内容）
     - 验证计划文档（完整内容）
     - `registers/requirements.csv` 中 `requirement_id` 匹配本项目前缀的全部行
     - `registers/traceability.csv` 中 `trace_id` 匹配本项目前缀的全部行
     - `registers/evidence.csv`（只读引用）
     - `registers/risks.csv` 中与本项目相关的风险行
  4. 统计需求总数，按 priority 分组（P0/P1/P2/P3），作为后续覆盖验证的基线。
- **检查点**：
  - Gate 7 审批记录存在且 status=approved
  - 所有必需产物文件存在且可读取
  - 需求按 priority 分组统计完成（例：P0=12 条，P1=23 条，P2=15 条，P3=8 条）
  - 若任何产物缺失：终止并报告缺失文件清单

### Step 2: 构建团队映射矩阵

- **输入**：requirements.csv 全部需求行 + PRD 文档四模块结构
- **操作**：
  1. 以 `requirements.csv` 中的 `owner` 字段为**主映射依据**，为每条需求确定主责团队。
  2. 补充**跨领域映射**：对涉及多团队的需求（根据需求描述内容分析），附加协作团队标记。跨领域识别规则：

     | 需求中涉及的关键词 | 可能涉及的团队 |
     |-------------------|---------------|
     | BLE / Wi-Fi / Zigbee / 通信协议 / 射频 | 固件 + 硬件 + 认证（质量） |
     | 配网 / 绑定 / 注册 / 设备发现 | 固件 + APP + 云端 |
     | UI / 界面 / 交互 / 页面 / 通知 | APP |
     | OTA / 固件升级 / 差分升级 / 回滚 | 固件 + APP + 云端 |
     | BOM / 器件 / 芯片 / 传感器 / PCB | 硬件 + 供应链 |
     | 认证 / FCC / CE / CCC / SRRC / 合规 | 硬件 + 质量 |
     | 外壳 / 模具 / 结构 / IP 等级 / 散热 | 硬件 |
     | 安装 / 支架 / 壁挂 / 配件 / 工具 | 硬件 + 售后 |
     | 数据存储 / 隐私 / 加密 / 安全启动 | 固件 + 云端 + 质量 |
     | API / 接口 / MQTT / HTTP / WebSocket | 固件 + APP + 云端 |
     | 成本 / MOQ / 交期 / 供应商 | 供应链 |
     | 测试 / 验证 / 验收 / 用例 | 测试 |
     | 维护 / 保养 / 更换 / 清洁 / 售后 | 售后 |

  3. 建立如下结构的映射矩阵：

     ```
     REQ-{project}-001 → 主责: 固件, 协作: [APP, 云端]
     REQ-{project}-002 → 主责: 硬件, 协作: [供应链]
     REQ-{project}-003 → 主责: APP, 协作: []
     ...
     ```

  4. 标记**无归属需求**：如果某条需求的 owner 字段为空或无法映射到 7 个团队中的任何一个，标记为 "unassigned" 并记录到交付包索引文件的"未分配需求"表中。

- **检查点**：
  - 每一条需求至少有一个主责团队标记
  - "unassigned" 需求已记录并将在索引文件中呈现给 PM
  - 跨领域识别覆盖了通信、认证、升级、安装等常见跨团队场景

### Step 3: 按团队过滤需求并提取上下文

- **输入**：Step 2 的映射矩阵 + 全部产物内容
- **操作**：

  对每个团队（硬件 / 固件 / APP / 测试 / 质量 / 供应链 / 售后），执行以下过滤和提取：

  **3a. 过滤需求子集**：
  - 提取该团队为主责或协作方的全部需求（requirement_id + requirement + priority + acceptance_criteria + related_evidence）
  - 按 priority 降序排列（P0 → P1 → P2 → P3）

  **3b. 提取团队专属上下文**：

  | 团队 | 从 PRD 中提取的内容 | 从其他产物中提取的内容 |
  |------|--------------------|---------------------|
  | **硬件** | Section 硬件模块：核心组件选型、电气规格、BOM 约束、认证要求、环境适应性；Section 结构模块：外观尺寸、结构设计、散热设计、安装与固定、DFM | risks.csv 中的硬件/供应链风险；evidence.csv 中的硬件选型证据 |
  | **固件** | Section 软件模块—固件需求：传感器/执行器逻辑、状态机转换、通信协议、OTA 策略、安全启动；Section 功能需求中与固件相关的内容（设备状态、处理规则）；Section 6 状态与规则表 | risks.csv 中的固件/通信风险 |
  | **APP** | Section 软件模块—APP 需求：设备发现/绑定、设备控制界面、数据展示、告警推送、多设备管理、用户账号；Section 功能需求中与 APP 相关的内容（触发入口、用户可见表现）；Section 4 用户故事与流程 | 产品定义文档中的目标用户和核心场景章节 |
  | **测试** | Section 5 详细需求中所有 P0/P1 需求的验收标准；Section 7 非功能需求的验证方式；Section 8 验收标准汇总表 | 验证计划文档的完整内容；traceability.csv 的全部记录（含 validation_item 字段） |
  | **质量** | Section 硬件模块—认证要求（FCC/CE/SRRC/BQB 等及标准号）；Section 硬件模块—环境适应性指标；Section 7 非功能需求中的安全/可靠性指标 | evidence.csv 中与认证相关的证据；risks.csv 中与质量/认证相关的风险 |
  | **供应链** | Section 硬件模块—BOM 约束（成本目标、关键器件供应商、替代料策略、长交期物料）；Section 结构模块—DFM 约束 | risks.csv 中的供应链风险 |
  | **售后** | Section 功能需求中与安装/维护/售后相关的内容；Section 结构模块—安装与固定、可维护性、包装要求；Section 功能范围表中"安装/售后"行 | 产品定义文档中的目标用户信息（用于理解安装工和维护者的需求） |

  **3c. 提取团队专属验收标准**：
  - 从 requirements.csv 的 `acceptance_criteria` 字段提取该团队涉及的每条需求的验收标准
  - 从 traceability.csv 的 `validation_item` 字段提取验证项（主要给测试团队）

- **检查点**：
  - 每个团队的需求子集非空（如果某团队需求数为 0，确认该团队确实不涉及本项目——如纯固件升级项目可能没有硬件团队的任务）
  - 每个团队提取的上下文至少覆盖 3 类内容（需求清单 + 专属规格/约束 + 验收标准）
  - 未出现"某条需求同时出现在全部 7 个团队中"的过度分发（那是无差别的完整 PRD 分发）

### Step 4: 生成每个团队的交付包文档

- **输入**：Step 3 中每个团队过滤后的需求子集和上下文
- **操作**：

  为每个团队在 `output/<project>/handoff/` 下独立生成一个 markdown 文件。文件名约定为团队英文名：`hardware.md`、`firmware.md`、`app.md`、`test.md`、`quality.md`、`supply-chain.md`、`after-sales.md`。

  每个文件按本 Skill 第 5 节"输出结构"中对应团队的模板逐项写入。写入顺序：
  1. 文档头部（项目名称、团队名称、交付日期、上游产物版本）
  2. 该团队的需求清单表（含 requirement_id、需求描述、priority、验收标准）
  3. 该团队的专属规格与约束
  4. 该团队的验收标准汇总
  5. 跨团队依赖说明（该团队的交付物被哪些团队依赖，以及该团队依赖哪些团队的交付物）
  6. 附录：该团队可忽略的内容范围（明确告知团队哪些 PRD 章节与他们无关，防止 FOMO 驱动他们去读完整 PRD）

- **检查点**：
  - 7 个团队文件全部生成（即使某个团队需求数为 0，也要生成文件并说明"本项目不涉及该团队的交付物"）
  - 每个文件不包含其他团队的专属内容（如硬件交付包中不出现 APP UI 需求）
  - 每个文件的"跨团队依赖"章节非空——至少标注了上下游依赖关系
  - 每个文件有明确的日期和版本号

### Step 5: 生成主索引文件

- **输入**：Step 4 的 7 个团队交付包
- **操作**：

  生成 `output/<project>/handoff/INDEX.md`，内容按本 Skill 第 5 节"主索引文件结构"模板填写，包含：
  1. 项目信息摘要
  2. 交付包文件清单与接收团队
  3. 需求覆盖矩阵（哪些需求分发给了哪些团队）
  4. P0 需求覆盖验证结果
  5. 跨团队依赖关系图
  6. 未分配需求清单（如有）
  7. 上游产物版本快照

- **检查点**：
  - INDEX.md 中 7 个交付包的链接全部有效（指向 `output/<project>/handoff/` 下的实际文件）
  - 需求覆盖矩阵中的行数等于 requirements.csv 中本项目的需求总数
  - P0 需求覆盖率达到 100%（每条 P0 需求至少在 cover 矩阵中被 1 个团队覆盖）

### Step 6: 验证 P0 需求全覆盖

- **输入**：requirements.csv 的 P0 需求清单 + Step 5 的需求覆盖矩阵
- **操作**：
  1. 提取 requirements.csv 中所有 priority=P0 的 requirement_id
  2. 逐一检查每条 P0 需求是否在至少一个团队的交付包中被引用
  3. 对于未被任何团队覆盖的 P0 需求：
     - 回溯到 PRD 原文确认该需求的责任归属
     - 如果归属明确：将该需求补充到对应团队的交付包中
     - 如果归属模糊：在 INDEX.md 的"未分配需求"表中标注，并标注为"需 PM 决策归属"
  4. 统计覆盖率：P0 覆盖数 / P0 总数 × 100%

- **检查点**：
  - P0 需求覆盖率 = 100%
  - 如果 < 100%：INDEX.md 中明确记录了未覆盖的 P0 需求的 ID、描述、归属模糊原因、建议负责团队
  - 所有"需 PM 决策归属"的需求在 INDEX.md 中附带了上下文，PM 可以不做额外调查即做出归属判断

### Step 7: 呈现交付摘要并提交最终确认

- **输入**：完整的交付包集合 + INDEX.md
- **操作**：
  1. 向用户呈现交付摘要（格式见下文"交付摘要呈现"）
  2. 列出关键数字：总需求数、P0 覆盖数/率、各团队需求数、未分配需求数
  3. 对任何异常情况发出告警（如某团队需求数为 0、存在未分配 P0 需求、跨团队依赖存在循环等）
  4. 等待用户确认后方可视为本 Skill 完成

  交付摘要呈现格式：

## 6. Quality Bar（最低质量标准）

交付包在提交给各团队之前必须通过以下全部检查项。任何未通过的检查项都是交付阻碍。

- [ ] **P0 需求 100% 覆盖**：requirements.csv 中所有 priority=P0 的需求，在需求覆盖矩阵（INDEX.md）中至少被 1 个团队覆盖。覆盖率 = 100%。低于 100% 不得交付，必须补充分配或升级给 PM 做归属决策。
- [ ] **7 个团队交付文件全部生成**：`output/<project>/handoff/` 下存在 hardware.md、firmware.md、app.md、test.md、quality.md、supply-chain.md、after-sales.md 共 7 个文件。即使某团队不涉及本项目（需求数为 0），也必须生成文件并说明原因。缺失任一文件则交付不完整。
- [ ] **交付内容与上游产物一致**：每条出现在交付包中的需求描述、验收标准必须与 requirements.csv 和 PRD 原文逐字一致（或明显的非语义性格式调整如编号前缀）。不允许出现"优化"后的措辞、补充的技术细节或 Agent 自行推断的内容。抽查 5 条跨团队的高优先级需求进行原文比对，0 条不一致。
- [ ] **无跨团队信息泄漏**：每个团队的交付包中不包含其他团队的专属内容。检查方式：hardware.md 中不出现"用户故事""UI 界面""APP 交互"等 APP 专属词汇；app.md 中不出现"BOM 成本""PCB layout""器件选型"等硬件专属词汇；firmware.md 中不出现"供应商资质""MOQ""交期"等供应链专属词汇。抽查每个团队文件，0 条泄漏。
- [ ] **每个交付包 ≥ 5 个实质章节**：每个团队的 markdown 文件中，除去"你可以忽略的内容"章节外，至少有 5 个独立章节（如需求清单、规格/约束、验收标准、跨团队依赖、相关风险等）。仅有"需求清单"一个章节的交付包不满足质量标准——团队无法仅凭需求 ID 清单开展工作。
- [ ] **跨团队依赖无循环**：INDEX.md 中的跨团队依赖关系图中不存在循环依赖（A 依赖 B 且 B 依赖 A 且两者的交付有时间先后要求）。如果确实存在双向信息依赖（设计阶段 A 需要 B 的输入，但 B 也需要 A 的部分规格），必须在依赖描述中注明打破循环的方式（如先出草案、后期对齐）。
- [ ] **上游版本快照完整**：INDEX.md 的"上游产物版本快照"表完整填写了 PRD、产品定义、验证计划、requirements.csv、traceability.csv 的版本号和批准日期。任何一项缺失都会导致未来无法追溯"交付包是基于哪个版本的产物生成的"。

### 好的交付包 vs 差的交付包

**好的硬件交付包（节选）**：

```
| 待机功耗 | ≤50μA | — | 3.3V 供电, 25°C | 同上 |
| 工作功耗 | ≤300mW (峰值) | — | Wi-Fi 连续发送模式 | 同上 |
```

**差的硬件交付包**：

```
硬件需要满足功耗要求，具体见 PRD。
```

**好的"可以忽略的内容"章节**：
```

以下 PRD 章节与硬件团队无关，不需要阅读：
- Section 4 用户故事与流程（由 APP 和固件团队负责）
- Section 5 详细需求中标注 owner ≠ 硬件且无硬件协作标记的条目
- Section 3 功能范围表中"固件""APP""云端""后台"行
```

**差的"可以忽略的内容"章节**：
```
（没有这个章节，或者写"见 PRD 原文"）
```
问题：团队不知道自己可以跳过什么，FOMO 驱动下会去读完整 PRD，交付包的价值归零。

**好的跨团队依赖描述**：
```
### 你依赖以下团队的输出

| 被依赖方 | 依赖内容 | 获取时间要求 |
|---------|---------|------------|
| 硬件团队 | 引脚定义（GPIO 分配表）、通信接口规格（UART 波特率/SPI 模式）、功耗参数（各模式下的电流值） | 固件开发启动前 |

```

**差的跨团队依赖描述**：
```
需要硬件团队和 APP 团队的配合。
```
问题：没有明确依赖什么信息、何时需要。团队不知道找谁要什么。

### 常见陷阱

1. **把"拆包"当"删减"**：交付包不是 PRD 的删减版，而是 PRD 的重组视图。好的交付包让团队读完后不需要再碰 PRD；坏的交付包只是把 PRD 中"看起来不相关"的章节删掉，团队还是要回查原文。

2. **跨团队需求只发给一个团队**：OTA 升级涉及固件、APP、云端三个团队。如果把 OTA 需求只放在固件交付包中，APP 和云端团队不知道他们也需要为 OTA 做适配。正确做法：每条跨领域需求的主责团队收到完整需求描述，协作团队收到"你需要在 X 方面配合"的子集。

3. **验收标准遗漏**：交付包中列出需求但未附带验收标准。团队知道要做什么但不知道做到什么程度算完成。每一条出现在交付包中的需求必须附带其验收标准。

4. **过度依赖"见 PRD 原文"引用**：在交付包中大量写"详见 PRD Section X"。如果团队需要多次回查原文，交付包就失去了"一站式信息包"的价值。正确做法：将相关信息**直接嵌入**交付包，只在必要时标注来源章节供审计溯源。

5. **忽略"不涉及"团队**：如果一个团队在本项目中确实没有交付物（如纯固件升级不需要硬件团队），必须生成文件并明确说明"本项目不涉及硬件团队的交付物，原因：{说明}"。不生成文件会导致团队不知道自己是否被遗漏了。

6. **交付包之间信息不一致**：固件交付包中写的 BLE 配网超时是 30s，APP 交付包中写的是 45s，PRD 原文是 30s。问题出在拆包时 APP 团队的内容被"优化"过。所有数字和约束必须与 PRD 原文逐字一致。
