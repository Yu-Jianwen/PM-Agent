# hw-retro — 项目复盘与方法沉淀

## 1. Purpose（目的）

本 Skill 解决"这个项目教会了我们什么、如何让下一个项目更好"的问题。它是 3-Agent 系统中唯一横跨 Researcher、PM、Reviewer 三个角色的共享技能 —— 复盘的对象不是某一个 Agent 的产出，而是整个方法论体系的运行效果。

在 Agent 工作流中，hw-retro 位于收尾阶段。项目完成（或重大阶段结束）后触发，输入验证计划的执行结果、各阶段 Gate 评审记录、上市后的市场和用户反馈、售后数据，输出两个产物：

1. **项目复盘报告**（人类阅读）：总结 what went well / what went wrong / what surprised us / what would we do differently
2. **method_learnings.csv 写入**（机器消费，主输出）：将项目中发现的、可复用的方法改进沉淀为结构化记录，驱动跨项目的方法论进化

**method_learnings.csv 是 PRIMARY 输出。** 复盘报告解决的是"这个项目发生了什么"，CSV 解决的是"下一个项目应该怎么做"。报告不写入下一项目的 Agent 上下文，CSV 会。

## 2. Context（上下文/适用场景）

### 触发条件

- 项目完成后（所有 Gate 通过、产品进入量产或交付）
- 重大阶段结束后（如 EVT/DVT/PVT 阶段门、Gate 审批阶段性完成）
- 上市后复盘（产品上市 N 个月，有市场反馈和售后数据）
- 项目中止或路由降级后（决策复盘，方法为何失效）

### 前置条件

| 条件 | 检查方式 |
|------|---------|
| 验证计划结果可读 | `output/{project}/验证计划.md` 或验证结果文档存在 |
| Gate 审批记录可读 | 各 Gate 的审批记录（通过/退回/有条件通过）已归档 |
| 产品定义与 PRD 可读 | 原始判断可回溯 |
| 市场反馈（如适用） | 上市后的用户评价、售后工单、销售数据、竞品动态 |
| `registers/method_learnings.csv` 已初始化 | 至少包含 header 行 |
| 相关台账可读 | evidence.csv, assumptions.csv, risks.csv, requirements.csv, traceability.csv, decisions.csv |

### 输出消费者

| 消费者 | 用途 |
|--------|------|
| hw-intake（PM） | 读取 method_learnings.csv 中与项目路由和流程裁剪相关的规则，指导新项目路由判定 |
| hw-product-strategy（PM） | 读取 method_learnings.csv 中与市场判断和假设验证相关的经验 |
| hw-prd（PM） | 读取 method_learnings.csv 中与需求定义和模板改进相关的建议 |
| hw-market-study（Researcher） | 读取 method_learnings.csv 中与研究方法和证据收集相关的改进 |
| hw-review（Reviewer） | 读取 method_learnings.csv 中与质量检查和审查标准相关的更新 |
| 人工 PM | 阅读复盘报告，批准 method_learnings.csv 中建议的模板变更和流程调整 |
| 组织知识库 | method_learnings.csv 作为跨项目的方法资产，持续积累 |

### 与增量复盘的关系

在 AGENTS.md 中定义了两类复盘时机：
- **阶段结束时增量写入**：每个研究阶段（如市场研究完成、竞品研究完成）结束时，如发现可复用的方法经验，可以增量写入 method_learnings.csv。此时使用本 Skill 的轻量模式（仅 Step 5 和 Step 7，不生成完整复盘报告）。
- **项目完成后完整复盘**：触发本 Skill 的完整流程，生成完整的项目复盘报告 + method_learnings.csv 写入。

## 3. Operating Principles（操作原则）

### 原则 1：可复用优先（Reusability Over Narrative）

method_learnings.csv 中只写入"能被下一个项目复用"的方法经验。一次性项目事实（如"XX 供应商交期延迟 2 周"）留在复盘报告里，不进入 CSV。可复用经验（如"关键器件必须提前 8 周锁定供应商，不能在 PRD 阶段才确认"）才进入 CSV。

- **反面行为**：把复盘报告中的每一条问题都翻译成 method_learnings 记录，导致 CSV 充斥"XX 项目芯片选型晚了"等无法迁移的一次性事实。或在 learning 字段写"这次做得不好"而不给出可操作的规则。
- **违反后果**：method_learnings.csv 被噪音淹没，下游 Agent 读取时无法提取有效规则，跨项目学习机制失效。Reviewer 在检查 method_learnings 质量时标记低价值记录。

### 原则 2：证据驱动的复盘（Evidence-Backed Retro）

复盘中的每一条"what went wrong"和"what surprised us"必须有对应的原始判断（来自 MRD/BRD/产品定义/PRD/验证计划/evidence.csv）和实际结果作为对照。不能凭记忆或印象下结论。

- **反面行为**：写"市场判断偏乐观"但不回顾当初 MRD 中的市场规模假设和 evidence.csv 中的具体证据。写"用户体验不好"但不引用用户研究中的具体发现和上市后的用户评价。
- **违反后果**：复盘变成意见交换而非事实核对，无法区分"方法错了"还是"执行偏了"。导致的 method_learnings 可能纠正一个不存在的方法问题，或忽略真正的系统缺陷。

### 原则 3：区分偏差类型（Classify Before Prescribe）

在提出改进建议之前，必须先判断偏差的根因类型：证据不足（信息不够）、方法错误（分析框架有缺陷）、执行偏差（方法对但没做到）、外部变化（不可控的环境因素）、决策变化（主动选择了不同方向）。不同类型对应不同的改进动作。

- **反面行为**：把所有问题归因为"研究不够深入"，统一开"下次多研究"的药方。或把外部环境变化（如政策突变）当作方法错误来修正。
- **违反后果**：改进方向错误 —— 证据不足需要补信息源，方法错误需要改分析框架，执行偏差需要改流程和检查点。错配改进类型导致重复犯错。

### 原则 4：CSV 是方法资产的唯一真相源（CSV as Single Source of Truth for Methods）

复盘报告中对方法改进的描述必须与 method_learnings.csv 中的对应记录一致。如果报告中说"建议在 PRD 模板中增加认证时间线字段"，CSV 中必须有对应的记录且 recommended_template_change 字段具体描述改动内容。冲突时以 CSV 为准。

- **反面行为**：复盘报告中写了 5 条方法改进建议，但只挑了 2 条写入 CSV。或报告中的建议和 CSV 中的记录表述不一致。
- **违反后果**：下游 Agent 只读 CSV，报告中的方法建议不会被消费。报告和 CSV 脱节导致方法资产不可信。

### 原则 5：区分"停止做"和"改变做"（Stop vs Change）

"What went wrong"的分析必须区分两类：应该完全停止的行为（stop doing）和方向对但方法需要调整的行为（change how）。前者写入 method_learnings 作为裁剪规则（learning_type: 裁剪规则），后者作为方法修正（learning_type: 方法修正）。

- **反面行为**：所有的负面发现都写成"下次注意"，不区分是应该砍掉的流程还是应该改进的方法。
- **违反后果**：流程只增不减，每次复盘都加检查项，体系越来越臃肿。L1 项目被过度流程压垮。

## 4. Instructions（分步骤指引）

### Step 1：加载项目上下文与全量台账

- **输入**：读取以下文件：
  - `output/{project}/` 下所有输出文档（产品规划报告、MRD/BRD、产品定义、PRD、验证计划等）
  - `registers/evidence.csv`（筛选 source_project = {project} 或 related_doc 关联本项目）
  - `registers/assumptions.csv`（筛选与本项目相关的记录）
  - `registers/risks.csv`（筛选与本项目相关的记录）
  - `registers/requirements.csv`（筛选 requirement_id 匹配本项目前缀）
  - `registers/traceability.csv`（筛选 trace_id 匹配本项目前缀）
  - `registers/decisions.csv`（筛选与本项目相关的决策记录）
  - 各 Gate 审批记录（通过/退回/有条件通过）
  - `registers/method_learnings.csv`（读取现有记录，避免重复写入）
- **操作**：
  1. 确定项目名称（用于构造 ML-{project}-{seq} ID 前缀）
  2. 确定复盘范围：全项目复盘 / 阶段复盘（标注复盘阶段）
  3. 提取项目路由等级（L1/L2/L3），复盘深度据此调整
  4. 收集验证计划执行结果：哪些验证项通过/失败/未完成，失败原因
  5. 收集市场反馈（如适用）：上市后用户评价、售后工单、销售数据
  6. 确定输出路径：`output/{project}/11_项目复盘与方法沉淀记录.md`
- **检查点**：
  - 项目名称已确定，可用于构造 ML ID
  - 至少识别出 3 个 Gate 的审批记录
  - 验证结果（通过/失败/未完成）的覆盖率 ≥ 计划验证项的 80%（缺失的显式声明）
  - 市场反馈数据（如项目已上市）至少覆盖 2 个渠道

### Step 2：回看原始关键判断

- **输入**：Step 1 收集的 MRD/BRD、产品定义、PRD、验证计划
- **操作**：
  1. 从上述文档中提取"当时认为是对的"关键判断：
     - 市场判断（TAM/SAM/SOM、增长率、竞品格局）→ 来源 MRD/市场研究报告
     - 用户判断（目标用户、核心场景、痛点强度）→ 来源用户研究报告
     - 产品判断（功能范围、技术路线、BOM 目标、认证计划）→ 来源产品定义/PRD
     - 商业判断（定价、渠道、毛利率、销量预测）→ 来源 BRD
     - 风险判断（top risks、应对策略）→ 来源 risks.csv
  2. 每个判断标注来源文档和对应的 evidence_id 或 assumption_id
  3. 不要在此步骤做评价，只做"当时我们相信什么"的事实提取
  4. 将提取结果填入复盘报告第 2 节（原始判断回看）模板
- **检查点**：
  - 至少提取 5 个关键原始判断，覆盖市场/用户/产品/商业/风险中 ≥3 个维度
  - 每个判断有明确的来源文档引用（章节或 evidence_id/assumption_id）
  - L1 项目至少 3 个判断，L2 至少 5 个，L3 至少 8 个

### Step 3：对照实际结果，识别偏差

- **输入**：Step 2 的原始判断清单 + 验证结果 + 市场反馈 + 售后数据
- **操作**：
  1. 对每个原始判断，对照实际结果，判定：正确 / 部分正确 / 错误
  2. **正确** → 进入"what went well"分析
  3. **部分正确 / 错误** → 深入分析偏差方向和幅度
  4. 特别关注以下信号：
     - 验证计划中"失败"或"未完成"的验证项
     - Gate 审批中"退回"的 Gate 和退回原因
     - 上市后用户评价与产品定义中用户假设的矛盾
     - 售后数据中的高频问题类型
     - 实际 BOM 成本 vs 目标 BOM 成本
     - 实际认证周期 vs 计划认证周期
     - 实际上市时间 vs 计划上市时间
  5. 将结果填入复盘报告第 2 节（原始判断回看）和第 3 节（验证结果复盘）
- **检查点**：
  - 所有 Step 2 中提取的判断都有实际结果对照（无"待确认"状态滞留）
  - 验证计划中所有"失败"项都有偏差说明
  - 至少识别 3 个"部分正确"或"错误"的判断作为深入分析对象

### Step 4：分析 what went well（值得保持的做法）

- **输入**：Step 3 中判定为"正确"的判断 + 各 Gate 一次通过的记录
- **操作**：
  1. 列出本项目中被验证为正确的关键判断和方法实践
  2. 分析为什么它们有效：
     - 是证据充分？（引用 evidence.csv 中高质量源的贡献）
     - 是方法正确？（如五看中的某个分析框架特别有效）
     - 是执行到位？（如 Reviewer 的 3-Lens 验证确实发现了隐藏矛盾）
     - 是前置条件匹配？（如 L1 裁剪规则正好适配项目特征）
  3. 判断哪些可以推广：
     - 可以固化为"下次继续做"的规则 → 进入 method_learnings（learning_type: 方法修正 / 检查项）
     - 可以推广到其他路由等级 → 标注 applies_to
     - 仅适用于特定类型项目 → 标注适用范围和不适用场景
  4. 将分析填入复盘报告第 5 节（方法沉淀），同时为每条可推广经验准备 method_learnings 记录
- **检查点**：
  - 至少列出 3 个"值得保持"的实践
  - 每个实践有成功的证据（引用了实际结果或验证数据）
  - 可推广的经验已准备对应的 method_learnings 草案（learning_type 已确定）

### Step 5：分析 what went wrong 和 what surprised us

- **输入**：Step 3 中判定为"部分正确"或"错误"的判断 + 意外发现
- **操作**：
  1. **What went wrong（应停止或改变的做法）**：
     - 列出方法或判断中出问题的地方
     - 对每个问题，从以下 4 个维度分析根因：
       - 证据不足：当时有没有足够的信息做判断？如果有，为什么没找到？
       - 方法错误：使用的分析框架是否本身有缺陷？
       - 执行偏差：方法对但执行不到位（如应该做 3-Lens 但跳过了）
       - 外部变化：不可控的环境变化（政策、供应链、竞品动态）
     - 判定可预防性（高/中/低）
     - 区分"应该停止做"和"应该改变做"
  2. **What surprised us（错误的假设）**：
     - 列出"当时所有人都相信、但被实际结果推翻"的判断
     - 分析为什么会产生这个盲点：
       - 是不是某个证据被忽略了？
       - 是不是某个假设的 confidence 标高了？
       - 是不是团队有集体认知偏差？
     - 每个 surprise 标注对应的原始 assumption_id（如果有）
     - 提出如何在下个项目中更早发现此类盲点
  3. 将分析填入复盘报告第 4 节（偏差原因分析）和第 5 节（方法沉淀）
  4. 为每条可复用的教训准备 method_learnings 草案
- **检查点**：
  - 每个 wrong 项都有明确的偏差类型标注（证据不足/方法错误/执行偏差/外部变化/决策变化）
  - 每个 wrong 项都有可预防性判定和对应改进动作
  - 至少识别 1 个"surprise"（如果确实没有，需显式声明"本项目中未发现推翻团队共识的意外"）
  - 每条进入 method_learnings 的教训已确定 learning_type

### Step 6：提取方法改进建议

- **输入**：Steps 4-5 的所有分析结果
- **操作**：
  1. 将所有可复用的经验和教训分类为 4 种 learning_type：
     - **方法修正**：现有方法正确但需要微调（如"用户研究中 N=30 不够，改为 N=50"）
     - **模板字段**：模板中缺少某个字段导致信息丢失（如"PRD 模板缺少认证时间线字段"）
     - **裁剪规则**：流程应该针对某些场景增或减（如"L1 路由可跳过波特五力分析"）
     - **检查项**：Reviewer 检查清单需要增加或删除某个项（如"增加 BOM 替代料检查"）
  2. 对每个建议，明确：
     - 适用场景（`applies_to`）：什么路由级别、什么产品类型、什么阶段
     - 不适用场景（`not_applicable_to`）：什么情况下这个规则不适用
     - 建议的模板变更（`recommended_template_change`）：具体改哪个模板、增加/修改/删除什么字段
  3. 区分建议优先级：
     - P0：不采纳会导致下个项目重复犯同类错误
     - P1：采纳后显著提升效率或质量
     - P2：锦上添花的改进
  4. 将分析填入复盘报告第 6 节（模板与流程改进建议）
- **检查点**：
  - 每条建议有明确的 learning_type、applies_to、not_applicable_to
  - recommended_template_change 字段具体到模板文件名和字段名（不是"改进模板"这种模糊描述）
  - P0 建议已确认 owner（负责推动落地的人）
  - 至少 1 条建议涉及模板字段或检查项的增删改

### Step 7：写入 method_learnings.csv（PRIMARY 输出）

- **输入**：Steps 4-6 中准备的 method_learnings 草案
- **操作**：
  1. 为每条可复用的方法经验分配 learning_id：`ML-{project}-{seq}`，seq 从 001 递增
  2. 对每条记录，按 method_learnings.csv 的 11 个字段逐一填充：

     | 字段 | 说明 | 写入规则 |
     |------|------|---------|
     | `learning_id` | `ML-{project}-{seq}` | seq 从 001 递增，不跳跃 |
     | `source_project` | 来源项目名称 | 使用 hw-intake 中确定的项目名 |
     | `source_stage` | 发现此经验的阶段 | 如"市场研究""PRD 编写""EVT""上市后复盘" |
     | `learning_type` | 方法修正 / 模板字段 / 裁剪规则 / 检查项 | 四选一，不能为空 |
     | `learning` | 具体的可操作方法经验（≤150字） | 必须是可操作的规则，不是描述性语句 |
     | `applies_to` | 适用场景 | 如"L2/L3 硬件产品""所有路由等级""涉及射频认证的项目" |
     | `not_applicable_to` | 不适用场景 | 如"L1 轻量项目""纯软件产品""无认证要求的项目" |
     | `recommended_template_change` | 建议的模板变更 | 具体到模板文件名和字段名，无建议则填"无" |
     | `owner` | 负责人 | 推动落地的具体角色，如"PM""Researcher""Reviewer" |
     | `status` | 状态 | 新建记录统一填"待处理" |
     | `notes` | 补充说明 | 可选，空间用于记录关联的复盘报告章节或额外上下文 |

  3. **learning 字段的编写标准**：
     - 必须是可操作的规则，包含"在 X 情况下，做 Y"的动作描述
     - 好的 learning：`在 L2/L3 项目中，PRD 编写阶段必须对 P0 器件标注至少 1 个备选供应商，避免供应链单一依赖`
     - 差的 learning：`供应链风险需要注意`（模糊，不可操作）
     - 差的 learning：`XX 项目芯片选型晚了导致延误`（一次性事实，不可复用）
  4. 使用 `echo` 或 Python csv 模块追加写入，每条记录一行
  5. 写入前检查：`learning_id` 不与现有记录重复
- **检查点**：
  - 每条记录 11 个字段全部填充（`notes` 可为空）
  - learning_type 仅为 4 个允许值之一
  - learning 字段 ≤150 字且包含可操作的动作描述
  - learning_id 无重复
  - 至少写入 2 条记录

### Step 8：生成项目复盘报告

- **输入**：Steps 1-6 的所有分析产物
- **操作**：
  1. 按第 5 节"Output Structure"中的完整报告模板组织内容
  2. **第 2 节（原始判断回看）**：填入 Step 2 的原始判断和 Step 3 的偏差判定
  3. **第 3 节（验证结果复盘）**：填入验证计划的执行结果
  4. **第 4 节（偏差原因分析）**：填入 Step 5 的根因分析
  5. **第 5 节（方法沉淀）**：填入 Steps 4-5 中值得复用的经验和教训
  6. **第 6 节（模板与流程改进建议）**：填入 Step 6 的改进建议，每项标注优先级和负责人
  7. **第 7 节（下一项目复用提醒）**：基于全部分析，提炼下次同类项目的注意事项
  8. 确保报告中所有方法沉淀的条目与 method_learnings.csv 中的记录一一对应
  9. 填写第 1 节（项目基本信息）
- **检查点**：
  - 报告 7 个主章节全部存在，无空章节
  - 第 5 节中的方法沉淀条目与 method_learnings.csv 中的记录数量一致
  - 第 6 节中的每项建议有优先级（P0/P1/P2）和负责人
  - 第 7 节至少包含 3 条具体提醒（不是"注意质量"等模糊说法）
  - 报告中的方法改进描述与 CSV 中的 learning 字段语义一致

### Step 9：执行复盘质量自检

- **输入**：完成的复盘报告 + method_learnings.csv 新增记录
- **操作**：
  1. **完整性检查**：报告 7 章全部非空；method_learnings 记录 11 字段完整
  2. **一致性检查**：报告中"方法沉淀"的条目数 = method_learnings.csv 中本次新增的记录数；报告中引用的 learning_id 在 CSV 中存在
  3. **可操作性检查**：method_learnings.csv 中每条记录的 learning 字段包含"在 X 情况下，做 Y"的动作描述；不包含一次性项目事实
  4. **覆盖度检查**：what went well / what went wrong / what surprised us 三个维度都有分析（如果某一维度为空，需在报告中显式说明原因）
  5. **重复检查**：扫描 method_learnings.csv 中现有的记录，本次新增的 learning 描述不与已有记录实质重复（语义相同的合并为一条）
  6. **优先级检查**：所有 P0 建议已确认 owner
- **检查点**：
  - 全量检查通过
  - 无占位符（"TBD"/"TODO"/"根据实际情况调整"）
  - 报告和 CSV 无矛盾

## 8. Best Practices（最佳实践）

### 好 vs 差的输出对比

#### method_learnings.csv 写入

| 维度 | 好的输出 | 差的输出 |
|------|---------|---------|
| learning | `在 L2/L3 硬件项目中，市场研究阶段必须对核心器件（MCU/传感器/无线模块）做供应风险评估，至少覆盖 2 类器件并标注替代来源` | `供应链很重要，下次要注意` |
| recommended_template_change | `01_产品市场与机会研究报告.md 4.1.3 节"核心器件供应风险评估"表增加"实际供货周期（周）"列` | `改进模板` |
| applies_to | `L2/L3 硬件产品，涉及 MCU/传感器/无线模块的项目` | `所有项目` |
| not_applicable_to | `L1 纯配置变更、纯软件产品、无核心器件的项目` | （空） |

#### 复盘报告写作

| 维度 | 好的输出 | 差的输出 |
|------|---------|---------|
| 偏差分析 | `PRD 中 BOM 目标成本 85 元，实际 EVT 样机 BOM 成本 112 元。偏差类型：证据不足。根因：市场研究阶段未获取关键器件供应商报价（仅使用了 1688 零售价估算），零售价与批量价偏差约 30%` | `BOM 成本超预算了，下次算准一点` |
| What Surprised Us | `我们假设 Wi-Fi 模组可以无缝替换为国产替代品（A-CWLS-005，confidence: 高），实际国产模组的射频性能在 2.4G 拥堵环境下丢包率是进口模组的 3 倍，导致 EVT 阶段重新选型` | `国产模组效果不好` |
| 下项目提醒 | `下次同类产品立项时，必须在市场研究阶段获取至少 2 家供应商的正式报价（非零售价），并标注报价有效期和 MOQ` | `注意供应链成本` |

### 常见陷阱

1. **把一次性事实当方法沉淀**：`XX 供应商交期延迟 2 周` 是一次性事实，不是方法。方法应该是 `关键器件必须在 PRD 阶段确认至少 2 家合格供应商的实际交期（非口头承诺），交期超过 8 周的器件必须标注为高风险并启动备选方案`。

2. **归因过于笼统**：所有问题都归因为"沟通不够""研究不深""时间太紧"。必须追溯到具体的证据缺失、方法缺陷或执行偏差。

3. **复盘没有 surprise**：如果每次复盘都没有"我们错了"的发现，说明复盘深度不够。即使是成功的项目，也应该能找到至少一个被推翻的假设。

4. **method_learnings 只写负面教训**：正面的"what went well"也可以沉淀为方法修正或检查项。"这个方法被验证有效，固化为下次必须执行的步骤"同样是高价值的方法沉淀。

5. **applies_to 和 not_applicable_to 留空**：不标注适用范围的方法沉淀等于没有沉淀，因为下游 Agent 不知道这个规则什么时候适用。

6. **忽略"应该停止做什么"**：复盘容易只加不减。如果某个流程步骤在所有项目中都被跳过或没有产生价值，应该在 method_learnings 中写入裁剪规则（learning_type: 裁剪规则），明确在什么场景下可以跳过。

7. **复盘报告和 CSV 脱节**：写完复盘报告后挑几条写入 CSV，导致报告中的方法建议和 CSV 中的记录不一致。正确做法是 CSF 驱动报告 —— 先确定哪些经验值得写入 CSV，再在报告中引用这些记录。

8. **阶段复盘不写 method_learnings**：AGENTS.md 规定"每研究阶段结束时增量写入"。即使项目没完成，研究/规划阶段中发现的方法改进也应该立即沉淀，否则可能遗忘。
