# hw-red-team — 红队对抗性测试

## 1. Purpose（目的）

本 Skill 实现 Reviewer Agent 的第二个核心职责：**红队对抗性测试，回答"什么会让这个产品死掉？"**。

在 3-Agent 协作系统中的位置：

```
PM 产出 PRD + 产品定义 → hw-review 审查文档质量 → 修正通过
                                                    → hw-red-team 红队测试 → 杀伤性假设 + 验证方案
                                                    → hw-validation-plan 纳入验证项
                                                    → Gate 7 审批
```

本 Skill 的输出直接输入到 hw-validation-plan —— 红队识别的杀伤性假设的验证方案应被纳入产品的验证计划中。

### 与 hw-review 的分工

| 维度 | hw-review | hw-red-team |
|------|-----------|-------------|
| **核心问题** | "做得对吗？" | "什么会让它死掉？" |
| **方法论** | 3-Lens 对抗性验证（回溯：证据是否支撑声明） | 预-mortem（前瞻：假设错了产品会怎样） |
| **审查对象** | 文档质量（证据、结构、一致性） | 产品假设（市场、技术、用户、竞争、执行） |
| **输出** | findings（需要修正的问题） | 杀伤性假设 + 最便宜验证方案 |
| **决策权** | 可以拒绝文档（blocker → rejected） | 不做决策，只呈现 |
| **触发时机** | 每个 Researcher/PM draft 产出时 | PRD + 产品定义 ready（阶段末端，一次性） |

**hw-red-team 不是第二遍审查。** hw-review 已经检查了文档的正确性。hw-red-team 假设文档是正确的，然后问："即使一切按文档说的那样，产品就一定能成功吗？哪些隐藏的假设如果错了，一切都会崩塌？"

## 2. Context（上下文/适用场景）

### 触发条件

- PRD 已产出并通过 hw-review 审查（verdict = approved 或 conditional 已修正）
- 产品定义文档已产出并通过 hw-review 审查
- assumptions.csv 已填充（Researcher + PM 均已标记假设）
- PM 在 Gate 7 之前显式触发 hw-red-team

### 前置条件

- `registers/assumptions.csv` 可访问，且包含 Researcher 阶段和 PM 阶段标记的所有假设
- `registers/evidence.csv` 可访问（用于核验假设的 evidence 支撑）
- `registers/risks.csv` 可访问（用于区分已知风险和隐含假设）
- PRD 文档可访问（含 requirements.csv + traceability.csv）
- 产品定义文档可访问

### 输出消费者

- PM Agent：将杀伤性假设的验证方案纳入 hw-validation-plan
- 人类 PM：决定哪些验证方案值得投入资源执行
- Gate 7 审批：红队报告作为审批参考材料
- assumptions.csv：新增红队识别的假设记录

### 不适用场景

- 文档质量审查 → 使用 hw-review
- 项目复盘 → 使用 hw-retro
- 仅需确定性校验（Python 脚本）→ 直接运行 validators/scripts/
- 早期阶段（研究阶段或产品规划阶段）→ 红队测试需要完整的产品定义才能有效执行

## 3. Operating Principles（操作原则）

### Principle 1: 预-mortem 优先，数据验证在后

先想象产品死掉了，再倒推原因。不要从现有数据出发"找问题"——这会受锚定效应影响，只看到数据已经暗示的问题。正确的顺序是：想象失败 → 列出可能原因 → 识别假设 → 检查是否有数据支撑这些假设。

- **反面行为**：从 assumptions.csv 中逐条审查置信度，而不是先做预-mortem。这样做会遗漏 assumptions.csv 中没有记录的隐藏假设——那些团队根本没想到要质疑的假设才是最危险的。
- **违反后果**：最致命的假设往往不在台账里（因为团队认为"这还用想？"）。如果只审查已有假设，会错过那些"集体盲点"级别的杀伤性假设。

### Principle 2: 按杀伤力排序，不按置信度排序

一个高置信度但一旦错了产品必死的假设，比一个低置信度但错了也无所谓的假设更重要。排序公式是 **lethality × uncertainty**，不是单纯的 confidence。

- **反面行为**：把"置信度低"的假设自动排在最前面，忽略那些"高置信度但从未被验证过"的假设。很多团队对核心假设"很有信心"仅仅因为从没质疑过它。
- **违反后果**：团队在低影响力的不确定性上花费验证资源，而真正致命的假设因为"大家觉得没问题"而被跳过，直到产品上市后才被市场验证为错误。

### Principle 3: 只呈现，不决策

红队的职责是呈现最可怕的假设和检验方法。**永远不要替 PM 决定"这个假设可以接受"或"这个验证不值得做"。** 决策权完整保留给人类 PM。

- **反面行为**：在报告中写"建议继续"或"该假设风险可接受"，或在杀伤性假设排名中自行排除某些假设因为"验证成本太高"。
- **违反后果**：红队如果替 PM 做风险接受决策，就失去了其存在的意义——红队的价值恰恰在于呈现 PM 可能因乐观偏差而忽略的威胁。红队自己做风险接受决策等于把"独立挑战者"变成了"另一个同意者"。

### Principle 4: 最便宜的验证，不是最完善的验证

为每个杀伤性假设设计的是**刚好足够获得信号的最便宜测试**，而不是最严谨、最全面的验证方案。目标是让 PM 能用最小成本判断"继续"还是"掉头"。

- **反面行为**：设计昂贵的、需要数月执行的验证方案（如"做完整的市场调研"、"建造功能原型进行用户测试"），或退回"需要更多研究"的模糊建议。
- **违反后果**：PM 因为验证成本太高而跳过验证，直接带着未验证的杀伤性假设进入开发——这正是红队测试试图避免的结果。如果验证方案比产品开发还贵，它就不会被执行。

### Principle 5: 区分"隐藏假设"和"已知风险"

已知风险（已在 risks.csv 中登记、有 mitigation 的）不是红队的重点。红队关注的是**尚未被识别为风险的假设**——那些如果错了产品会死，但团队可能没意识到自己在做的假设。

- **反面行为**：把 risks.csv 中已有的风险重新包装成"杀伤性假设"输出。这是重复劳动，不增加价值。
- **违反后果**：红队报告变成 risks.csv 的重新排版，PM 看不到任何新洞察。真正的隐藏假设继续潜伏。

### Principle 6: 每一个杀伤性假设必须有可证伪的验证方案

验证方案必须能产生一个清晰的 yes/no 信号——"假设成立"或"假设不成立"。模糊的验证方案（"进一步研究"、"收集更多数据"）等于没有验证方案。

- **反面行为**：验证方案写"进行用户调研以确认需求强度"，没有说明调研多少人、问什么问题、什么结果算"确认"、什么结果算"推翻"。
- **违反后果**：PM 执行了"验证"但得不到明确结论，浪费了时间资源却没有降低不确定性。模糊的验证方案和没做验证一样危险。

## 4. Instructions（分步骤指引）

### Step 1: 加载产品全貌

- **输入**：
  - PRD 文档（`output/<project>/PRD_产品需求文档.md`）
  - 产品定义文档（`output/<project>/04_产品定义文档.md`）
  - `registers/assumptions.csv`（全部记录）
  - `registers/evidence.csv`（全部记录）
  - `registers/risks.csv`（全部记录）
  - `registers/requirements.csv`（PRD 关联）
  - `registers/traceability.csv`（PRD 关联）

- **操作**：
  1. 读取 PRD，提取产品的核心价值主张、目标用户、关键功能、四模块约束（功能/软件/硬件/结构）
  2. 读取产品定义，提取产品定位、JTBD、MVP 边界、差异化策略、目标定价
  3. 读取 assumptions.csv，理解团队已经意识到的假设及其验证状态
  4. 读取 risks.csv，标记已知风险——这些将在后续步骤中排除，避免重复
  5. 读取 evidence.csv，理解团队判断的证据基础——哪些假设有强证据，哪些没有
  6. 构建"产品成功逻辑链"：从核心假设 → 用户价值 → 商业成功的关键因果链条，显式写下来

- **检查点**：
  - [ ] PRD 和产品定义均已读取，能用自己的语言描述产品核心逻辑
  - [ ] 产品成功逻辑链已显式写出（≥5 个关键因果节点）
  - [ ] 已知假设清单已提取（从 assumptions.csv）
  - [ ] 已知风险清单已提取（从 risks.csv），标记为"不重复"区域
  - [ ] 已加载项目的 project 标识符（用于后续 ID 生成）

### Step 2: 预-mortem — 想象产品失败

- **输入**：Step 1 的产品成功逻辑链 + 产品全貌

- **操作**：
  1. **设定场景**：
     ```
     现在是产品上市后 12-18 个月。
     产品在市场上失败了。不是"表现一般"——是彻底的商业失败。
     销售额远低于预期（不到目标的 20%）。产品正在被考虑退市。
     ```
  2. **生成失败场景**：在此设定下，从以下六个维度各自生成至少 1 个具体失败场景：
     - **市场失败**：目标市场不存在/太小/不愿付费/购买决策链条断裂
     - **用户失败**：用户不理解产品价值/学习成本过高/使用体验差/迁移困难
     - **技术失败**：关键性能指标不可实现/可靠性不达标/供应链断裂/良率过低
     - **竞争失败**：竞品快速跟进/价格战/替代方案出现/渠道被锁死
     - **执行失败**：开发延期/认证未通过/生产爬坡困难/售后体系崩溃
     - **外部冲击**：监管政策变化/标准更新/核心技术被替代/经济环境恶化
  3. 每个失败场景必须具体——包含"发生了什么"和"为什么会发生"。
     - 好的场景："目标用户群（一二线城市年轻租房群体）的实际规模远小于预估，因为该群体中 80% 租住在已配智能锁的品牌公寓中，无自主购买需求。"
     - 差的场景："目标市场规模不够大"——太模糊，无法追溯假设。
  4. 目标产出 8-15 个具体失败场景。

- **检查点**：
  - [ ] ≥8 个失败场景已生成
  - [ ] 六个维度中至少四个有 ≥1 个场景
  - [ ] 每个场景包含具体因果链（不是模糊的"市场不好"）
  - [ ] 场景覆盖了产品成功逻辑链中的关键节点

### Step 3: 从失败场景提取假设

- **输入**：Step 2 的失败场景列表 + Step 1 的已知假设清单

- **操作**：
  1. 对每个失败场景，反向追溯：**哪个/哪些假设如果错了，会导致这个场景发生？**
  2. 从失败场景中提取假设，格式为：**"我们假设 [X] 是成立的。如果 [X] 不成立，产品可能因为 [Y] 而失败。"**
  3. 将提取的假设与 assumptions.csv 中的已知假设进行交叉比对：
     - 假设已在 assumptions.csv 中 → 标记 `source: known`，引用已有的 assumption_id
     - 假设不在 assumptions.csv 中 → 标记 `source: newly_identified`，这是红队的独特贡献
  4. 特别注意提取那些"团队根本没有意识到自己在做的假设"——这类假设藏在以下地方：
     - PRD 中的无条件陈述（"用户需要 X 功能"——假设了用户需要）
     - 产品定义中的对标选择（"对标竞品 A"——假设了竞品 A 的策略是正确的）
     - 隐含的因果关系（"有了 X 功能就能实现 Y 价值"——假设了因果链成立）
     - 时间窗口假设（"我们有 12 个月的时间窗口"——假设了竞品不会提前行动）
     - "行业常识"（"这个品类毛利就是 40%"——假设了成本结构不会变化）

- **检查点**：
  - [ ] 每个失败场景至少提取 1 个对应假设
  - [ ] 假设总数 ≥ 10
  - [ ] 新识别假设（不在 assumptions.csv 中的）≥ 3（红队独立贡献的证明）
  - [ ] 每个假设写明了"如果 X 不成立 → 产品因为 Y 而失败"的因果链
  - [ ] 识别了至少 2 个团队可能未意识到的隐藏假设

### Step 4: 排序 — 杀伤力 × 不确定性

- **输入**：Step 3 的全部假设（已知 + 新识别）

- **操作**：
  1. 对每个假设，进行两维评分：

     **Lethality（杀伤力）**：
     - `critical`：假设不成立 → 产品几乎必然失败（>70% 概率），核心价值主张崩溃
     - `high`：假设不成立 → 产品严重受损（30-70% 概率失败），需要重大 pivot
     - `medium`：假设不成立 → 产品受损但可生存（<30% 概率失败），局部调整即可
     - `low`：假设不成立 → 影响有限，不影响核心价值

     **Uncertainty（不确定性）**：
     - `critical`：完全无证据支撑，或仅有 D 级源/直觉/行业常识
     - `high`：仅有单一 C 级源支撑，或自相矛盾的证据
     - `medium`：有 B 级源支撑但未经独立验证，或有部分矛盾的证据
     - `low`：有 A 级源支撑，或经过实际验证/多个独立源交叉确认

  2. 按杀伤力排序（不是按不确定性排序）：
     1. Lethality=critical + Uncertainty=critical → **KILLER**（第一优先级）
     2. Lethality=critical + Uncertainty=high → **KILLER**（第一优先级）
     3. Lethality=critical + Uncertainty=medium → **HIGH PRIORITY**
     4. Lethality=high + Uncertainty=critical → **HIGH PRIORITY**
     5. Lethality=high + Uncertainty=high → **INVESTIGATE**
     6. Lethality=medium + Uncertainty=critical → **INVESTIGATE**
     7. 其他组合 → **NOT KILLER**（排除出红队报告）

  3. **关键判断**：高杀伤力但低不确定性的假设 **不是** 红队的重点。这些是团队的"安全赌注"——即使错了后果严重，但团队有充分理由相信它们是对的。红队可以提及但不需要设计验证方案。
  4. **已知假设的附加判断**：如果假设已在 assumptions.csv 中且已有 validation_method，评估该验证方法是否足够。如果现有验证方法充分 → 降一级优先级（不需要重复验证）。
  5. 红队报告聚焦的假设数量：**3-7 个**（KILLER + HIGH PRIORITY）。超过 7 个说明排序不够狠——红队的价值在于聚焦，不是穷举。

- **检查点**：
  - [ ] 每个假设都有 Lethality 和 Uncertainty 评分
  - [ ] 评分有简要理由（1-2 句话，引用 evidence 或说明证据缺失）
  - [ ] KILLER 和 HIGH PRIORITY 假设总数在 3-7 之间
  - [ ] NOT KILLER 的假设已明确排除并说明了排除理由
  - [ ] 已知假设的现有验证方法已被评估，重复验证不会浪费资源

### Step 5: 为每个杀伤性假设设计最便宜验证方案

- **输入**：Step 4 排序后的 KILLER + HIGH PRIORITY 假设

- **操作**：
  1. 对每个 KILLER 和 HIGH PRIORITY 假设，设计验证方案。设计原则：
     - **最便宜**：用最少的时间和金钱获得一个 yes/no 信号。目标成本为零或接近零。
     - **可证伪**：必须能产出"假设成立"或"假设不成立"的明确结论。不能产出"需要进一步研究"。
     - **不依赖产品开发**：验证可以在产品开发之前完成。不需要功能原型、不需要代码。
     - **信号足够**：测试结果的信噪比足够支持"继续/掉头"决策。

  2. 验证方案设计模板（每个假设必须填满 5 个字段）：
     - **Validation method**：具体操作步骤。不是"做用户调研"，而是"找 5 个目标用户画像匹配的人，给他们看产品概念描述和价格，问'你现在会付钱预定吗？'"。
     - **Cost estimate**：钱（¥）+ 时间（天）。如果是零成本（如利用现有渠道的搜索、电话访谈），显式说明为什么零成本。
     - **Time estimate**：从开始到获得结论的天数。目标 ≤ 14 天。
     - **Success criterion**：什么结果算"假设通过验证"？必须是可观测、可量化的。
     - **Failure criterion**：什么结果算"假设被推翻"？必须是同样可观测、可量化的。

  3. **验证方法降级链**：优先使用以下方法（从最便宜到最贵）：
     - 公开数据核查（搜索已有数据验证假设，如市场规模、竞品定价）→ ¥0, 0.5-2 天
     - 专家访谈（1-3 个领域专家电话/微信聊 30 分钟）→ ¥0-500, 1-3 天
     - 供应商 RFQ（发 3 封邮件给供应商询价询交期）→ ¥0, 3-7 天
     - Landing page / 广告测试（在社交平台投放最小化广告测转化）→ ¥200-1000, 3-7 天
     - 用户概念测试（5-8 个目标用户的结构化访谈）→ ¥0-2000, 5-10 天
     - 最小化原型测试（纸面原型/数字原型，非功能原型）→ ¥1000-5000, 7-14 天
     - 功能原型测试 → ¥5000+（仅在上述方法都无法获得信号时使用）

  4. 每个验证方案在描述中必须回答三个问题：
     - 这个测试最多会证伪什么？（测试的边界）
     - 什么结果意味着"不确定，需要进一步验证"？（避免假阴性/假阳性）
     - 如果这个测试通过了，下一个最便宜的验证是什么？（为多步验证铺垫）

- **检查点**：
  - [ ] 每个 KILLER 和 HIGH PRIORITY 假设都有验证方案
  - [ ] 每个验证方案包含全部 5 个字段（method, cost, time, success criterion, failure criterion）
  - [ ] 至少 50% 的验证方案成本为 ¥0（公开数据/专家访谈/供应商 RFQ）
  - [ ] 每个验证方案的时间 ≤ 14 天
  - [ ] 每个验证方案能产出 yes/no 信号（success criterion 和 failure criterion 互斥且完备）
  - [ ] 没有一个验证方案是"做更多研究"或"进一步分析"

### Step 6: 输出红队报告 + 写入台账

- **输入**：Step 1-5 的全部产出

- **操作**：
  1. 编写红队报告（完整结构见 Output Structure），保存到 `output/<project>/red_team_report.md`
  2. 对 Step 3 中识别的新假设（source=newly_identified），追加写入 `registers/assumptions.csv`：
     - `assumption_id`: `A-{project}-{next_seq}`（递增序号，不与已有 ID 重复）
     - `assumption`: 假设陈述（"我们假设 X。如果 X 不成立 → Y"）
     - `category`: 市场/用户/技术/供应链/商业/合规 六选一
     - `related_doc`: `output/<project>/red_team_report.md`
     - `impact`: 高/中/低（映射自 Lethality）
     - `confidence`: 高/中/低（映射自 Uncertainty: critical→低, high→低, medium→中, low→高）
     - `validation_method`: 来自 Step 5 的最便宜验证方案（缩写成一行）
     - `owner`: 留空（由人类 PM 指定）
     - `status`: `red_team_identified`（区别于 Researcher/PM 标记的假设）
     - `notes`: 标注"红队预-mortem 识别"，附验证方案的成功/失败标准摘要
  3. 将红队报告路径和新增假设的 assumption_id 列表返回给 PM Agent

- **检查点**：
  - [ ] 红队报告已保存到正确路径
  - [ ] 报告包含所有必需章节（见 Output Structure）
  - [ ] 新假设已追加写入 assumptions.csv，ID 无冲突
  - [ ] 每条新假设的 status 为 `red_team_identified`
  - [ ] 报告中有明确的"红队结论"章节（不做是否继续的决策声明）

## 6. Quality Bar（最低质量标准）

红队报告完成后，Reviewer 自身输出必须满足以下条件：

- [ ] **场景完整性**：失败场景覆盖至少 4 个维度（市场/用户/技术/竞争/执行/外部冲击），总数 ≥ 8 个。单一维度的场景说明预-mortem 不够全面。

- [ ] **假设提取深度**：新识别假设（source=newly_identified）≥ 3 个。如果所有假设都来自 assumptions.csv 已有记录，说明红队没有发现团队的集体盲点——红队未增加独立价值。

- [ ] **排序纪律**：KILLER + HIGH PRIORITY 假设总数在 3-7 之间。少于 3 个可能遗漏了关键假设（预-mortem 不够彻底）；多于 7 个说明排序不够狠，没有做到真正的"聚焦最可怕的"。

- [ ] **验证方案可执行性**：每条验证方案包含完整的 5 个字段（method, cost, time, success criterion, failure criterion）。缺少任一字段的验证方案视为未完成——PM 无法据此执行。

- [ ] **成本纪律**：至少 50% 的验证方案成本为 ¥0（公开数据核查、专家电话访谈、供应商邮件 RFQ）。如果大多数验证方案都需要 ¥5000+，说明红队没有认真找最便宜的替代方法。

- [ ] **决策边界清晰**：红队报告中没有任何"建议继续"、"建议放弃"、"风险可接受"等决策性语言。报告语言是条件陈述（"如果 X 不成立，则 Y"），不是建议陈述（"应该做 Z"）。

- [ ] **已知风险不重复**：报告中不出现 risks.csv 中已有登记且已包含 mitigation 的风险。如果出现，说明 Step 1 的已知风险排除不彻底。

- [ ] **新假设正确落盘**：所有 source=newly_identified 的假设已写入 assumptions.csv，status 字段为 `red_team_identified`，ID 无冲突，字段映射正确。

- [ ] **可追溯性**：每个杀伤性假设可以追溯到具体的预-mortem 失败场景；每个失败场景可以追溯到产品成功逻辑链的关键节点。链路断裂的假设需要重新审视。

- [ ] **摘要质量**：摘要 ≤ 500 字，包含杀伤性假设数量、最危险单一假设、验证总预算、需 PM 决策事项。无占位符（TBD/TODO/待补充）。

## 8. Best Practices（最佳实践）

### 好的杀伤性假设 vs 差的杀伤性假设

**好的杀伤性假设（具体、可证伪、可追溯）**：

```markdown
#### KA-1: 目标用户愿意为远程开锁功能支付 ¥200+ 的价格溢价

| 维度 | 评分 | 理由 |
|------|------|------|
| Lethality | critical | 产品定价 ¥599 的核心支撑是远程功能溢价。如果用户只愿为远程功能支付 ¥50，产品要么亏损降价，要么失去核心差异化——两种结果都会导致商业失败。 |
| Uncertainty | critical | assumptions.csv 中此假设 confidence=中，但 evidence 只有一条：A-CWLS-012 引述的行业报告说"用户看重安全性"，没有涉及价格支付意愿。团队从未直接询问过用户愿意支付多少。 |
| 来源 | known (A-CWLS-004) | 已在 assumptions.csv 中标记，但现有验证方法为"参考竞品定价"——竞品定价不等于用户支付意愿。 |
```

**差的杀伤性假设（模糊、不可证伪、无杠杆）**：

```markdown
#### KA-X: 用户需求是真实存在的

问题：太模糊。"用户需求"是什么需求？"真实存在"怎么算验证？无法设计验证方案。
修正：具体化假设——"至少 30% 的目标用户认为'远程开锁'是不可或缺的功能（不是 nice-to-have）。"
```

### 好的验证方案 vs 差的验证方案

**好的验证方案（具体、便宜、可证伪）**：

```markdown
| **方法** | 找 5 个符合目标用户画像的人（一二线城市租房者，年龄 25-35，现有门锁非智能锁），进行 20 分钟视频访谈。展示产品概念描述和功能清单（不含定价），然后问：(1) 你觉得这个产品值多少钱？(2) 这些功能中你愿意为哪个额外付钱？(3) [展示 ¥599 价格] 在这个价格你会买吗？如果不会，什么价格你会买？ |
| **成本** | ¥0（利用团队个人网络或社交媒体招募，视频访谈免费） + 3 天 |
| **成功标准** | ≥3/5 人在不知道价格的情况下给出的心理价位 ≥ ¥599；或知道价格后 ≥3/5 人表示"会买"或"可能会买" |
| **失败标准** | ≥4/5 人给出的心理价位 < ¥399；或知道 ¥599 价格后 ≥4/5 人表示"不会买" |
```

**差的验证方案（模糊、昂贵、无结论）**：

```markdown
| **方法** | 进行用户调研以确认价格接受度 |
| **成本** | 待定 |
| **成功标准** | 用户接受定价 |
```

问题：方法没说怎么调研、调研谁、问什么问题；成本写"待定"；成功标准无法判断——几个用户接受算"接受"？

### 常见陷阱

1. **红队变成第二遍 hw-review**：发现自己在检查 evidence 的 source_grade 或 direct_quote 时，立即停止。那是 hw-review 的职责。红队只关心"假设错了会怎样"，不关心"假设有没有被正确记录"。

2. **预-mortem 不够悲观**：预-mortem 的场景需要是**彻底的商业失败**，不是"表现一般"。如果场景中产品还在"挣扎"、"调整策略"，说明悲观度不够。场景设定是"退市在即"，不是"需要迭代"。

3. **验证方案变成了开发计划**：如果验证方案需要先开发功能原型、需要写代码、需要开模具，那就是搞错了。红队的验证方案是**在产品开发之前就能执行的最小化测试**。需要开发才能验证的，不叫"最便宜验证"。

4. **被高置信度假设欺骗**：团队对某些假设"很有信心"可能只是因为从未质疑过。如果 assumptions.csv 中一个假设的 confidence=高 但 validation_method 为空或写了"行业常识"，需要警惕——这可能是一个从未被验证的隐藏假设。

5. **忽略"成功逻辑链"中跳过的环节**：如果 PRD 中说"A 功能 → B 用户价值 → C 商业成功"，但 A→B 之间没有任何 evidence 支撑，这是一个典型的隐藏假设——团队假设了 A 必然导致 B。

6. **验证方案完美主义**：想设计一个"无懈可击"的验证方案，导致成本飙升。红队的原则是"刚好足够获得信号"，不是"科学严谨到可以发论文"。5 个人的概念测试比 500 人的问卷调查更符合红队精神（只要 5 个人给出了信号）。

7. **把所有假设都标成 KILLER**：如果报告中有 15 个 KILLER 假设，说明排序机制失效了。KILLER 的意思是"这个假设错了产品必死"——一个产品不可能有 15 个独立的必死条件。绝大多数假设错了产品只会受伤，不会死。

8. **替 PM 决定验证优先级**：红队报告呈现了验证方案的成本和重要性排序，但不应该说"建议优先执行 X"或"Y 不值得验证"。决策是 PM 的——PM 可能有红队不知道的资源约束或战略优先级。
