# hw-mrd-brd — 市场需求文档与商业需求文档编写

## 1. Purpose

本 Skill 解决"市场需要什么、商业上值不值得做"的问题。它将已批准的产品规划报告（含市场机会、用户洞察、竞品格局、商业判断方向）转化为结构化的市场需求文档（MRD）和商业需求文档（BRD），为下游产品定义（hw-product-definition）提供"做什么"和"为什么做"的决策依据。

在 PM Agent 工作流中，本 Skill 位于产品规划（hw-product-strategy）之后、产品定义（hw-product-definition）之前。它承接产品规划报告的"三定"结论（定方向、定市场、定商业逻辑），产出 MRD（回答"市场上是否存在值得进入的需求"）和 BRD（回答"商业上值不值得投入、投入多少、收益和风险是什么"）。

**路由差异是核心设计**：

| 路由 | 输出格式 | 使用模板 | 文档数 |
|------|---------|---------|--------|
| L2 标准流程 | 合并版 MRD+BRD | `07_MRD_BRD合并版_标准流程.md` | 1 份 |
| L3 完整流程 | 独立 MRD + 独立 BRD | `02_MRD_市场需求文档.md` + `03_BRD_商业需求文档.md` | 2 份 |

L1 项目不经过本 Skill（L1 裁剪了 MRD/BRD 阶段，市场需求和商业判断在 L1 轻量产品定义/PRD 合并文档中简要覆盖）。

## 2. Context

### 触发条件

- 产品规划报告已通过 Gate 4 审批（L2/L3 路由）
- 上游输入就绪：产品规划报告 + evidence.csv + assumptions.csv + risks.csv
- L1 项目不触发本 Skill（L1 无独立 MRD/BRD 阶段）

### 前置条件

| 条件 | 检查方式 |
|------|---------|
| 产品规划报告已批准 | Gate 4 approval record（decisions.csv 中 decision_type=product_strategy_approval, status=approved） |
| 目标市场和用户已明确 | 产品规划报告"目标市场"和"目标用户"章节已填写 |
| 竞品格局已分析 | 产品规划报告"竞争定位"章节或相关竞品研究报告已就绪 |
| 商业方向已确定 | 产品规划报告"商业逻辑"章节已填写（定价方向、成本目标、收入逻辑） |
| 项目路由等级已知 | 项目启动卡第 1 节 route_level = L2 或 L3 |
| evidence.csv 已填充 | 研究阶段产出的 evidence 记录可供引用 |

### 输入

- 产品规划报告（`output/{project}/14_产品规划报告.md`）
- `registers/evidence.csv`（市场、用户、竞品相关 evidence 记录）
- `registers/assumptions.csv`（产品规划阶段标记的假设）
- `registers/risks.csv`（已识别的风险）
- 项目启动卡（`output/{project}/00_项目启动卡.md`）— 获取路由等级

### 输出消费者

| 消费者 | 消费内容 | 时机 |
|--------|----------|------|
| hw-product-definition（PM） | MRD/BRD 中的目标市场、用户需求、商业约束 | Gate 5 批准后，进入产品定义阶段 |
| hw-review（Reviewer） | MRD/BRD 完整草稿 | 本 Skill 产出 draft 后独立审查 |
| Gate 5 审批（人工 PM） | MRD/BRD + Reviewer findings | 确认商业可行性 |
| hw-gate-prep（PM） | MRD/BRD 结论摘要 | Gate 5 简报生成时引用 |

### 不负责

- 不执行市场研究或竞品分析 — 那是 Researcher Agent 的工作（hw-market-study, hw-competitive-analysis, hw-user-research）
- 不编写产品规划报告 — 那是上游 hw-product-strategy 的工作
- 不定义产品功能和规格 — 那是下游 hw-product-definition 和 hw-prd 的工作
- 不自行批准 MRD/BRD — Gate 5 是人工决策点
- L1 项目不触发本 Skill

## 3. Operating Principles

### Principle 1: 路由决定输出格式

L2 和 L3 路由产出不同格式的文档。L2 使用合并版 MRD+BRD（一份文档覆盖市场需求和商业判断，更轻量、更快）；L3 使用独立 MRD + BRD（两份文档，市场需求和商业判断分开深度展开，适用于新品类）。不对 L2 项目强制输出 L3 格式的两份独立文档（过度工程），也不对 L3 项目使用 L2 合并模板（需求缺失风险）。

**反面行为**：L2 项目（同品类新 SKU，市场已知）被要求写完整的独立 MRD（7 章）和独立 BRD（7 章），填入了大量从产品规划报告中逐字搬运的内容，造成文档冗余和 Gate 5 审批周期延长。或 L3 新品类项目使用合并版模板略过市场细分、角色链分析、商业模式画布等关键章节。

**违反后果**：过度工程 → PM 和 Reviewer 时间被浪费在填写已知信息上，项目节奏受阻。需求缺失 → 产品定义阶段发现关键市场或商业假设未经验证，需退回补充研究。

---

### Principle 2: 证据驱动的需求声明

MRD 中的每一条市场判断（市场规模、用户需求强度、竞品缺口）必须引用至少一条证据（evidence_id）或已标记置信度的假设（assumption_id）。BRD 中的每一条成本估算、收益预测、定价假设必须标注置信度和依据来源。"市场很大""用户需要""竞品没有"等无来源声明在 MRD/BRD 中不可接受。

**反面行为**：市场细分表中填写"中国市场，规模约 100 亿"但不标注数据来源和时间。收益测算表中填写"预计第一年销量 10 万台"但不说明推算逻辑和关键假设。竞品比较表中声称"我方产品有明显优势"但不引用竞品拆机、评论分析或体验测试的证据。

**违反后果**：Reviewer 在 hw-review 中标记 severity=blocker。无证据的需求声明 → 下游产品定义建立在不可靠的前提上 → Gate 5 退回 → 需补充研究后重新提交。

---

### Principle 3: 不做重复研究

本 Skill 从产品规划报告和 evidence.csv 中提取已有的市场和商业判断，将其结构化为 MRD/BRD 格式，而非重新执行市场研究。如果产品规划报告中的某个维度信息不足以支撑 MRD/BRD 的对应章节，应标记为"待补齐"并说明需要什么输入、从哪里获得，而不是自行发起新的研究。

**反面行为**：产品规划报告中已有明确的目标市场定义，但 MRD 编写时重新写了一份不同的市场细分（基于 Agent 自身知识而非产品规划报告的结论）。或发现产品规划报告中缺少某竞品的 BOM 估算，Agent 自行推测数字而不标记为假设。

**违反后果**：MRD/BRD 与产品规划报告结论不一致 → 产品定义阶段出现方向冲突 → Gate 5 退回要求对齐。

---

### Principle 4: 商业判断必须给出明确方向

BRD 的立项建议章节必须形成明确决策（建议立项 / 暂缓 / 不建议），不能以"需要进一步分析""视市场情况而定"等开放式结论结束。即使是"暂缓"，也必须写明暂缓条件和重新评估的触发条件。收益测算不能只给单一乐观数字，必须包含保守、基准、乐观三种情景。

**反面行为**：立项建议写成"建议在条件成熟时推进"，不定义什么是"条件成熟"。收益预测只给一个"基准情景"数字，不说明上下行风险。

**违反后果**：Gate 5 审批人无法做出明确的 go/no-go 判断 → 审批退回 → 要求补充情景分析和明确建议。

---

### Principle 5: 缺失输入显式声明，不硬写结论

如果产品规划报告中的某个关键输入缺失（例如目标市场的渠道结构、竞品 BOM 成本、认证费用估算），不能在 MRD/BRD 中硬写成确定结论。必须在该章节中显式声明该项为假设或待补齐，标注置信度和影响范围，并写入 L2 合并版的"输入来源与缺口说明"表或 L3 BRD 的对应假设字段。

**反面行为**：产品规划报告未提供认证费用估算，BRD 中自行填入一个数字但标注 confidence=高。或认证费用缺失时直接跳过不写，造成成本估算表不完整。

**违反后果**：基于错误假设的商业判断 → 立项后发现实际成本远超预期 → 项目被迫中止或大幅缩减范围。

---

### Principle 6: 跨文档一致性

MRD 和 BRD 之间的市场判断、用户定义、竞品结论必须一致。合并版中这是自然保证的（同一份文档）；独立 MRD 和 BRD（L3）中，两份文档的"目标市场""目标用户""竞品格局"描述必须互相对齐，不能出现 MRD 说目标市场是 A，BRD 收益测算却按市场 B 计算的情况。

**反面行为**：L3 项目，MRD 市场细分表写了 3 个目标细分市场，BRD 收益测算却只覆盖了其中 1 个，且没有说明为何另外 2 个被排除。或 MRD 用户角色链中有"安装商"角色，BRD 渠道和售后部分却完全没有涉及安装商。

**违反后果**：Reviewer 在跨文档一致性检查中发现冲突 → severity=blocker → 两份文档需同步修正。

## 4. Instructions

### Step 1: 加载产品规划与确定路由

**输入**：
- 读取 `output/{project}/00_项目启动卡.md` 第 1 节，获取 `route_level`（L2 或 L3）
- 读取产品规划报告（`output/{project}/14_产品规划报告.md` 或等价文件）
- 读取 `registers/evidence.csv` 中与本项目相关的 evidence 记录（按 project 字段筛选）
- 读取 `registers/assumptions.csv` 中与本项目相关的 assumption 记录
- 读取 `registers/risks.csv` 中与本项目相关的 risk 记录

**操作**：
1. 确认路由等级为 L2 或 L3。若为 L1，停止执行并说明"L1 项目不经过 MRD/BRD 阶段，市场需求和商业判断在 L1 轻量产品定义/PRD 合并文档中覆盖"。
2. 从产品规划报告中提取以下关键信息块，作为 MRD/BRD 的输入素材：
   - 目标市场定义（地域、品类、细分维度）
   - 目标用户画像（含角色链信息，如有）
   - 核心用户场景和 JTBD
   - 竞品定位和差异化方向
   - 定价方向、成本目标、收入逻辑（商业逻辑部分）
   - 关键假设和已识别风险
3. 从 evidence.csv 中提取市场、用户、竞品相关的 evidence 记录（可通过 `related_component` 或 `category` 字段筛选），建立 evidence 引用池。
4. 判断每个 MRD/BRD 章节的输入充分性：已有（可直接填写）/ 部分（可填写但需标注假设）/ 缺失（声明待补齐）。

**检查点**：
- [ ] 路由等级已确认为 L2 或 L3（非 L1）
- [ ] 产品规划报告已读取，关键信息块已提取（≥4 个信息块）
- [ ] evidence 引用池已建立（≥3 条相关 evidence 记录，或已声明 evidence 不足）
- [ ] 每个 MRD/BRD 章节的输入充分性已标注（已有/部分/缺失）
- [ ] 如有缺失输入，已识别哪些是阻塞项（影响产品定义）vs 非阻塞项（可后置补齐）

---

### Step 2: 编写 MRD 部分（市场需求）

**输入**：Step 1 提取的目标市场、目标用户、竞品、用户场景信息块 + evidence 引用池

**操作**：

以下操作同时适用于 L2（合并版第 2-3 节）和 L3（独立 MRD 第 1-7 节）。L3 版本内容更深，L2 版本聚焦与决策直接相关的需求。

#### 2a. 市场定义与细分（L3 独立 MRD 第 2 节；L2 合并版第 2 节"市场需求"表的市场维度）

1. 使用 STP 方法论，从产品规划报告中提取市场边界定义
2. 按用户、场景、渠道、价格带、安装交付方式等维度细分市场
3. 填写市场细分表，每个细分市场标注：用户群体、场景、价格带、渠道、规模/增长、优先级
4. 标注数据来源（evidence_id）或声明为假设（assumption_id + confidence）
5. L3 额外：为每个细分市场写 1-2 句选择/不选择的理由

#### 2b. 目标用户与角色链（L3 独立 MRD 第 3 节；L2 合并版在"市场需求"表的用户列覆盖）

1. 识别并定义智能硬件特有的角色链：使用者、决策者、付费者、影响者、安装/维护者、风险承担者
2. 为每个角色填写：人群描述、关注点、决策影响
3. 如果产品规划报告中某角色信息缺失，标注为假设并说明"待用户研究验证"
4. L2 可简化为只列出与本次产品决策直接相关的角色（≥2 个）

#### 2c. 用户需求与场景（L3 独立 MRD 第 4 节；L2 合并版第 2 节"市场需求"表）

1. 使用 JTBD 格式描述每个核心场景：当（场景），我想（任务），以便（结果）
2. 为每个 JTBD 标注：当前痛点、期望结果、需求强度（高/中/低）、支撑证据（evidence_id）
3. 需求强度评级必须有依据：引用用户研究中的频次/强度数据，或竞品评论中的痛点提及频率，或标注为假设
4. L2 聚焦与本次产品决策直接相关的场景（≥3 个），L3 覆盖完整场景集

#### 2d. 竞品与替代方案（L3 独立 MRD 第 5 节；L2 合并版第 3 节"竞品与替代方案"）

1. 不仅列同类产品，还列入用户当前的替代方案（人工服务、传统机械方案、手机软件、已有家电系统等）
2. 每个方案填写：目标用户、核心卖点、用户好评/差评、价格、成本/BOM 推断（如有）、安装售后体验、我方机会
3. 好评/差评必须有来源（竞品评论分析、拆机报告、体验测试的 evidence_id）
4. L2 聚焦与本项目决策直接相关的 3-5 个竞品/替代方案；L3 覆盖完整竞品格局
5. 智能硬件特有的竞品维度（拆机结构、BOM 成本、购买安装体验、售后体验）必须至少覆盖其中 2 项

#### 2e. 市场需求优先级（L3 独立 MRD 第 6 节；L2 合并版在"市场需求"表的优先级列覆盖）

1. 使用评分矩阵对需求排序，维度：痛点强度、支付意愿、市场规模、竞争空白、交付复杂度、合规风险
2. 每个需求给出综合优先级（P0/P1/P2）和进入建议
3. 评分依据必须可追溯（evidence_id 或 assumption_id）
4. L2 可直接在需求表中标注优先级，L3 需要完整的评分矩阵表

#### 2f. MRD 结论（L3 独立 MRD 第 1 节和第 7 节；L2 合并版第 1 节"结论"的市场部分）

1. 写 MRD 结论摘要（≤200 字），包含：推荐目标市场、推荐核心需求、推荐差异化方向、不建议进入的市场/需求
2. 列出进入前必须验证的问题（≥3 个，按优先级排序）
3. 结论必须与前述章节的分析保持一致，不能出现前面说"市场 A 优先级最高"、结论却说"以市场 B 为主"的自相矛盾

**检查点**：
- [ ] MRD 各章节已填写且内容实质（非占位符或仅一个词）
- [ ] L3 独立 MRD：7 个章节（结论、市场细分、角色链、需求场景、竞品替代方案、需求优先级、MRD 结论）全部有内容
- [ ] L2 合并版：第 2 节（市场需求）和第 3 节（竞品与替代方案）表格已填写，≥3 个用户/客户场景、≥3 个竞品/替代方案
- [ ] 每条市场判断和需求声明标注了来源（evidence_id、assumption_id 或"来自产品规划报告第 X 节"）
- [ ] JTBD 使用"当...我想...以便..."格式，非功能列表
- [ ] 竞品分析覆盖了智能硬件特有的 ≥2 个维度（拆机/BOM/安装体验/售后体验）
- [ ] 需求优先级有评分依据（非仅凭主观判断）
- [ ] 结论与前述章节分析一致

---

### Step 3: 编写 BRD 部分（商业需求）

**输入**：Step 1 提取的商业逻辑信息块 + MRD 结论（Step 2f）+ evidence 引用池 + assumptions.csv + risks.csv

**操作**：

以下操作同时适用于 L2（合并版第 4-5 节）和 L3（独立 BRD 第 1-7 节）。L3 版本需要完整的商业模式画布和情景化收益测算，L2 版本聚焦关键商业判断。

#### 3a. 业务目标（L3 独立 BRD 第 2 节；L2 合并版第 4 节"商业判断"表）

1. 从产品规划报告中提取业务目标（收入、毛利、销量、客户数、战略卡位等）
2. 目标应尽量量化：每个目标包含指标名称、当前值、目标值、时间范围、负责人
3. 如果产品规划报告中某目标未量化，标注为假设并说明"待 Gate 5 确认"
4. 战略类目标（如"补齐产品线""建立品牌认知"）需说明如何衡量是否达成

#### 3b. 商业模式与收益逻辑（L3 独立 BRD 第 3 节；L2 合并版第 4 节"商业判断"表的收益逻辑行）

1. L3：使用商业模式画布简化分析，填写 8 个模块：目标客户、价值主张、渠道、收入来源、成本结构、关键资源、关键伙伴、售后/服务模式
2. 收入来源需区分：硬件销售 / 配件耗材 / 软件订阅 / 服务费 / 数据变现 / 其他
3. 售后/服务模式对智能硬件尤其重要：安装服务、保修策略、配件供应、维修网络
4. L2：以简洁的"收益逻辑"描述代替完整画布（≤3 句话）

#### 3c. 投入与成本（L3 独立 BRD 第 4 节；L2 合并版第 4 节"商业判断"表的成本影响行）

1. 列出智能硬件特有的成本项：研发投入、模具/结构、BOM、认证测试、试产、渠道/营销、售后服务
2. 每项标注：估算金额、关键假设、置信度（高/中/低）
3. BOM 成本估算引用竞品拆机或供应链询价证据（evidence_id）；无证据时标注 confidence=低
4. 认证费用按目标市场列出（FCC/CE/SRRC/BQB 等），每个认证标注标准号和估算费用范围
5. L2 可汇总为大类（≥3 类），L3 需逐项列出

#### 3d. 收益测算（L3 独立 BRD 第 5 节；L2 合并版第 4 节"商业判断"表的毛利影响行）

1. 至少给出三种情景：保守、基准、乐观
2. 每种情景包含：销量、售价、收入、毛利率、毛利、回收期、关键假设
3. 关键假设必须显式声明（如"保守情景假设渠道铺货率仅达到基准的 60%"）
4. 回收期计算逻辑必须可复现（可写明公式或计算步骤）
5. L2 可简化为基准 + 保守两种情景

#### 3e. 商业风险（L3 独立 BRD 第 6 节；L2 合并版第 4 节中隐含在商业判断中，并在第 5 节"决策建议"中提及）

1. 识别智能硬件特有的商业风险：认证不通过、供应链中断、良率不达预期、售后成本超支、库存积压、渠道动销不及预期
2. 每个风险标注：概率（高/中/低）、影响（高/中/低）、预警信号、应对措施、负责人
3. 风险评级必须与 `registers/risks.csv` 中的记录一致；不一致时以 CSV 为准
4. L2 聚焦 top 3 风险；L3 需覆盖 ≥5 个商业风险

#### 3f. 立项建议与 BRD 结论（L3 独立 BRD 第 1 节和第 7 节；L2 合并版第 1 节"结论"的商业部分和第 5 节"决策建议"）

1. 给出明确的立项建议：建议立项 / 暂缓 / 不建议
2. 写明：立项条件、所需资源、下一阶段里程碑、退出条件
3. 立项建议必须与收益测算和风险评估保持一致。如果基准情景回收期超过 3 年且有 ≥2 个高风险项，"建议立项"需要非常强的战略理由支撑
4. L2 合并版第 5 节"决策建议"还要补充：产品定义输入（本 MRD/BRD 传递给产品定义的要点）、待验证问题、未补齐但允许后置的输入、阻塞下一阶段的输入

## 6. Quality Bar

Reviewer 将按以下 checklist 逐项检查。全部通过方可进入 Gate 5 审批。

- [ ] **路由格式正确**：L2 输出合并版（1 份文档，6 个章节），L3 输出独立 MRD + BRD（2 份文档，各 7 个章节）。L2 文档不遗漏第 0 节"输入来源与缺口说明"，L3 两份文档不缺失任何章节
- [ ] **证据可追溯**：MRD 部分每条市场判断和需求声明标注了来源（evidence_id、assumption_id 或"来自产品规划报告第 X 节"）；BRD 部分每个成本估算标注了置信度（高/中/低）。无"裸声明"（看起来像事实但没有来源）
- [ ] **商业判断明确**：BRD 给出了明确的立项建议（立项/暂缓/不建议）和具体条件，不是"需要进一步分析"等开放式结论。收益测算包含 ≥2 种情景（L2）或 ≥3 种情景（L3），每种情景有关键假设
- [ ] **跨文档/跨章节一致**：MRD 和 BRD 之间的目标市场、目标用户、竞品描述一致。L3 两份独立文档的市场/用户描述互相对齐
- [ ] **智能硬件特有维度覆盖**：竞品分析覆盖了 ≥2 个智能硬件特有维度（拆机/BOM/安装体验/售后体验）；成本估算覆盖了 ≥3 个智能硬件特有成本项（BOM/模具/认证/试产/售后）；角色链识别了 ≥3 个角色
- [ ] **输入来源表完整**（L2 合并版第 0 节）：6 行输入项全部有状态标注；所有"缺失"项有处理方式；缺失且阻塞产品定义的项有责任人和截止时间
- [ ] **MRD 结论与 BRD 结论逻辑一致**：MRD 说"市场机会大、竞争空白明显"，但 BRD 说"暂缓"——这种矛盾必须有充分理由解释（如虽然市场好但投入超出当前能力），否则为 inconsistency
- [ ] **风险与台账一致**：BRD 中的商业风险评级与 risks.csv 中对应当前项目的记录一致
- [ ] **无占位符**：输出文档中无 TBD / TODO / "待定" / "根据实际情况调整"。未确认项写"待确认"并标注 expected_source
- [ ] **摘要精炼**：L2 第 1 节"结论" ≤200 字；L3 MRD 第 1 节"文档结论" ≤200 字；L3 BRD 第 1 节"商业结论" ≤200 字

## 8. Best Practices

### 好的输出 vs 差的输出

**好的 MRD 市场需求声明：**
```
场景：用户离家后想起可能没关窗户
JTBD：当用户离家后（场景），希望远程检查窗户开关状态并在必要时远程关闭（任务），
      以避免雨水损坏室内物品或安全风险（结果）
当前痛点：不确定窗户是否关了，只能返回检查，浪费时间（用户研究：68% 受访者有此经历，EV-USER-003）
期望结果：手机上一键查看所有窗户状态，远程关闭，关闭后收到确认通知
需求强度：高
证据：EV-USER-003, EV-USER-007（售后工单中"窗户未关导致进水"类投诉占售后总量的 12%）
```

**差的 MRD 市场需求声明：**
```
场景：智能控制
需求：用户需要远程控制窗户
需求强度：高
```
问题：无 JTBD 格式、无痛点、无证据、需求强度无依据。

---

**好的 BRD 收益测算：**
```
| 情景 | 销量 | 售价 | 收入 | 毛利率 | 毛利 | 回收期 | 关键假设 |
| 保守 | 5,000 台 | ¥899 | ¥4.5M | 35% | ¥1.6M | 18 个月 | 渠道铺货率 30%，仅覆盖一线城市 |
| 基准 | 12,000 台 | ¥999 | ¥12.0M | 40% | ¥4.8M | 12 个月 | 渠道铺货率 60%，覆盖一二线城市 |
| 乐观 | 25,000 台 | ¥1,099 | ¥27.5M | 45% | ¥12.4M | 6 个月 | 渠道铺货率 85% + 大客户集采订单 5,000 台 |

关键假设说明：
- 渠道铺货率基于历史同品类产品上市数据（EV-MARKET-012），基准值取中位数
- 乐观情景的大客户订单基于现有客户关系（3 家已表达意向，A-SALES-003, confidence=中）
- 毛利率差异反映了规模效应对 BOM 成本的摊薄（采购量每翻倍，BOM 成本降约 8%，EV-SUPPLY-005）
```

**差的 BRD 收益测算：**
```
| 情景 | 销量 | 收入 | 毛利率 |
| 基准 | 10,000 台 | ¥10M | 40% |
```
问题：只有单一情景、无关键假设、数字来源不明、无回收期。

---

**好的"立项建议"：**
```
- 是否建议立项：建议立项
- 立项条件：
  1. BOM 成本控制在 ¥320 以内（当前估算 ¥280-350，需供应商正式报价确认，confidence=中）
  2. FCC + CE 认证周期确认 ≤12 周（需认证实验室评估，截止 Gate 6 前）
  3. 至少 1 家核心渠道签署意向书（截止 Gate 6 前）
- 退出条件：
  1. 若 DVT 阶段 BOM 成本超 ¥380（基准情景毛利率将跌破 30%），项目暂停并重新评估
  2. 若认证在计划上市日期前 8 周仍未通过，上市时间顺延一季并重新测算收益
```

**差的"立项建议"：**
```
- 是否建议立项：视情况而定
- 立项条件：BOM 成本可控，认证顺利
- 退出条件：出现重大问题时暂停
```
问题：无具体数字、无明确决策方向、退出条件模糊到不可执行。

| L2 和 L3 模板混用 | L2 项目写了 7 章独立 MRD，大量内容从产品规划报告逐字搬运；或 L3 项目用合并版模板略过了角色链分析和商业模式画布 | Step 1 确认路由后严格使用对应模板。L2 用 07 合并版，L3 用 02+03 独立版 |
| 把 MRD 写成功能列表 | MRD 的需求场景表中直接写"支持远程开关窗""支持定时关窗"等功能，而不是 JTBD 格式的需求 | 使用"当...我想...以便..."JTBD 格式；需求描述写用户任务和期望结果，不写功能实现 |
| 收益测算只有乐观数字 | 只给一个"基准情景"，且数字偏高，没有保守情景 | 至少给出保守和基准两种情景（L2）或三种（L3）；保守情景应有明确的悲观假设 |
| 竞品分析只看同类产品 | 只分析同品类智能硬件竞品，忽略了传统机械方案、人工服务、手机 App 等替代方案 | 至少纳入 1-2 个非同类替代方案（如传统窗户+手动关窗、物业巡检服务等） |
| 成本估算无置信度 | 所有成本项不加区分地写一个数字，不标数据来源和可靠性 | 每项成本标注置信度（高=有供应商报价或历史数据；中=基于竞品拆机估算；低=基于行业经验推测） |
| 立项建议回避决策 | 写成"建议进一步研究""待市场验证后决定"等开放式结论，把决策推给下游 | 必须在当前信息下给出明确建议（立项/暂缓/不建议），即使信息不完美。同时列出条件和退出标准 |
| 角色链遗漏 | 只写"用户"一个角色，忽略了智能硬件的购买者、安装者、维护者角色 | 至少识别 3 个角色（使用者、决策者、付费者、影响者、安装/维护者中选），分析其不同关注点 |
| 商业风险只写通用风险 | 列"市场竞争激烈""技术风险"等通用风险，不写智能硬件特有的认证、良率、售后、库存风险 | 至少覆盖 2 个智能硬件特有风险维度（认证/供应链/良率/售后/库存/渠道动销） |
