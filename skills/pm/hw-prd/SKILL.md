# hw-prd — 硬件产品需求文档编写

## 1. Purpose（目的）

本 Skill 解决"具体怎么做、怎么验收"的问题。它将已批准的产品定义文档（04_产品定义文档 或 L1 轻量产品定义）转化为一份完整的、可实现的、可测试的硬件 PRD，覆盖功能、软件、硬件、结构四个模块。

在 PM Agent 工作流中，本 Skill 位于产品定义（hw-product-definition）之后、验证计划（hw-validation-plan）之前。它承接"为谁做、解决什么问题、边界在哪里"，产出"具体做什么、怎么做、怎么验证"。PRD 不应重新讨论市场是否值得做，除非产品定义发生重大变化。

本 Skill 同时负责同步维护 requirements.csv 和增量维护 traceability.csv，确保需求与证据之间的可追溯性。

## 2. Context（上下文/适用场景）

### 触发条件

- 产品定义文档已通过 Gate 6 审批（或 L1 场景下已通过 Gate 1 路由判定）
- 上游输入就绪：产品定义文档 + 技术约束 + 供应链约束 + 合规约束
- 对于 L1 路由：使用 12_L1_轻量产品定义_PRD合并文档 模板，在 PRD 前置章节嵌入最小产品定义
- 对于 L2/L3 路由：使用 05_PRD_产品需求文档 模板，独立产品定义文档已就绪

### 前置条件

| 条件 | 检查方式 |
|------|---------|
| 产品定义文档已批准 | Gate 6 approval record（L2/L3）或 Gate 1 路由判定为 L1 |
| 目标用户和场景已明确 | 产品定义文档"目标用户"和"核心场景与 JTBD"章节已填写 |
| MVP/本版范围已明确 | 产品定义文档"产品范围"章节已填写 |
| 关键约束已知 | 技术/供应链/合规约束已记录在 evidence.csv 或产品定义文档中 |
| 验收指标已定义 | 产品定义文档"成功指标"章节已填写 |

### 输出消费者

| 消费者 | 用途 |
|--------|------|
| hw-validation-plan（PM） | 基于 PRD 需求生成验证计划 |
| hw-review（Reviewer） | 独立审查 PRD 四模块完整性和可追溯性 |
| hw-handoff（PM） | PRD 冻结后作为下游交付包的组成部分 |
| Gate 7 审批（人工 PM） | 确认 PRD + 验证计划后可进入开发 |

### 路由差异（L1 vs L2/L3）

| 维度 | L1 | L2/L3 |
|------|-----|-------|
| 使用模板 | 12_L1_轻量产品定义_PRD合并文档 | 05_PRD_产品需求文档 |
| 产品定义 | 嵌入 PRD 前置章节（最小产品定义） | 独立文档，已批准 |
| 输入来源表 | L1 使用条件检查 + 输入来源表 | 标准输入来源与缺口说明表 |
| 需求深度 | 仅覆盖变更/新增部分 | 完整需求覆盖 |
| 章节数 | 7 章 | 9 章（含独立验收标准章节） |

## 3. Operating Principles（操作原则）

### Principle 1: 四模块完整性

硬件 PRD 必须覆盖 **功能 / 软件 / 硬件 / 结构** 四个模块。任何一个模块缺失或仅有标题而无实质内容，PRD 不应通过 Gate 7。

- **反面行为**：只写软件功能需求，将"硬件选型待定""结构由 ID 团队负责"作为占位，实际不定义硬件和结构需求。
- **违反后果**：Reviewer 在 hw-review 中标记 severity=blocker，PRD 退回，不得进入验证计划阶段。四模块完整性是 AGENTS.md 质量底线第 3 条，无例外。

### Principle 2: 证据驱动的需求

每一条 P0/P1 需求必须有至少一条可追溯的证据来源（evidence_id）或已声明的假设（assumption_id）。需求不应凭空产生，不应基于个人偏好或"行业惯例"而无证据支撑。

- **反面行为**：编写需求时直接列出功能清单，不标注任何来源，事后补 traceability 记录。或引用"一般认为""市场普遍做法"等不可验证的说法作为证据。
- **违反后果**：traceability.csv 覆盖率不足 → Reviewer 标记 severity=blocker。AGENTS.md 质量底线第 4 条："P0/P1 requirement 必须有 ≥1 条 traceability 记录"。

### Principle 3: 可验收性

每一条 P0/P1 需求必须包含可量化、可测试的验收标准。验收标准不能是主观判断词（如"体验良好""操作流畅""界面美观""响应快速"），必须是可测量、可重复验证的指标。

- **反面行为**：验收标准写成"用户体验良好""系统稳定可靠""操作方便"。或在 L1 场景下以"轻量"为由省略验收标准。
- **违反后果**：测试团队无法编写测试用例，Reviewer 标记 severity=blocker。需求无验收标准等同于不可交付。

### Principle 4: 同步写台账

requirements.csv 必须在每条需求定义时**同步**写入，不能批量在 PRD 完成后一次性补录。traceability.csv 必须在建立 evidence→requirement 关联时**增量**追加，不能事后批量构造。

- **反面行为**：先写完整个 PRD markdown，最后统一"导出"到 CSV。或写完 PRD 后回头补造 traceability 记录来满足覆盖率检查。
- **违反后果**：同步写入中断 → 需求 ID 可能重复或遗漏。增量追加缺失 → traceability 记录与需求定义脱节，关联关系不可信。

### Principle 5: 路由遵从

L1 项目使用轻量合并模板，L2/L3 使用完整 PRD 模板。不对 L1 项目施加 L3 级需求深度（过度工程），也不对 L3 项目使用 L1 模板（需求缺失风险）。

- **反面行为**：L1 小改款项目，每个需求按 L3 标准写完整状态机和端云联动，导致 PRD 过度膨胀。或 L3 新品类项目，以"后续迭代再细化"为由使用 L1 模板略过硬件/结构需求。
- **违反后果**：过度工程 → 浪费 PM 和 Reviewer 时间，项目节奏受阻。需求缺失 → 开发阶段才发现未定义的需求，导致硬件改版或模具重开。

## 4. Instructions（分步骤指引）

### Step 1: 加载产品定义与约束

- **输入**：读取已批准的产品定义文档（L2/L3: `04_产品定义文档.md`；L1: 项目启动卡中的产品定义章节）+ `registers/evidence.csv` 中的约束记录
- **操作**：
  1. 提取目标用户、核心场景（JTBD）、MVP 范围、产品边界、成功指标
  2. 提取关键约束：技术约束（芯片平台、通信协议等）、供应链约束（供应商、交期、MOQ）、合规约束（认证标准、目标市场法规）、成本约束（BOM 目标）
  3. 填写 PRD Section 0（输入来源与缺口说明表）：逐项标注状态（已有/替代/缺失）、是否阻塞 PRD、处理方式
  4. L1 项目额外填写"L1 使用条件检查"表，逐项确认满足条件
- **检查点**：输入来源表全部已填写；所有"阻塞=是"的条目已给出处理方式（补齐/后置/决策确认）；无"缺失"且"阻塞=是"且未处理的条目

### Step 2: 定义功能需求（功能模块）

- **输入**：产品定义文档的用户场景、JTBD、MVP 范围
- **操作**：
  1. 列出本版本包含和不包含的功能（Section 3 功能范围表），按硬件/固件/APP/云端/后台/安装售后拆开
  2. 编写用户故事与流程（Section 4），每个故事包含：作为某类用户 → 希望完成某操作 → 以获得某结果，以及前置条件、主流程、异常流程、优先级
  3. 逐条编写功能需求（Section 5 详细需求），每条包含：
     - 用户价值、触发入口、前置条件
     - 输入、处理规则、输出
     - 设备状态（在线/离线/低电量/故障/升级中/恢复出厂/绑定/解绑）
     - APP/云端/固件联动
     - 权限规则、异常场景、埋点/日志
     - 验收标准（可测量）
  4. 定义状态与规则（Section 6），列出设备、用户、订单、服务等关键对象的状态：进入条件、退出条件、用户可见表现、系统处理
- **检查点**：所有 MVP 范围场景有对应功能需求覆盖；每条功能需求有可测量的验收标准；设备状态覆盖了在线/离线/低电量/故障/升级/恢复出厂/绑定/解绑等硬件关键状态

### Step 3: 定义软件需求（软件模块）

- **输入**：功能需求（Step 2）+ 产品定义中的设备状态机 + 端云流程
- **操作**：
  1. **固件需求**：定义固件逻辑，包括传感器数据采集与处理、执行器控制算法、状态机转换逻辑、通信协议实现（BLE/Wi-Fi/Zigbee 等）、OTA 升级策略（全量/差分、回滚机制）、本地数据缓存与同步、错误检测与自恢复、安全启动与固件签名验证
  2. **APP 需求**：定义移动端/桌面端应用逻辑，包括设备发现与绑定流程（BLE 扫描/二维码/Wi-Fi 配网）、设备控制界面与交互规则、数据展示与历史记录、告警推送与通知、多设备管理、用户账号与权限、离线模式降级策略
  3. **云端需求**：定义云服务逻辑，包括设备注册与认证（设备 ID/密钥管理）、数据上行与下行协议（MQTT/HTTP/WebSocket）、设备影子/数字孪生、规则引擎与自动化场景、数据存储与备份策略、用户数据隐私与合规（GDPR/个人信息保护法）
  4. **后台需求**：定义运营后台功能，包括设备管理（激活/停用/远程诊断）、用户管理、固件版本管理与灰度发布、数据分析与监控面板、客服与售后工单
- **检查点**：固件需求覆盖所有设备状态转换；APP 需求覆盖完整的用户操作闭环（发现→绑定→使用→解绑）；云端需求覆盖数据安全与隐私合规；所有软件需求有关联的功能需求 ID

### Step 4: 定义硬件需求（硬件模块）

- **输入**：产品定义中的规格参数 + 技术约束 + 合规要求 + evidence.csv 中硬件相关证据
- **操作**：
  1. **核心组件选型**：定义主控芯片（MCU/SoC）、通信模块（BLE/Wi-Fi/Zigbee/LoRa/Cellular）、传感器、执行器、电源管理芯片、存储等关键器件的规格要求和技术选型依据
  2. **电气规格**：定义输入电压/电流范围、功耗目标（工作/待机/休眠）、电池容量与续航、充电方式与充电时间、接口定义（USB/UART/SPI/I2C/GPIO）、ESD/EMC 防护等级
  3. **BOM 约束**：BOM 成本目标、关键器件供应商（至少 2 个可选源）、替代料策略、长交期物料的提前识别
  4. **认证要求**：目标市场的强制性认证（FCC/CE/SRRC/BQB 等）、建议性认证、每一个认证的标准号和适用条件
  5. **环境适应性**：工作温度/湿度范围、存储温度/湿度范围、抗振动/抗跌落规格
- **检查点**：关键器件有选型依据（性能/成本/供货/兼容性）；电气规格有明确的目标值；认证标准有具体的标准号；BOM 目标成本已量化

### Step 5: 定义结构需求（结构模块）

- **输入**：硬件需求（Step 4）+ 产品定义中的工业设计约束 + 使用环境
- **操作**：
  1. **外观与尺寸**：外形尺寸（长×宽×高）、重量目标、颜色/材质/表面处理（CMF）、工业设计的关键约束（品牌语言、人机工程）
  2. **结构设计**：外壳材质与工艺（注塑/CNC/钣金/压铸）、装配方式（卡扣/螺丝/超声焊接/胶粘）、防水防尘（IP 等级与密封方案）、可拆卸部件（电池盖/滤网/SIM 卡槽）
  3. **散热设计**：热源识别（主控/功放/电池/充电电路）、散热方式（自然散热/导热片/风冷/液冷）、热仿真要求、温升限值
  4. **安装与固定**：壁挂/桌面/吸顶/磁吸/嵌入式安装方式、安装孔位与间距、安装配件清单、安装工具要求
  5. **可制造性与可维护性**：DFM 约束（拔模角度/壁厚/分模线）、维修可达性（易损件可更换、关键接口可测试）、包装要求（跌落保护、运输振动）
- **检查点**：外壳材质和工艺已明确；IP 等级有目标值；散热方案匹配热源功耗；安装方式已定义；DFM 基本约束已纳入

### Step 6: 同步写入 requirements.csv

- **输入**：Steps 2-5 中定义的每一条需求
- **操作**：
  1. 每定义完一条需求（命名格式 REQ-{project}-{seq}，如 REQ-CWLS-001），立即向 `registers/requirements.csv` 追加一行
  2. 写入字段：
     - `requirement_id`: REQ-{project}-{seq}
     - `requirement`: 需求描述（与 PRD 文档中一致）
     - `source`: 来源章节（如"05_PRD Section 5 R-003"）
     - `priority`: P0 / P1 / P2 / P3
     - `doc`: 固定为 "PRD"
     - `owner`: 责任方（如"固件""硬件""结构""APP""云端"）
     - `status`: 初始为 "draft"
     - `acceptance_criteria`: 验收标准（与 PRD 文档中一致，可测量）
     - `related_evidence`: 关联的证据 ID（逗号分隔，如 "EV-CWLS-003,EV-CWLS-007"）
     - `notes`: 补充说明（可选）
  3. **同步写入**意味着：写完一条需求 → 立即写 CSV → 再写下一需求。不在 PRD 全部完成后才批量导出。
- **检查点**：requirements.csv 中的 requirement_id 与 PRD 文档中的需求编号一一对应，无遗漏无重复；priority 字段不为空；P0/P1 需求的 acceptance_criteria 不为空

### Step 7: 增量追加 traceability.csv

- **输入**：requirements.csv 中的 requirement_id + evidence.csv 中的 evidence_id + 产品定义文档中的假设
- **操作**：
  1. 对每条需求，确定支撑它的证据或假设。追溯链可以是：evidence_id → requirement_id，也可能是 evidence_id → assumption_id → requirement_id
  2. 每建立一条关联，立即向 `registers/traceability.csv` 追加一行：
     - `trace_id`: T-{project}-{seq}
     - `research_finding`: 研究发现的摘要（引用 evidence.csv 中的直接引述）
     - `market_need`: 市场需求描述
     - `product_definition`: 产品定义中的对应章节引用
     - `requirement_id`: REQ-{project}-{seq}
     - `validation_item`: 该需求对应的验证项（与未来验证计划对齐）
     - `evidence_id`: EV-{project}-{seq}（或 A-{project}-{seq} 如果是假设支撑）
     - `status`: 初始为 "draft"
     - `notes`: 补充说明（可选）
  3. **增量追加**意味着：每建立一条关联 → 立即写 CSV。不在所有需求写完后再批量构造 traceability。
  4. 如果某条需求暂时无法关联到现有 evidence，应在 notes 中标注"待补齐证据"并在 PRD 的输入来源表中标记为假设。
- **检查点**：每条 P0/P1 需求至少有 1 条 traceability 记录；所有引用的 evidence_id 和 requirement_id 在被引用表中确实存在（无孤儿记录）

### Step 8: 验证四模块完整性与质量

- **输入**：PRD 完整草稿 + requirements.csv + traceability.csv
- **操作**：
  1. **四模块完整性检查**：逐模块确认 ——
     - 功能模块（Step 2）：Section 3/4/5/6 已填写，功能需求非空
     - 软件模块（Step 3）：固件 + APP + 云端 + 后台需求非空
     - 硬件模块（Step 4）：核心组件 + 电气规格 + BOM + 认证 + 环境适应性非空
     - 结构模块（Step 5）：外观尺寸 + 结构设计 + 散热 + 安装 + DFM 非空
  2. **P0/P1 可追溯性覆盖检查**：统计 requirements.csv 中 priority=P0 和 P1 的行数 X，统计 traceability.csv 中对应 requirement_id 的行数（去重）Y，要求 Y = X（100% 覆盖）
  3. **验收标准可测量性检查**：逐条检查 P0/P1 需求的 acceptance_criteria 字段，确认不含"体验良好""操作方便""稳定可靠""快速响应"等主观词，每条有可量化的指标或可观察的行为条件
  4. **ID 格式合规检查**：requirement_id 符合 REQ-{project}-{seq}，trace_id 符合 T-{project}-{seq}
  5. **孤儿记录检查**：traceability.csv 中引用的所有 requirement_id 在 requirements.csv 中存在，所有 evidence_id 在 evidence.csv 中存在
  6. 填写 PRD Section 7（非功能需求）：性能、功耗、可靠性、安全、隐私、兼容性等指标
  7. 填写 PRD Section 8（验收标准）：需求级和版本级验收标准汇总表
  8. 填写 PRD Section 1（产品概述）和 Section 2（需求背景与目标）—— 这些可以最后写因为它们是总结性内容
- **检查点**：四模块全部非空且内容实质（非占位）；P0/P1 traceability 覆盖率 = 100%；所有验收标准可测量；无 ID 格式错误；无孤儿记录

## 5. Output Structure（输出结构）

### 输出文件清单

| 文件 | 路径 | 写入时机 | 说明 |
|------|------|---------|------|
| PRD 文档 | `output/<project>/PRD_产品需求文档.md` | 全部完成后落盘 | L2/L3 使用完整模板；L1 使用合并模板 |
| requirements.csv | `registers/requirements.csv` | **同步写入**（Step 6） | 每定义一条需求即追加 |
| traceability.csv | `registers/traceability.csv` | **增量追加**（Step 7） | 每建立一条关联即追加 |

### L2/L3 PRD 文档结构（基于 05_PRD_产品需求文档）

```markdown
# 05_PRD_产品需求文档

### 文档说明
PRD 承接产品定义，把产品方向和边界转成可实现、可测试、可验收的功能和规则。
回答"具体怎么做、怎么验收"。

### 内容说明
- 输入：产品定义文档、用户故事地图、设备状态机、端云流程、技术/供应链/合规约束
- 输出：功能需求、流程规则、状态规则、非功能需求、验收标准、研发和测试输入

应先补齐产品定义或使用 L1 轻量产品定义/PRD 合并文档。
```

## 6. Quality Bar（最低质量标准）

Reviewer 将按以下 checklist 逐项检查。全部通过方可进入 hw-validation-plan 阶段。

- [ ] **四模块完整性**：功能、软件、硬件、结构四个模块全部有实质内容（非"待定""后续补充"等占位符），每个模块至少包含 3 个以上已定义的需求条目
- [ ] **P0/P1 traceability 覆盖率 100%**：requirements.csv 中所有 priority=P0 和 priority=P1 的需求，在 traceability.csv 中至少有 1 条对应记录
- [ ] **P0/P1 验收标准可测量性 100%**：所有 P0/P1 需求的 acceptance_criteria 不含主观词（"体验良好""操作方便""稳定可靠""快速响应""美观大方"等），每条有具体数值、百分比、时间范围或可观察的行为条件
- [ ] **输入来源表完整**：Section 0 所有行已填写，所有"阻塞=是"的条目有明确处理方式，无"缺失 + 阻塞=是 + 未处理"的情况
- [ ] **需求全覆盖**：产品定义中 MVP 范围内的所有用户场景，在 PRD 中有对应的功能需求（可正向追溯）
- [ ] **ID 格式合规**：所有 requirement_id 符合 REQ-{project}-{seq}，所有 trace_id 符合 T-{project}-{seq}，seq 从 001 递增无跳跃无重复
- [ ] **无孤儿记录**：traceability.csv 中所有 requirement_id 在 requirements.csv 中存在，所有 evidence_id 在 evidence.csv 中存在
- [ ] **设备状态覆盖**：Section 6 状态与规则表覆盖了硬件的关键状态（在线/离线/低电量/故障/升级中/恢复出厂/绑定/解绑等）
- [ ] **非功能需求完整**：Section 7 覆盖性能、功耗、可靠性、安全、隐私、兼容性至少 6 类非功能指标
- [ ] **变更记录就绪**：Section 9（L2/L3）或 Section 7（L1）的变更记录表已创建，初始版本行已填写

## 8. Best Practices（最佳实践）

### 好的需求 vs 差的需求

**好的功能需求（功能模块）**：
```
需求 REQ-001：蓝牙一键配网
- 用户价值：用户无需输入 Wi-Fi 密码即可完成设备配网
- 触发入口：设备首次上电，LED 指示灯橙色闪烁
- 前置条件：手机蓝牙已开启，设备处于出厂状态（未绑定）
- 输入：用户在 APP 点击"添加设备"，APP 扫描到设备 BLE 广播
- 处理规则：
  1. APP 通过 BLE 发送配网请求，设备返回 device_id + challenge
  2. APP 将当前 Wi-Fi SSID + 密码 + challenge 加密后通过 BLE 发送
  3. 设备解密后连接 Wi-Fi，连接成功后通过 MQTT 上报注册请求
  4. 云端注册成功后下发 device_token，设备存储并进入待绑定状态
- 输出：设备 LED 绿色常亮，APP 显示"添加成功"并进入设备主页
- 设备状态：出厂 → 配网中 → 待绑定
- APP/云端/固件联动：固件处理 BLE 通信和 Wi-Fi 连接 → 云端处理设备注册 → APP 引导用户操作
- 异常场景：
  - BLE 连接超时（30s）：设备 LED 橙色快闪，APP 提示"连接超时，请靠近设备后重试"
  - Wi-Fi 密码错误：设备 LED 红绿交替闪烁，APP 提示"密码错误，请重新输入"
  - 云端注册失败（网络不通）：设备本地缓存，每 30s 重试，最多重试 10 次
- 验收标准：配网成功 ≤30s（从点击"添加设备"到显示"添加成功"），成功率 ≥99%（500 次测试）
```

**差的功能需求**：
```
需求：设备支持配网
- 用户价值：方便用户使用
- 验收标准：配网成功率高，体验良好
```
问题：无具体流程、无异常处理、验收标准不可测量。

**好的硬件需求（硬件模块）**：
```
需求 REQ-010：主控芯片选型
- 芯片型号：ESP32-C3（首选）/ BL602（备选）
- 选型依据：
  1. 支持 BLE 5.0 + Wi-Fi 4，满足配网和数据上报需求（EV-001）
  2. 待机功耗 <50μA，满足电池供电场景续航目标（EV-004）
  3. ESP32-C3 通过 FCC/CE/SRRC 认证，降低认证风险（EV-007）
  4. 批量采购单价 <$1.2（1k+），满足 BOM 成本目标
- 验收标准：工程样机待机功耗实测 ≤50μA，Wi-Fi 连接稳定性 24h 无断连
```

**差的硬件需求**：
```
需求：主控芯片
- 选一款合适的 MCU
- 验收标准：满足产品需求
```
问题：无选型依据、无具体型号或备选、验收标准不可测量。

**好的结构需求（结构模块）**：
```
需求 REQ-020：外壳防护等级
- IP 等级：IP54（防尘 5 级 + 防溅水 4 级）
- 密封方案：上下壳超声焊接 + 按键硅胶密封圈 + USB 口硅胶塞
- 依据：产品用于厨房环境，需防尘和防溅水（目标场景定义）；竞品 A 和 B 均为 IP54（EV-012）
- 验证：按 GB/T 4208-2017 标准进行 IP54 测试
- 验收标准：通过 GB/T 4208-2017 IP54 全部测试项目，无进水、无功能异常
```

**差的结构需求**：
```
需求：外壳
- 好看，防水
- 验收标准：外观良好
```
问题：无 IP 等级目标、无密封方案、无验证标准。

### 常见陷阱

1. **把 PRD 写成产品定义**：PRD 不应重复讨论"为什么做""做不做"，而应聚焦"怎么做""怎么验收"。如果发现自己在写市场分析或竞品对比，应回到 PRD 的"怎么做"视角。

2. **软件/硬件/结构模块写成"待定"**：写 PRD 时习惯只写软件功能，对硬件和结构只标注"待硬件团队确认""待 ID 设计"。PRD 必须给出需求规格（目标值 + 约束条件），让硬件和结构团队在约束内设计。

3. **BOM 没有备选方案**：关键器件只列一个型号一个供应商，等于写死了供应链。P0 级器件必须列至少 1 个备选。

4. **状态机遗漏升级和故障状态**：只写正常流程的状态转换，漏了 OTA 升级中的状态（升级中/升级失败/回滚）、故障状态（传感器故障/通信故障/电池故障）及对应的用户表现和恢复逻辑。

5. **Non-functional 要求写成"满足国标"**："满足国标"不是需求。应写具体的标准号和关键指标目标值。例如"按 GB 4943.1-2022 进行安全测试，漏电流 ≤0.25mA"。

6. **L1 项目过度剪裁**：L1 "轻量"指的是流程轻量，不是需求定义可以省略。即使是小改款，新增或变更的需求也必须写清楚输入/处理/输出/异常/验收标准，四模块中受影响的部分必须有实质内容。
